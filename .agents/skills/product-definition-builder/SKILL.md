# Product Definition Builder

## Overview

Use this skill to turn a user's product idea or requirement into a buildable product definition. For a UI-bearing package, define routes, screen structure, flows, visible-region responsibilities, actions, states, one platform-appropriate responsive set, per-target behavior, and trace IDs in `PRD.md`; project every target into one interactive low-fidelity `wireframes.html` containing every page; verify every page-target-state combination in a real browser with no unintended overlap, clipping, or horizontal overflow; and obtain human structural approval. That is a complete stopping point. Continue into Taste, high-fidelity preview, or a formal design-system pair only when the owner explicitly asks. Default all generated artifacts to English unless the user explicitly requests another language.

## Workflow

1. Read `references/interview-guide.md` before asking discovery questions.
2. Read `references/artifact-lifecycle.md`'s Detect Enhancement Mode section, then check whether `docs/product/PRD.md`, or another Markdown document whose title or content clearly describes the same product, already exists in the repository. Check `docs/product/.prd-staging/` in the same step: a validated but unpublished package left by an earlier run is the newer baseline, and resuming, publishing, or discarding it is the user's call before this run drafts anything. If one does, treat this run as an **enhancement** of that package, not a new one: read the existing `PRD.md`, `architecture.md`, `stack-decisions.md`, and — when present — `wireframes.html`, `design-system.md`, `design-system.json`, `market-research.md`, `research-assessment.md`, and `outcome-review.md` in full before asking anything else. Also read an existing `docs/ACTIVATION.md` for current operational context, but never regenerate or overwrite it from enhancement mode. Carry forward the product package's content, decisions, and trace IDs unchanged, and scope every remaining step to only what the new request adds, changes, or removes. Never restart discovery from a blank slate or regenerate the whole package from scratch when an existing package for the same product is found.
3. Conduct a complete but concise product interview before drafting, unless the user explicitly says to skip questions, make assumptions, or produce a first draft immediately. Run the open-ended discovery as three bounded free-text turns from `references/interview-guide.md`: **Product and users**; **Workflows, data, and rules**; then **Delivery, success, and risk**. Ask exactly one segment per turn, end the turn, and wait for the user's reply. Before each later segment, use everything already known to omit answered or inapplicable prompts; if the user answers a later topic early, do not repeat it. Tell the user in segment 1 that applicable multiple-choice decisions follow only after all applicable free-text segments are complete. Do not call `AskUserQuestion` during any free-text segment. In enhancement mode, first classify the delta's UI impact with the owner — `none`, `structure`, `style`, or `both`, per `references/interview-guide.md`'s Enhancement Mode; never assume `none`, because most enhancements are design-side. Then run only the segments the requested delta changes or leaves unresolved, and carry every unaffected answer forward unchanged.
4. Run the research-first assessment per `references/research-first-guide.md` before any closed-set decision: a bounded, read-only pass over segment and problem evidence, jobs to be done, existing alternatives, integration and adoption baseline, and market-side risks, applying `references/market-research-guide.md`'s Source Rules unchanged. It is on by default for a non-trivial new package; skip it only when the user declined it, no web search or fetch tool is available, or the package is a trivial stub, and record which reason applied in `PRD.md`'s `### Research Gate`. The researcher recommends and the human owner decides the gate: `go` proceeds to step 5 with the assessment as input; `clarify` asks exactly the recorded unresolved questions in one bounded `AskUserQuestion` round, resolves them in `research-assessment.md`, and re-records the gate; `stop` drafts nothing — report the findings and leave `research-assessment.md` in the staging directory for the user. In enhancement mode, skip this step entirely; the delta is assessed by the post-draft market-research pass. Stage `research-assessment.md` with the package and publish it to `docs/product/research-assessment.md`; its findings mint stable `RA-*` IDs that `PRD.md` cites exactly like `MR-*` IDs.
5. After all applicable free-text segments have replies and the final coverage check has no material gap, use their aggregate answers to skip resolved or inapplicable decisions, then issue the first `AskUserQuestion` call, sized to the question tool's actual per-call question and option limits, resolving the remaining closed-set decisions marked `(AskUserQuestion)` in `references/interview-guide.md` that depend on no other answer: product archetype and validation depth. Do not issue this call in the same turn as any free-text segment or targeted free-text follow-up. Keep the deployment platform out of this call. It only means something once the archetype is known, so step 7 carries it. Do not ask the user to choose from a fixed high-fidelity style catalog during discovery; the later UI Design Pass derives a product-specific direction from the approved wireframes. In enhancement mode, only re-ask a closed-set decision the new idea actually reopens; otherwise keep the existing package's answer.
6. For a UI-bearing product, capture a `Builder UX Direction Decision` before visual work. Resolve the builder to the human product/design decision owner or commissioning team. Use the minimum number of `AskUserQuestion` calls permitted by the tool's actual per-call limit for the closed dimensions — experience priority, guidance versus expert control, information density, and preferred layout/interaction pattern — and capture confirmation/recovery behavior as free text, since it varies too much by action to enumerate further. Validation depth is already answered by step 5's call; carry that answer forward instead of re-asking it. Mark every decision `selected`, `provisional`, or `assumed`. In enhancement mode, only revisit a dimension the new idea actually affects. The UI Design Pass and any later `design-system-compiler` compilation consume this decision and do not replace it with agent taste.
7. Issue the next `AskUserQuestion` call or calls, each sized to the question tool's actual per-call limit, for every applicable closed-set decision that depends on step 5's archetype answer, marked `(AskUserQuestion)` in `references/interview-guide.md`:
    - the deployment platform (Cloudflare / Vercel / AWS / Self-hosted, plus the tool's built-in Other for anything else, including an explicit stage-to-provider mapping) when the resolved surface includes a deployable web, API, or hosted backend target;
    - the mobile platform follow-up when an archetype is a mobile app, and the desktop platform follow-up when one is a desktop app;
    - the database category and auth strategy for a product with a backend, persistent data, or auth requirement — evident from the free-text interview's data/integrations and business-rules answers, or the archetype captured in step 5.
    - the monetization model when the product has commercial intent or an unresolved pricing strategy, and the partner channel when outside promoters or sellers may contribute revenue. These decisions select a model, not a provider; apply `references/monetization-and-partner-channel-guide.md` afterward to recommend RevenueCat or another current fit.

    Skip any question the archetype makes inapplicable, or that the user's prompt, the existing package, or the current repository already answers. A browser-extension surface is not asked the deployment-platform question: it ships through a browser add-on store, not a hosted web target, and resolves distribution with `references/architecture-playbook.md`'s Browser Extension Pattern. Local persistence or local-only auth may require the backend/data decision pair and backend analysis without creating a hosted deployable surface; `has_backend` alone never triggers the deployment-platform question. Skip the database-category and auth-strategy pair only when the product provably has no backend, persistent data, or auth surface, such as a purely static content or marketing site with no forms, accounts, or dynamic data. Skip monetization and partner-channel questions only under their recorded rules; pricing never silently selects RevenueCat, and affiliate, referral, and reseller are not interchangeable. Skip the whole phase only when none of its questions apply. Do not drop an applicable decision to satisfy an invented total-call budget, and do not silently pick a database category, auth strategy, monetization model, partner channel, provider, deployment platform, mobile platform, or desktop platform on the user's behalf.
8. Classify the product as one or more archetypes: web app, mobile app, desktop app, browser extension, internal tool, automation or agent workflow, API or backend service, or hybrid. For a mobile app, also record the resolved mobile platform (native iOS, native Android, Flutter, or React Native); for a desktop app, also record the resolved desktop platform (macOS, Windows, or cross-platform); for a browser extension, also record the resolved browser target (Chrome with Manifest V3 by default; Firefox or Safari as explicit alternatives) — since these select the matching pattern in `references/architecture-playbook.md`. Record whether it has any public-facing marketing, landing, or SEO-relevant page as distinct from purely internal or authenticated-only surfaces; this gates the SEO copy review below.
9. After discovery, read `references/output-contract.md`, `references/wireframe-guide.md`, `references/ui-design-pass.md`, `references/ui-grading-rubric.md`, `references/architecture-playbook.md`, `references/dynamic-workflow.md`, `references/research-first-guide.md`, and `references/market-research-guide.md`, plus the rest of `references/artifact-lifecycle.md`. When monetization or partner distribution may apply, also read `references/monetization-and-partner-channel-guide.md`. For a web app, internal tool, public website, browser extension, or hybrid with a browser frontend, also read `references/frontend-stack-selection.md`. For any product with a backend, persistent data, or auth requirement — most products other than a purely static content site — also read `references/backend-stack-selection.md`. For a mobile-app or desktop-app surface, also read `references/mobile-stack-selection.md`; its desktop platform patterns live in `references/architecture-playbook.md`.
10. Before drafting, inventory earlier documents related to the same product as described in `references/artifact-lifecycle.md`. Do not move anything yet. In enhancement mode, this still includes the existing package identified in step 2 — it will be archived for history once the enhanced draft is published, even though its content already carried forward into that draft.
11. For a non-trivial package, run `assets/templates/CLAUDE_PRD_WORKFLOW.template.js` only when Claude Code Dynamic Workflow is observed, the parent has an explicit multi-agent authorization for this run, `args.multi_agent_authorized` is `true`, neither single-agent nor sequential-only execution is required, and the host can enforce the `builder_readonly` tool profile from `references/dynamic-workflow.md`. Pass the authorization decision into the workflow arguments; capability or tool availability never grants authorization. Run it only after the interview, the `AskUserQuestion` decisions, source inputs, monetization and partner-channel models, explicit expected deployable-surface inventory, and provider-neutral release targets are frozen. Skip the workflow in enhancement mode: its lanes generate fresh content, which is exactly what step 2 forbids. Perform the roles sequentially against the existing package instead. Retain failed lanes explicitly and treat the returned package as a candidate for parent review. If Dynamic Workflow, the authorization, or the read-only boundary is unavailable, perform the same roles sequentially and state that fallback.
12. Draft or repair the core Markdown package in the staging location defined by `references/artifact-lifecycle.md`:
    - `PRD.md`
    - `architecture.md`
    - `stack-decisions.md`
    - In every package, record the Monetization Infrastructure Gate and Partner Channel Gate in `PRD.md`, including explicit `not_required` reasons. When either applies, carry its separately selected layers into `architecture.md` and `stack-decisions.md`; do not collapse billing, entitlement, merchant-of-record, affiliate, referral, and reseller responsibilities into one vendor label.
    - For a UI-bearing product, create `wireframes.html` using `references/wireframe-guide.md` and `assets/templates/WIREFRAMES.template.html`. Run `references/wireframe-guide.md`'s Reference Pass before drafting the HTML: fetch the structures of mainstream comparable sites, pull gallery composition references such as Dribbble, and record them in `PRD.md`'s `### Wireframe Approval` as `Wireframe references consulted:`, or record which reason skipped the pass. It is one self-contained interactive file containing every `UI-*` surface, an all-pages overview, page switcher, data-driven responsive-target controls, state control, visible section-purpose labels, runtime layout QA, and working PRD actions that switch pages, open local overlays, or show local feedback. A screen or region whose motion or imagery treatment is already decided carries one visible `mediaIntent` note with its dedicated draft prompt, owner source, and `generationStatus: deferred`; this is a later MCP-generation handoff, not permission to generate now. `PRD.md` remains the source for scope and behavior; the HTML is the only wireframe deliverable.
    - Do not start the UI Design Pass or invoke `design-system-compiler` automatically. An approved `wireframes.html` completes the wireframe stage. Step 15 runs only when the original request or a later explicit owner instruction continues into visual design.
    - For a product with no UI surface — a headless API or backend service, or an automation whose only surfaces are notifications it sends into someone else's UI — do not create `wireframes.html`, run a UI Design Pass, or invoke `design-system-compiler`; record the skip in `PRD.md` and publish no placeholder UI or design files.
    - Draft `DEPLOYMENT.md` from `../delivery-harness/assets/templates/DEPLOYMENT.template.md` when the package has a deployable surface: record the platform chosen in the deployment decision; seed the Required Secrets and Variables inventory with every exact name already established by the product or architecture; record known auth callbacks, allowed origins, webhooks, domains, roles, and other provider-side work in External Console Setup; and leave their human-owned statuses plus the remaining Human Setup Checklist for the owner. Record names and destinations only, never values. Do not invent implementation-owned key names or URLs: leave them visibly unresolved for `delivery-harness` to reconcile from the finished code before the first deployable push. A purely local product records `manual` mode or skips the file with a note in `stack-decisions.md`. Publish it to `docs/DEPLOYMENT.md` with the package.
    - When the package has a web, iOS, or browser-extension release target and `docs/ACTIVATION.md` does not already exist, resolve `../product-activation/assets/templates/ACTIVATION.template.md` and create one `ACTIVATION.md` seed. Fill the product, owner when known, selected `core` plus surface profiles, only those supported release target IDs, and one Outcome Coverage row for every PRD metric and required `TEST-*` signal scoped to that supported target subset. Leave Android, desktop, API-only, and other unsupported targets outside the Activation seed, including in a hybrid package. Leave implementation-owned actions, routes, accounts, queries, release SHAs, artifact/build identities, sources, and evidence visibly pending. Run the sibling `product-activation/scripts/check_activation.py --activation <staged ACTIVATION.md> --prd <staged PRD.md>` before publication. Publish the seed to `docs/ACTIVATION.md`. If the live path already exists, preserve it byte-for-byte, stage no replacement, and record in `DOCUMENTS.md` that `product-activation` must reconcile it after delivery.
    - Draft `DOCUMENTS.md` from `../delivery-harness/assets/templates/DOCUMENTS.template.md` as the manifest of every flow document, publish it to `docs/DOCUMENTS.md`, and fill the status column for each document this package creates; keep it current through publish and archive.

    A product is UI-bearing when a person interacts with a surface this product ships. A native mobile or desktop app is UI-bearing without a browser frontend; an internal tool with one admin screen is UI-bearing; a service whose only output is an API response, a webhook, or a message posted into a third-party client is not.

    After drafting, run `references/wireframe-guide.md`'s quality check and Wireframe Approval Gate. In a real browser, inspect every `UI-*` surface at every declared viewport or size class and every non-`n/a` state. The template's layout QA must report no region collision or horizontal overflow, and every visible action must perform its PRD-recorded page, overlay, or feedback behavior. Before the owner gate, bind the candidate to the exact PRD revision or hash and apply `references/ui-grading-rubric.md`: when the host has multi-agent browser capability and dispatch is explicitly authorized, three fresh read-only graders score wireframe scope and every `block` is repaired; when the capability is unavailable, record the exact capability-unavailable skip and continue. Record the resulting `UI grading:` line in the same approval record. Present `wireframes.html`, record the owner, decision, date, approved `UI-*` scope, exact responsive set, states, browser check, and unresolved items in `PRD.md`'s `### Wireframe Approval`, and show the status in the HTML. Then run `python <product-definition-builder-root>/scripts/check_wireframe_html.py --html <staged wireframes.html> --prd <staged PRD.md> --require-filled --require-approved`; the `--prd` cross-check fails when the wireframe screens and the structured PRD `UI-*` entries differ in IDs, their one literal route, exact state sets, or responsive set. Missing, rejected, unapproved, browser-failing, or checker-failing HTML blocks later visual work. Approval confirms structure only, not usability or visual style.

    In enhancement mode, start from the existing package's content: preserve unaffected sections, wireframe entries, `PRD-*`, `ARCH-*`, `UI-*`, `UX-*`, `TEST-*`, `DS-*`, `MR-*`, `RA-*` IDs, and stable release target IDs verbatim, edit or add only what the new discovery changed, mint new TEST IDs only for newly uncovered obligations, and add release target IDs only for new destinations. Apply the UI-impact classification from step 3 through `references/wireframe-guide.md`'s Enhancement Revisions: `none` preserves `wireframes.html` and any approved UI target verbatim; `structure` or `both` updates the affected `UI-*` entries in `PRD.md`, regenerates the affected wireframe pages, and re-runs the Wireframe Approval Gate on the changed scope; `style` or `both` asks the owner to re-run the UI Design Pass or explicitly confirm the existing direction and records that decision — a stale visual contract never publishes silently.
13. Produce `implementation-plan.md` only when the user explicitly asks for delivery sequencing or implementation planning. Its test strategy must reuse the canonical `TEST-*` IDs from `PRD.md`; it may add sequencing and implementation detail but must not create anonymous replacements or duplicate TEST identities. Its release plan must also reuse the stable release target IDs from `architecture.md` rather than renaming destinations.
14. Run the market-research gap pass against the drafted package, following `references/market-research-guide.md`. It is on by default for a non-trivial package; skip it only when the user declined it, no web search or fetch tool is available, or the package is a trivial stub, and record which reason applied. Delegate it to one bounded read-only researcher using exactly one of these authorized routes: (a) the `market-research` lane of `assets/templates/CLAUDE_PRD_WORKFLOW.template.js` only when step 11 actually ran the authorized workflow; (b) a single read-only subagent only when the parent has a separate explicit subagent/delegation authorization for that researcher; or (c) the parent doing the same role inline when no delegation authorization is present, the user/host requires single-agent or sequential-only execution, or the workflow was unavailable. Never infer the single-subagent grant from tool availability, the fact that the package is non-trivial, or a workflow fallback. The researcher reads the drafted `PRD.md` — plus `research-assessment.md` when the research-first pass ran — and returns `market-research.md` plus gap findings; it never edits a file. The pass is a reconciliation: carry still-valid `RA-*` findings and their sources forward unchanged, re-check what the draft changed, and research only what the assessment left `UNVALIDATED` or what the draft newly raises. Stage `market-research.md` with the rest of the package, apply the findings the user's scope allows — including evidence that strengthens or contradicts a `stack-decisions.md` layer row or alternative — cite the supporting `MR-*` IDs in the sections they change, and record anything that would widen scope as an open question instead of acting on it. Every claim carries a source URL, publisher, and retrieval date, or it is recorded `UNVALIDATED` — never invent a competitor, price, or market figure. If the role returns blocked, publish without the artifact and record the unvalidated market context in `PRD.md`'s `## Assumptions`.
15. Only when the owner explicitly requests visual design, and after the PRD UI surface contract, approved `wireframes.html`, and market-research gap pass are resolved, run `references/ui-design-pass.md` directly from this skill. Otherwise record `Visual design phase: not requested` and complete the package at the wireframe stage.

    Resolve the design-direction skill from the repository's Skill Bindings table in its `AGENTS.md` when one is bound; otherwise use the bundled default `design-taste-frontend`, and record `applicable`, `partially_applicable`, or `n/a: <reason>`. The visual phase opens from the approved PRD package and runs as one combined pass with both skills: the design-direction skill leads the overall direction, and the frontend-implementation skill covers the direction skill's excluded surfaces. Apply it to landing, portfolio, editorial, public marketing, and compatible redesign surfaces. For dashboards, data tables, multi-step product UI, native mobile, or another declared exclusion, load the bound frontend-implementation skill (default `frontend-design`) for the uncovered surfaces instead of forcing Taste to apply. Never combine two design-direction skills — an alternative such as `gpt-taste` is an explicit owner-selected swap for a named scope only.

    Ask the human owner once for style preferences and visual references, including the closed key-surface treatment question from `references/ui-design-pass.md` — hero first: motion-led, imagery-led, both, or quiet. Treatments already annotated in `wireframes.html` as `mediaIntent` arrive pre-answered, and their draft prompts are refined into a deferred later MCP-generation handoff; this pass does not invoke a generation provider. Also inspect relevant readable candidates under `docs/design/`, any user-named design folder, and obvious in-scope design images found during the normal bounded scan; repository presence alone never makes one binding. Then produce one recommended product-specific direction by default. Produce three comparable directions only when the owner requests alternatives or a recorded visual conflict needs comparison. A direction may call itself market-supported only when valid `MR-*` evidence applies; a market-research URL is not visual evidence until it is separately inspected. Choose iconography through `references/ui-design-pass.md`'s online lookup as part of the direction: recommend one primary icon set plus a named fallback from the closed candidate set — Lucide, Phosphor, Heroicons, and Tabler — record them in the handoff's `Iconography:` line with cited official sources, and never silently default to a remembered library. Choose typography with the same lookup discipline — display/body pairing, Latin plus CJK coverage, loading strategy — and record the color derivation and dark-mode scope, in the handoff's `Typography:` and `Color & dark mode:` lines.

    Run the UI Preview Gate for every in-scope `UI-*` screen and its complete responsive-target and non-`n/a` state matrix. Login, registration, recovery, and authentication-error previews are omitted and recorded `n/a` for this visual pass without deleting production authentication requirements. Every UI-bearing product — web, native or cross-platform mobile, and desktop — uses one self-contained high-fidelity HTML review file as the implementation reference. It contains complete CSS and review JavaScript, a left sidebar, working page and state switching, and every product action needed to traverse the approved flows; visible controls navigate, switch state, open the documented modal or drawer, or show recorded feedback. Image and motion positions remain visible static placeholders carrying dedicated prompts, source decisions, triggers or placements, reduced-motion expectations, and `generationStatus: deferred`; do not invoke a generation provider or claim generated output during this pass. Render every in-scope page-target-state and overlay in a real browser and reject dead controls, broken navigation, unintended overlap, clipping, occlusion, or horizontal overflow. Before the human visual decision, bind the candidate to the exact PRD revision or hash and apply `references/ui-grading-rubric.md`: when multi-agent browser capability exists and dispatch is explicitly authorized, three fresh read-only graders score the high-fidelity HTML. A below-threshold result returns to the owning design flow for refinement, a new candidate hash, and the complete hard-gate/browser/grading sequence again; never present it for approval. Continue until it passes, the owner stops, or a PRD gap returns upstream. When capability is unavailable, record the exact skip and continue with the non-grading gates. Record path, SHA-256, limitations, browser evidence, grading/refinement history or skip, deferred generation handoff, and the human decision. Preview artifacts remain outside `docs/product/`.

    After approval, record the selected direction and immutable page-faithful HTML target in `PRD.md`'s `### UI Design Handoff`, including frozen PRD identity, included and auth-preview-`n/a` scope, states, responsive coverage, working interaction evidence, grading scores or capability-unavailable skip, deferred image and motion handoff, tolerance, and allowed deviations. Then run the Design System Need Gate. Mark it `required` when the owner asks for a formal system, an existing pair is canonical, or shared tokens and closed variants are needed across multiple surfaces, themes, platforms, teams, or automated checks. Mark it `not_required` for a small or single-surface UI whose approved target plus PRD and `wireframes.html` are sufficient. Mark it `blocked` when the decision cannot yet be made.

    Only when the result is `required`, load `design-system-compiler` and pass it the approved UI Design Handoff plus the staged product sources. It owns `design-system.md` and `design-system.json` and compiles the selected direction without reopening visual exploration by default. When the result is `not_required`, publish no placeholder pair; the approved UI target is the replacement visual contract. If a required skill or preview decision is unavailable, stop with the core documents staged and report the blocker.
16. Run the quality checklist in `references/output-contract.md` against the staged package. Before publishing, every `stack-decisions.md` layer row must be `Required`, `Selected`, or `Recommended`: a `Provisional` row blocks publication until it is resolved with the user or the user explicitly accepts it as `Provisional`, and that acceptance is recorded in `stack-decisions.md` — `delivery-harness` treats a Provisional layer as a stop condition at scaffold time, so a silent one stalls implementation. Resolve every required workflow lane and material verifier finding before finalization.
17. After validation, show the exact publish paths, overwrite targets, and archive moves. If the original request already authorized those exact mutations, perform them immediately. Otherwise, immediately after listing them, ask one explicit yes/no publication question. If the user approves, execute the approved publish and archive moves in the same run using `references/artifact-lifecycle.md`, and remove the now-empty run-specific staging directory as the final step of that same run — publication is not complete while a redundant staged copy still sits in `docs/product/.prd-staging/`; if the user declines or does not answer, leave the validated staging package intact and report it as ready to publish. Never archive documents when the workflow is incomplete, paused, failing validation, or awaiting approval.
18. In the same publish move set, resolve the sibling `../delivery-harness/scripts/configure_project_context.py` from this skill package and run `python <delivery-harness-skill-root>/scripts/configure_project_context.py --root <target-root> --check`. List each missing `AGENTS.md` or `CLAUDE.md` with step 17's publish paths. After the exact creations are approved, run the same command without `--check`; it creates only missing files, using `PROJECT_AGENTS.template.md` for `AGENTS.md` and the distinct `PROJECT_CLAUDE.template.md` for `CLAUDE.md`. Never copy one template to both files, and never overwrite, merge, or normalize an established root context file. If the user declines publication, seed nothing. When the creation is approved, fill the new `AGENTS.md`'s Skill Bindings table as part of the same publish: list the locally installed skills visible to this session — user-level and project skill directories plus the host's installed plugin skills — name the candidates for each slot (`design_direction`, `design_compilation`, `frontend_implementation`), confirm the bindings with the owner in one `AskUserQuestion` over those candidates, and write the confirmed skills into the table with the SHA-256 of each bound skill's `SKILL.md` (print them with `../delivery-harness/scripts/check_skill_bindings.py --agents-md <root>/AGENTS.md --skill-dir <dir> --show-hashes`); slots with no local candidate or an explicit owner default stay at the bundled default. An existing root `AGENTS.md` is never reopened for this — propose a binding update as its own explicit edit instead. As the publish's final move, run `python <delivery-harness-skill-root>/scripts/configure_project_context.py --root <target-root> --check --require-resolved` and report any unresolved placeholder it finds.
19. Report the final artifact paths, every seeded root rules file, the created or preserved Activation record, and every archived path.
20. After reporting a completed wireframe-stage package, say that visual design and implementation are separate optional next phases; do not invoke or automatically offer either. If the owner later requests Harness work after the visual phase is complete, state what it consumes: `PRD.md` for scope, behavior, and the approved UI Design Handoff; `wireframes.html` for low-fidelity page, section, state, and responsive structure; `architecture.md` and `stack-decisions.md` for implementation constraints; plus `design-system.md` and `design-system.json` only when the Design System Need Gate marked the pair `required`. When the gate is `not_required`, Harness consumes the recorded approved page-faithful UI target instead — normally the retained single high-fidelity HTML reference containing every page and its recorded hash.
21. When the owner asks for an outcome review after a deployment, produce `outcome-review.md` per `references/output-contract.md`: the deployed SHA with its release reference, the measurement window, each `PRD.md` `## Metrics` target and `TEST-*` expected signal with its baseline and actual, observed feedback, and one verdict — `no_change`, `enhancement`, or `incident`. When `docs/ACTIVATION.md` exists, read it in full and run the sibling checker with `--prd docs/product/PRD.md --require-verified-sources` plus `--require-ready` for every reviewed release target in its supported active target set; use only matching verified `MS-*` sources. Record Activation as `n/a` for a reviewed target outside that set instead of pulling an unsupported hybrid target into the gate or inventing a source. Missing Activation remains an explicit legacy or `n/a` state, never a guessed source. Run the review as its own bounded step once the measurement window has closed; never leave a run open waiting for adoption. Publish it to `docs/product/outcome-review.md` through the same approval-gate discipline as any fixed publish path, archiving a superseded review with the package. An `enhancement` verdict's findings become the input to the next enhancement request; an `incident` verdict's findings enter the next run's `PRD.md` `## Risks` and `## Open Questions`; every later run reads `outcome-review.md` in full during enhancement detection.

## Interview Rules

- Run discovery in two phases. First, ask the three bounded free-text segments in order: **Product and users**; **Workflows, data, and rules**; **Delivery, success, and risk**. Ask one segment per turn and wait for its reply. Dynamically omit already answered or inapplicable prompts from later segments, but do not merge multiple planned segments into one long message. After segment 3, compare the aggregate answers with `references/interview-guide.md`'s completeness criteria. If a material item is still missing and assumptions are not authorized, ask one compact targeted free-text follow-up containing only those gaps. Only after all applicable segments and that optional follow-up are complete may the closed `AskUserQuestion` batches begin. Use the tool's built-in Other option instead of inventing a separate free-text fallback. Do not run a fixed high-fidelity visual-style questionnaire here.
- Step 7's questions always come after the archetype and Builder UX calls — never fold them into step 5 or step 6. The deployment platform and the mobile/desktop platform follow-up depend on step 5's archetype answer, so asking them in that batch asks about a surface nobody has named yet. Batch each phase to the question tool's actual per-call capacity and ask every applicable decision; there is no host-specific total-call target. The first `AskUserQuestion` call starts only after every applicable free-text segment has a reply and the coverage check passes, so no multiple-choice form interrupts the open-ended sequence.
- Do not ask questions already answered by the user's prompt.
- Before drafting, finish release discovery with stable surface IDs and development/production target IDs. Keep `surface` separate from stage-specific `provider`. Under the standard promotion contract, development builds from `development` after exact-SHA promotion and production builds from `main` only after internal development PASS; initial delivery starts from `main`, while enhancements start from `development`. Record any explicit alternative source rule. Also close artifact/signing, channel, release gates, availability, rollout, and recovery. These are not extra closed-set `AskUserQuestion` calls.
- Mark optional questions clearly when they would improve quality but should not block progress.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.
- If the user gives conflicting requirements, resolve them before drafting or call out the conflict in `open questions`.
- Treat builder preference as a direction input, not as proof that users find the result usable. When it conflicts with user evidence or an accessibility requirement, record the conflict and validation need instead of silently following preference.
- In enhancement mode (Workflow step 2), never repeat questions the existing package already answers. Scope the free-text message and every `AskUserQuestion` call to what the new idea adds, changes, or leaves genuinely unresolved.

## Output Standards

- Write each artifact for the primary reader named in `references/output-contract.md`'s "How To Read This Package", and respect its length budget. Completeness is not the only bar — a document nobody finishes reading has not delivered its requirements.
- Put meaning before bookkeeping in every artifact. Open with what a human needs to understand the product; close with the ID matrices and decision records that machines, auditors, and downstream skills need. Never open a document with a trace table.
- Keep tables at seven columns or fewer, except the mandated hosted environment contract in `architecture.md`, whose columns are all release-critical. When a row needs more fields than that, write one block per item instead of widening the table.
- Prefer specific, buildable requirements over vague product language.
- Keep the current PRD package directly under `docs/product/`; reserve `docs/product/archived/` for superseded documents only.
- Tie every major requirement to a user need, workflow, metric, or constraint.
- Mint stable upstream trace IDs: `PRD-*` for product requirements, `ARCH-*` for architecture contracts, `UI-*` for UI surfaces, `UX-*` for usability requirements, `TEST-*` for test obligations, `MR-*` for market-research findings, and `RA-*` for research-first assessment findings. `design-system-compiler` owns `DS-*` and `DS-COMP-*`. Preserve every family across revisions and never reuse a retired ID for a different meaning.
- Keep market research evidence in `market-research.md` and conclusions in the artifact they affect. `PRD.md` cites the `MR-*` ID behind a statement; it does not restate the competitor table, the sources, or the retrieval dates. A market claim with no source is recorded `UNVALIDATED` with what was searched, never stated as fact and never invented.
- Keep `## Non-Functional Requirements` in every `PRD.md`, immediately after Functional Requirements. Use `PRD-*` IDs and record every applicable quality attribute with a scoped measure and target; record non-applicable categories explicitly as `N/A` with a reason. Vague words such as `fast`, `secure`, `reliable`, or `scalable` are invalid without measurable units, population or traffic shape, measurement window, and percentile where applicable.
- Keep `## Test Obligations` in every `PRD.md`, after Open Questions and before the trailing Builder UX decision. Use the canonical columns from `references/output-contract.md`. Map every `Must` functional requirement and every applicable NFR to at least one `TEST-*` row marked required, with upstream trace IDs and a literal or measurable expected signal.
- For every UI-bearing product, record the Builder UX Direction Decision and Wireframe Approval. Record a UI Design Handoff only when the owner explicitly requests and completes the later visual-design phase. Do not let a design or implementation agent invent its own taste when the human decision owner has not answered; use an explicit provisional assumption only when assumption mode is authorized.
- Include loading, empty, error, permission, and edge states when a UI or workflow has them.
- Treat `PRD.md` as canonical for product scope, UI behavior, the exact responsive set, and the approved UI Design Handoff. Treat `wireframes.html` as the single approved low-fidelity projection used to inspect page layout, per-target region order and spans, grouping, visibility, element inventory, states, responsive rearrangement, and runtime overlap/overflow status. `PRD.md` wins when scope or behavior conflicts with the HTML or a visual target. When required, `design-system-compiler` owns the high-fidelity design-system pair and preserves `DS-*` and `DS-COMP-*` across revisions.
- This skill owns the product definition, UI surface contract, low-fidelity wireframes, direct UI Design Pass, and Design System Need Gate, not production UI implementation. It creates no design system, production component, Harness plan, mission map, PLAN/RUN state, or E2E evidence register. `design-system-compiler` creates the pair only when required; `delivery-harness` implements either that pair or the approved replacement visual contract.
- Keep assumptions explicit and avoid hiding unresolved decisions in confident prose.
- Architecture may remain technology-neutral overall. For every product with a browser frontend, record the required or already selected frontend stack, or recommend one explicit stack when the user has not chosen and discovery provides enough evidence. On every layer row record Selection, Status, cited Authority/evidence, Why it fits, and Constraint/follow-up; sections may mix statuses, authority is a cited source rather than a status label, and a recommendation is not misrepresented as a fixed requirement. Record the deployment platform, rendering model, framework, UI library, styling approach, build tool, and key supporting choices as separate layers.
- For every deployable web, API, mobile, desktop, or browser-extension surface, close a provider-neutral release-target contract before drafting. Record the complete expected deployable-surface inventory with stable surface IDs, then give every target a stable target ID and a `development` or `production` stage. Record stable `surface` separately from stage-specific `provider`, the source policy (the exact branch or ref each stage's release builds from), artifact kind, signing requirement, exact channel or track, submission/promotion/review or manual-approval path, actual availability signal, rollout, and rollback or forward-fix path. Require development and production targets for every expected surface; reject missing surfaces. Providers may differ by stage. Preserve surface and target IDs across revisions and never reuse an ID for a different meaning. An upload, submission, or approval is not availability by itself.
- For a deployable web or API target, resolve the deployment platform explicitly via the interview's platform `AskUserQuestion` step (see Workflow step 7, after the archetype is known) unless the user or current repository already names one. Never silently assume a platform, and do not invent platform-specific requirements for docs-only work. Record one codebase promoted through separate development and production environments (named Workers for Cloudflare, or the platform's equivalent unit), exact release sources, isolated bindings and secrets, data/auth/payment modes, migration order, deployed-environment checks, and rollback.
- Keep native mobile and desktop targets in the provider-neutral release-target contract rather than forcing them into the hosted web/API environment table. For store or signed-installer delivery, production availability means the approved artifact is actually installable or downloadable through the named channel and passes its smoke check. When instant rollback is impossible, record rollout halt plus a signed forward-fix through the same review or distribution path.
- For every product with a backend, persistent data, or auth requirement, record the required/selected backend stack, or recommend one explicit stack when evidence supports it, following the same per-layer status and cited-authority discipline as the frontend. Record service topology first — monolith versus named services and monorepo versus polyrepo organization — followed by backend runtime/framework, database category, database engine, auth strategy, auth provider, and key supporting choices (API style, background jobs/queue, file/object storage) as separate layers.
- For a product with a backend, persistent data, or auth requirement, resolve the database category and auth strategy explicitly via the interview's backend/data `AskUserQuestion` step (see Workflow step 7) unless the user or current repository already names them. Do not silently pick a database category or auth strategy on the user's behalf. Never silently default to a specific database engine or auth vendor.
- For every product with a mobile app or desktop app target, record the required or already selected mobile/desktop stack in a `Mobile/Desktop Technology Decision` section, or recommend one explicit stack per `references/mobile-stack-selection.md` when the user has not chosen and discovery provides enough evidence, following the same per-layer status and cited-authority discipline as the frontend and backend sections. Record the platform, toolchain, distribution mechanism, backend/API integration, push/offline-sync approach, and testing as separate layers. This section may be added in a later revision after `Frontend Technology Decision` is already frozen, when a mobile or desktop target is added to an existing web product.
- Do not present Cloudflare, Astro, React, and Vite as peer alternatives: Cloudflare is a deployment/runtime platform, Astro is a web framework, React is a UI library, and Vite is a build tool that can be paired with React or used by frameworks.
- Keep a decision technology-neutral only when evidence is genuinely insufficient. In that case, document the missing evidence, decision owner, decision deadline, and a time-boxed spike with pass/fail criteria.
- When recommending a fast-moving hosted platform or framework, verify current official documentation and record the check date and sources in `stack-decisions.md`.
- Treat the stable PRD roles as an org graph and each bounded workflow run as a temporary work graph. Dynamic Workflow coordinates read-only analysis; the parent still owns source freeze, staged artifact writes, conflict resolution, approval, publication, and cross-session recovery.
- When `implementation-plan.md` is requested, include non-canonical Harness handoff signals for dependency order, parallel candidates, shared resources, required reviews, and human gates. Do not create PLAN/RUN mission maps in this skill.
