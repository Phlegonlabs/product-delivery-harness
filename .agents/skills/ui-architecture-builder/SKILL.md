# UI Architecture Builder

## Overview

Use this skill to turn product and wireframe inputs into a UI architecture package that both humans and agents must build through. Default all generated artifacts to English unless the user explicitly requests another language.

The binding rule the published package exists to enforce:

> A page cannot be freely designed. A page may only use approved content contracts, page recipes, product components, and primitives.

That rule begins only after the human has approved a selected HTML direction and the package has extracted its tokens, primitives, components, recipes, and registry from that approved visual source. Before approval, candidate HTML is an exploration artifact: it may use direction-local values and composition, and it must not be constrained by a registry that does not exist yet. This late-freeze boundary keeps an agent's later pages consistent without forcing the visual exploration itself through a prematurely fixed system.

This skill owns the UI architecture and visual layer. It does not create PRDs, backend architecture, implementation plans, harness plans, mission maps, or E2E evidence registers, and it does not write the product's real component code — `fullstack-harness-engineering` implements the architecture this package specifies.

## Workflow

1. Inspect the document folder first — the one the user names, the one the upstream handoff named, or `docs/product/` when a package is already published there — and identify product inputs such as `PRD.md`, `architecture.md`, `stack-decisions.md`, `wireframes.md`, and `implementation-plan.md`. Before discovery, detect whether the fixed UI-package paths in `references/artifact-lifecycle.md` already contain a package for the same product. If they do, enter **package enhancement mode**: read the complete existing package, freeze its files, IDs, content, artifacts, and decisions as the enhancement baseline, and record the requested add/modify/remove delta separately. Package enhancement is not the greenfield-versus-phased-migration **implementation adoption mode** recorded inside the package; one revises the design package, while the other governs how implementation adopts it. Read `architecture.md`'s `Product Archetype` section, plus `stack-decisions.md`'s Frontend and Backend Technology Decision and — for a native mobile or desktop target — its Mobile/Desktop Technology Decision, to extract the resolved platform (web, native iOS, native Android, Flutter, React Native, macOS, Windows, cross-platform desktop, or a hybrid) before the design interview. Carry that resolved platform forward and do not re-ask it in step 5–6, matching this skill's "do not ask questions already answered" convention. The platform decides the visual vocabulary (`references/visual-decision-guide.md`): every platform's page mockup is a real, viewable HTML file (HTML is a visual demonstration medium here, not the target's production technology), styled to the resolved platform's own conventions — iOS/macOS HIG cues, Android/Material cues, or desktop window chrome — rather than defaulting to web styling for a native or desktop target.
2. Locate the PRD's `Builder UX Direction Decision` when a UI-bearing product is in scope. Preserve its human decision owner and `selected`, `provisional`, or `assumed` status; if it is missing, use the design interview to ask for it before choosing the visual system.
3. Read `references/design-interview-guide.md` before asking design discovery questions.
4. Conduct a concise design interview unless the user explicitly says to skip questions or make assumptions. Scope this free-text message to the open-ended discovery categories in `references/design-interview-guide.md` (product/audience narrative, brand cues and recognizability, per-page/region scope and content, and confirmation/recovery behavior). In package enhancement mode, ask only about the requested delta and conflicts it creates; do not rediscover or reopen untouched baseline decisions.
5. Resolve closed technical and product decisions in at most three dependency waves, with at most four questions in each wave. Wave 1 covers the design target and platform-independent decisions. Wave 2 is conditional platform resolution and runs only when a mobile, desktop, or hybrid target still needs its platform resolved. Wave 3 covers platform-specific styling/theming and animation-runtime choices, then the remaining behavioral choices that fit. Never ask a styling, theming, or runtime question while the design target or required platform is unresolved. Use the host's structured closed-choice facility when available. Otherwise present the same closed choices as numbered options, including `Other`, without selecting a default or converting the decision into an open-ended question. Skip decisions already answered by the prompt, supplied documents, or — in package enhancement mode — the frozen baseline unless the accepted delta explicitly reopens them. Do not silently answer unresolved choices; leave any that do not fit the bounded waves as explicit open questions. Visual preference discovery is a separate contextual Ask User step in step 9; do not spend these waves on a fixed catalog of styles.
6. Confirm the design-target classification from the resolved wave answer: SaaS app, dashboard, internal tool, public website, marketing page, docs/content site, ecommerce/catalog, mobile app (native iOS, native Android, Flutter, or React Native), desktop app (macOS, Windows, or cross-platform), or hybrid. When step 1 already resolved the platform from the upstream product package or enhancement baseline, carry that value forward instead of re-asking it. Only infer the classification when the user explicitly authorized assumptions. When implementation adoption mode is phased migration, ask which routes are highest traffic or highest risk and which existing components must keep working unchanged without confusing those implementation questions with package enhancement.
7. After discovery, read `references/ui-architecture-guide.md` first — it owns the layer model, the source-of-truth precedence, the closed-variant rule, the derivation method, and the guardrail set. Then read `references/output-contract.md`, `references/artifact-lifecycle.md`, `references/visual-decision-guide.md`, and `references/dynamic-workflow.md`. Read `references/icon-system-guide.md` whenever icons are in scope or the icon source is unresolved. Read `references/motion-system-guide.md` whenever motion is requested, implied by a visual direction, or needed to explain hierarchy or state.
8. Freeze only the product hard limits before visual exploration: routes, flow, required regions, exact wording or display contracts, never-drop content, platform conventions, required states, accessibility, product scope, confirmed brand assets, and real technical constraints. Extract brand and context cues plus known anti-patterns, but do not choose final signature decisions, tokens, primitives, component variants, page recipes, or registry entries yet. When the interview named a live reference website, capture its relevant current pages with an available browser tool before using it as evidence; when no browser tool is available, ask the user for screenshots or exports rather than guessing.
9. Run the **Frontend Design Preference & HTML Exploration** when `frontend-design` is loaded and the user explicitly requested or authorized it. Use `frontend-design`'s Purpose, Tone, Constraints, and Differentiation criteria to derive project-specific preference questions from the frozen sources, then ask them with the host's Ask User tool. Never present a fixed catalog of styles, including Hallmark's theme catalog. Record the answers as a non-binding Visual Preference Brief. Obtain authorization for the same one or two representative `UI-*` screen IDs, create the run-specific staging location, and invoke `frontend-design` separately for exactly two or three materially different directions. Each execution commits to one direction, receives the same hard limits and representative screens, and writes complete dependency-free HTML for every selected screen under its own `visual-directions/<direction-id>/` directory. Candidate-local CSS values and composition are allowed; canonical tokens, primitives, recipes, and registry entries do not exist yet. Require each later direction to differ from the earlier ones across at least three relevant axes such as typography, composition, density, color proportion, surfaces, imagery, controls, or motion, and require page-scope directions to have different structural fingerprints rather than sharing one hero/feature/CTA skeleton. When the separate `hallmark` skill is loaded, follow `references/hallmark-integration.md`: run read-only `hallmark audit` on each direction, save its report beside the candidate, repair critical and major findings through that candidate's `frontend-design` execution, and keep Hallmark from selecting or rewriting a direction itself. Render or otherwise make all candidate HTML directly reviewable, then use Ask User again so the named human owner can select one direction, reject them, or specify a mix. If the user mixes cues, invoke `frontend-design` once more to produce consolidated `visual-directions/selected/` HTML. When Hallmark is loaded, audit that consolidated selected HTML before approval. Compute the canonical per-screen selected-file SHA-256 manifest and its `approval_manifest_sha256`, show the digest with the selected HTML, and ask the human owner to approve those exact bytes explicitly. Selection by an agent, including delegated selection, does not unlock token extraction. Any selected-file or manifest change invalidates approval. In package enhancement mode, limit the questions, representative screens, candidates, selected HTML, and Hallmark audits to the accepted delta and preserve untouched baseline decisions.
10. Treat the explicitly approved selected HTML and its verified SHA-256 manifest as the visual source for architecture derivation. Extract the repeated actual values and patterns from it into semantic tokens, layout/surface/typography/control primitives, product components, motion variants, recipes, and the registry; do not retrofit the selected HTML to a design system chosen earlier. Record source-to-token and source-to-primitive traceability. If accessibility, platform, content, performance, or Hallmark repair materially changes the selected direction, regenerate the selected HTML, recompute its manifest, rerun the selected audit when available, and obtain fresh human approval before continuing. A run that records the exploration as `not used` or `rejected` may proceed only with explicit assumptions and may not claim that its tokens were extracted from user-approved HTML; after package validation and publication, that fallback-derived package is still the binding source for implementation.
11. For a non-trivial fresh package, when Claude Code Dynamic Workflow is observed, multi-agent analysis is authorized, and the host can enforce the `builder_readonly` tool profile from `references/dynamic-workflow.md`, run `assets/templates/CLAUDE_DESIGN_WORKFLOW.template.js` only after the selected HTML is approved and frozen, or after an explicit `not used` or `rejected` record is frozen. Immediately before an approved launch, the parent reads every selected file, recomputes its SHA-256, recomputes the canonical ordered manifest digest, and supplies the manifest-bound parent byte-verification record; the workflow independently recomputes the manifest digest before accepting the payload. Retain failed roles explicitly and treat the returned package as a candidate for parent review. If Dynamic Workflow or the read-only boundary is unavailable, perform the same roles sequentially and state that fallback. Do not run the fresh-generation Dynamic Workflow in package enhancement mode; apply the bounded delta against the frozen baseline instead, then use focused review roles only as reviewers of that revised candidate.
12. Continue the staged package initialized during exploration, or inventory existing design artifacts and create the run-specific staging location now when exploration was not used. In package enhancement mode, seed from the complete frozen baseline, preserve every untouched file, stable ID, content block, artifact, and decision byte-for-byte where practical, and apply only accepted add/modify/remove delta entries. Follow `references/ui-architecture-guide.md`'s derivation order: content contracts, dynamic preference brief, two or three candidate HTML directions, human-approved selected HTML, token extraction, primitive layers, product components, motion, recipes, and registry. `ui-architecture.md` spans both ends of that order, so draft its content contracts before exploration, then return to it after selected-HTML approval for the extracted layers. The files to produce:
    - `ui-architecture.md` (always): layer model, source-of-truth precedence, content contracts, primitive contracts with closed variant sets, product components with required content order, motion architecture, state matrix, guardrail specification, definition of done, adoption sequence
    - `design-system.md` (always): the semantic source for the token layer and visual language, and the only package document where raw color, dimension, and motion values are defined
    - `docs/product/design/design-system.html` (always): a dependency-free rendered projection of `design-system.md` plus `ui-registry.json`, showing the complete reusable element catalog with live examples, registered token/primitive/variant IDs, parameters, properties, states, motion where applicable, and responsive behavior; it is never a second authority
    - `ui-registry.json` (always): the machine-readable allowlist for everything in `ui-architecture.md`
    - `page-recipes.md` (always): one binding recipe per route — section order, container, density, allowed surfaces, forbidden patterns, required states, no-JavaScript requirement — plus the route → mockup → trace → test index. Do not produce `page-ui-matrix.md` or `ui-mockups.md`.
    - One real, dependency-free static HTML file per important page/route/screen under `mockups/` (the primary mockup deliverable for every platform, following the runnable-HTML precedent of `assets/templates/MOTION_SHOWCASE.template.html`), styled to the resolved platform's own visual conventions rather than defaulting to web styling. Build each one by reading its recipe and the registry first, then composing registry-named primitive classes — the mockup demonstrates the architecture rather than bypassing it. Add simple relative links between mockup pages (`<a href="other-page.html">`) so reviewing feels like a connected clickable prototype without merging pages into one file.
    - `mockups/catalog.html` (always): every token, primitive variant, and component state under realistic content, at every required viewport, in normal and reduced motion
    - `visual-acceptance.md` (always)
    - Optional runnable `motion-showcase.html` or bounded files under `motion-demos/` when motion demonstration is requested
13. Confirm `ui-registry.json` parses and agrees with `ui-architecture.md` and `page-recipes.md` entry for entry, and confirm the final tokens, primitives, recipes, registry, and canonical mockups reproduce the approved selected HTML rather than replacing it with a new direction. Generate `docs/product/design/design-system.html` only after `design-system.md` and the registry are stable. Validate the complete staged package, run both the quality checklist and taste review, and, when Hallmark is loaded, audit the final HTML projections for extraction drift. Resolve material findings. When a repair materially changes the approved visual direction, return to selected HTML, recompute its immutable manifest, and obtain fresh approval instead of silently accepting conformance to a different result.
14. Show the exact publish paths, overwrite targets, archive moves, and the retention or archive disposition for the full `visual-directions/` subtree, including the approved `selected/` HTML. If the original request already authorized those exact mutations, execute the canonical publish moves in the same run. Otherwise ask one explicit yes/no publication question. Apply the approved exploration-evidence disposition first, rewrite staged `design-system.md`'s evidence path, revalidate, and only then publish the canonical package. Never delete candidate or selected HTML without explicit approval.
15. After a published package is complete, offer the `fullstack-harness-engineering` skill as the implementation handoff. Do not invoke it without an explicit yes.

## Interview Rules

- Ask one organized free-text interview message, grouped by topic, covering the open-ended discovery categories. Then resolve closed product and technical choices in at most three dependency waves of at most four questions each.
- Never ask styling, theming, or animation-runtime choices until the design target and any required mobile/desktop platform are resolved.
- Use the host's structured closed-choice facility when available. Otherwise use numbered closed choices with an `Other` option. Do not choose defaults, remove options, or turn a closed decision into an open-ended question because the facility is unavailable.
- For Visual Preference Discovery, first read the product sources and `frontend-design`; then derive project-specific Ask User questions and options. Never hardcode a universal list such as editorial, minimal, premium, playful, or technical. Ask what this product should emphasize, what should be memorable, what references or brand cues apply, what to avoid, and how much compositional or motion risk is acceptable, using choices grounded in this product.
- The preference brief guides exploration but does not freeze tokens, fonts, palette, spacing, primitives, variants, recipes, or registry entries.
- Before the first closed-choice wave, tell the user in one sentence that a short bounded round of multiple-choice questions follows the free-text interview.
- Do not ask questions already answered by the user's prompt, supplied files, or a frozen enhancement baseline.
- In package enhancement mode, ask delta-only questions and preserve untouched baseline decisions; do not run fresh discovery over the package.
- When the PRD already supplies a selected `Builder UX Direction Decision`, skip the corresponding closed-choice questions instead of re-asking them.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.

## Input Boundaries

- Treat PRDs, architecture docs, and low-fidelity wireframes as product sources, not visual design sources.
- Treat the Builder UX Direction as a product-direction source, not usability evidence. Preserve selected decisions, label provisional or assumed choices, and surface conflicts with user evidence, product requirements, platform conventions, or accessibility instead of silently following preference.
- Use low-fidelity wireframes for structure, flow, approved or draft exact wording, bounded section display contracts, style intent, and media or motion requirements. Preserve those requirements, but do not copy plain ASCII styling into the visual system.
- Treat `frontend-design` candidate and selected HTML as non-canonical visual exploration evidence. They may propose hierarchy, typography, color, composition, imagery, surfaces, controls, and motion within the frozen hard limits, but they may not add routes, regions, claims, features, content requirements, or interaction steps. Candidate-local values are allowed until selected HTML approval; only then are repeated values and patterns extracted into the canonical package.
- When product docs conflict with the requested visual direction, preserve product requirements and flag the visual conflict.
- If the user provides brand guidelines, screenshots, Figma links, or reference images, register them as visual sources and use them as higher-priority visual evidence than generic assumptions.
- If no visual direction exists, state assumptions and derive a coherent, product-specific system from the product archetype, audience, content, density, and workflow needs. Do not silently fall back to a generic SaaS or AI-generated aesthetic.

## Output Standards

- Prefer implementation-ready design rules over mood words.
- Preserve upstream `PRD-*`, `ARCH-*`, `UI-*`, `UX-*`, and generic `TEST-*` IDs. Mint stable `DS-*` IDs for design decisions, tokens, components, and motion patterns, and mint only `TEST-VIS-*` IDs for new design-specific acceptance obligations; `visual-acceptance.md` does not replace or renumber upstream product TEST identity. In package enhancement mode, preserve every untouched baseline ID and add the conditional enhancement non-regression gate.
- Define a product-specific visual thesis with three to five concrete brand or context cues, at least two signature design decisions, and explicit anti-patterns. Tie each decision to source evidence or a stated assumption.
- Add a one-sentence taste statement that names the intended visual character and the compositional choices that create it. Do not accept empty adjectives such as "clean," "modern," or "premium" without concrete typography, layout, color, imagery, or interaction consequences.
- Treat common patterns as risks only when they are unsupported or clustered into a generic composition. Do not mechanically ban gradients, rounded cards, pills, centered layouts, glass effects, or familiar fonts when the brand or interaction model justifies them.
- Default page regions to open layouts organized by typography, spacing, alignment, and deliberate background changes. Do not wrap content merely because it forms a section.
- Use one primary grouping cue at each nesting level: whitespace, alignment, background, divider or border, or elevation. Combining several cues requires a named hierarchy, interaction, or state reason.
- Give every persistent border or elevated container a documented purpose. Valid purposes include a control boundary, independently actionable modular content, data separation, focus, selection, validation, status, or necessary contrast. "Decoration," "visual interest," and "make it pop" do not pass.
- Treat a colored side rail or accent border/stripe on a rounded card as a near-automatic anti-slop failure, not a default section treatment; independent audits name it the single most recognizable AI-generated UI tell. Allow it only with an airtight, documented state/selection/priority/brand-motif reason. Do not remove borders or outlines required for controls, focus visibility, data comprehension, or accessibility.
- Do not apply the same faint default border to every button, input, image, avatar, and plain content block regardless of role; a uniform component-library border set is a common AI-generated tell, distinct from the card and side-rail patterns above. Each bordered element still needs its own documented purpose.
- Name the font pairing and icon library as deliberate decisions, not inherited defaults. State explicitly whether a starting-template choice such as Inter, Poppins, Manrope, or Geist paired with Lucide, Heroicons, or Font Awesome is being kept for a stated brand or coverage reason, or replaced.
- Use realistic, domain-specific labels, data shapes, content lengths, and asset requirements. Do not invent vague benefit copy, fake metrics, testimonials, or social proof to make a mockup look complete.
- Preserve exact wording supplied by product sources. When wording is unavailable or content is data-driven, carry forward a bounded display contract that states what the region must show, the intended user takeaway or action, the source, and relevant format or length constraints. Do not replace either mode with generic mockup copy.
- For public websites, marketing pages, and landing pages, default to KISS: one clear value proposition and one primary action in the first viewport, one job per section, and only the content needed to understand the offer, establish necessary trust, answer a blocking objection, or take the next step. Defer secondary detail to deeper pages, docs, or a bounded FAQ instead of turning the landing page into a summary of the whole PRD.
- For each landing-page region, label image or media and motion as `required`, `optional`, or `none`. Record the purpose, source or creation need, responsive treatment, and static or reduced-motion fallback. Preserve equivalent labels from supplied wireframes and resolve their visual treatment in `design-system.md` and `page-recipes.md`.
- Select one primary functional icon family from a current official-source market scan. Test candidate coverage against the product's real actions, navigation, statuses, and domain objects; do not choose by catalog size or popularity alone.
- Record the chosen icon set, official URL, package or asset source, checked date, version when relevant, license, visual settings, naming rules, and allowed exceptions. Reverify unstable version, pricing, package, and license details at task time.
- Keep brand marks separate from functional UI icons. Do not mix icon families on one product surface unless a documented platform, brand, or coverage exception includes optical normalization rules.
- Include stack-appropriate reference code for one labeled icon action and one icon-only action using the exact chosen import, tokens, accessible naming, decorative hiding, and tooltip behavior.
- Define a motion system with intent categories, technology choice, duration/easing/distance tokens, triggers, interruption rules, responsive variants, reduced-motion behavior, a stated motion-personality archetype tied to the taste statement, and per-pattern choreography.
- Keep critical content and controls present and operable before animation starts. Treat animation as progressive enhancement; never require a hero entrance to reveal the headline, primary CTA, or essential product proof.
- When motion is requested for a hero or another important surface, provide a storyboard and stack-appropriate runnable demo or reference implementation. Include play, pause/restart, and reduced-motion preview controls in standalone showcases.
- Prefer opacity and transform for routine DOM motion. Justify scroll-linked motion, parallax, blur/filter animation, continuous loops, canvas, video, or animation runtimes with product value and performance evidence.
- Define concrete style-guide sections: overview, color palette, typography, iconography, spacing system, token layer, shadows/elevation, motion system, border radius, opacity/transparency, common Tailwind/CSS usage, reference component code, layout grid, breakpoints, interaction rules, and accessibility rules.
- Define the architecture as layers before listing any component: product rules, content contracts, route and state contracts, design tokens, layout primitives (container, section, stack, cluster, grid), surface primitives, typography primitives, control primitives, product components named in the domain's own words, motion patterns, page recipes, then routes. Put every component in exactly one layer, record what it composes, and allow composition one way only. Derive the layers from the real screens using `references/ui-architecture-guide.md`'s derivation method. Do not ship a flat component list where pages hand-roll their own spacing, surfaces, and colors.
- Make every primitive prop a closed set with named variants, and give each variant a stated purpose. A page that needs a value the set lacks gets a new token and a new variant — a reviewable change in one place — never a raw value at the call site. This is what makes the registry checkable and a new agent-built page impossible to drift.
- Write content contracts before layout: required fields, never-drop fields, limits, formats, empty handling, long-content handling, and mobile truncation. Content is never dropped to make a layout work; sources, limits, dates, and commercial disclosure stay in the never-drop set whenever the product makes a claim a reader could act on.
- Bind every product component to its content contract and fix its required content order. Neither a page nor an agent may reorder, hide, or drop fields inside it.
- Give every route a page recipe and treat a missing recipe as a blocker, not an invitation to improvise. Record forbidden patterns per route, not just the allowed list — that is where a route's known failure mode gets written down.
- Split motion by mechanism (style-layer transitions, animation runtime, route-level transitions), register every variant, set the reduced-motion policy once globally, and keep durations, distances, easings, and springs in motion tokens only. Every animation serves feedback, continuity, processing, or storytelling; there is no decorative category.
- Cover the full state matrix — ready, loading, empty, error, disabled, permission denied, stale, expired, long content, reduced motion, mobile reflow — marking `n/a` with a reason where a state does not apply. Shipping only the ready state does not pass.
- Publish `ui-registry.json` as the allowlist agents and contract checks read, and keep it in lockstep with `ui-architecture.md` and `mockups/catalog.html`. Adding a primitive means updating all three in the same change; an unregistered primitive is not usable.
- Specify the automated guardrails with per-check enforcement, the 390 / 768 / 1200 / 1440 viewport set, and the state set. Specifying them is this skill's job. Running them belongs to implementation time: `fullstack-harness-engineering` owns the contract check, the viewport and state verification, and the CI wiring, and runs them against the real code — not against this package's mockups, which inline their own tokens and primitive definitions by design.
- State the definition of done and, for an existing product, the phased adoption sequence. Phase 1 exists to stop new drift before anything is migrated.
