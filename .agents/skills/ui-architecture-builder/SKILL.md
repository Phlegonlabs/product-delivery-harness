# UI Architecture Builder

## Overview

Use this skill to turn product and wireframe inputs into a UI architecture package that both humans and agents must build through. Default all generated artifacts to English unless the user explicitly requests another language.

The binding rule the package exists to enforce:

> A page cannot be freely designed. A page may only use approved content contracts, page recipes, product components, and primitives.

That rule is what keeps an agent's new page consistent with the existing design, keeps spacing, surfaces, controls, and motion identical across routes, keeps the specification, the code, and the mockups from drifting apart, and lets the styling engine change without rewriting the components above it.

This skill owns the UI architecture and visual layer. It does not create PRDs, backend architecture, implementation plans, harness plans, mission maps, or E2E evidence registers, and it does not write the product's real component code — `fullstack-harness-engineering` implements the architecture this package specifies.

## Workflow

1. Inspect the document folder first — the one the user names, the one the upstream handoff named, or `docs/product/` when a package is already published there — and identify product inputs such as `PRD.md`, `architecture.md`, `stack-decisions.md`, `wireframes.md`, and `implementation-plan.md`. Read `architecture.md`'s `Product Archetype` section, plus `stack-decisions.md`'s Frontend and Backend Technology Decision and — for a native mobile or desktop target — its Mobile/Desktop Technology Decision, to extract the resolved platform (web, native iOS, native Android, Flutter, React Native, macOS, Windows, cross-platform desktop, or a hybrid) before the design interview. Carry that resolved platform forward and do not re-ask it in step 5–6, matching this skill's "do not ask questions already answered" convention. The platform decides the visual vocabulary (`references/visual-decision-guide.md`): every platform's page mockup is a real, viewable HTML file (HTML is a visual demonstration medium here, not the target's production technology), styled to the resolved platform's own conventions — iOS/macOS HIG cues, Android/Material cues, or desktop window chrome — rather than defaulting to web styling for a native or desktop target.
2. Locate the PRD's `Builder UX Direction Decision` when a UI-bearing product is in scope. Preserve its human decision owner and `selected`, `provisional`, or `assumed` status; if it is missing, use the design interview to ask for it before choosing the visual system.
3. Read `references/design-interview-guide.md` before asking design discovery questions.
4. Conduct a concise design interview unless the user explicitly says to skip questions, make assumptions, or draft a first pass immediately. Scope this free-text message to the open-ended discovery categories in `references/design-interview-guide.md` (product/audience narrative, brand cues and recognizability, per-page/region scope and content, and confirmation/recovery behavior).
5. Immediately after the free-text interview message — not interleaved with it as separate turns — issue one or two `AskUserQuestion` calls (max 4 questions per call) resolving the closed-set decisions marked `(AskUserQuestion)` in `references/design-interview-guide.md`. The first call takes the architecture-defining decisions, because every later artifact is derived from them: design-target classification, styling and theming mechanism, registry enforcement (blocking or advisory), and greenfield versus phased migration. The second call takes the visual and behavioral decisions in scope: visual/style direction, experience priority, validation depth, and — when motion or icons are in scope — animation runtime, motion trigger timing, motion delivery format, and icon style. That is more candidates than eight slots hold, so skip every question the PRD, `architecture.md`, `stack-decisions.md`, `wireframes.md`, or the user's prompt already answers, let each skip promote the next question in line, and drop the rest in the order `references/design-interview-guide.md` marks. When the design-target answer is a mobile or desktop app and no upstream document resolved the platform, that platform follow-up takes a slot in the second call by dropping the next question in that order — the platform decides the entire visual vocabulary and cannot be assumed. Do not silently pick an option on the user's behalf, and do not open a third call. When the adoption-mode answer comes back as a phased migration, ask its two free-text follow-ups — which routes are highest traffic or highest risk, and which existing components must keep working unchanged — in the message that reports the interview results back, not as a new interview round.
6. Confirm the design-target classification from step 5's `AskUserQuestion` answer: SaaS app, dashboard, internal tool, public website, marketing page, docs/content site, ecommerce/catalog, mobile app (native iOS, native Android, Flutter, or React Native), desktop app (macOS, Windows, or cross-platform), or hybrid. When step 1 already resolved the platform from the upstream product package, carry that value forward instead of re-asking it. Only infer the classification when the user explicitly authorized assumptions.
7. After discovery, read `references/ui-architecture-guide.md` first — it owns the layer model, the source-of-truth precedence, the closed-variant rule, the derivation method, and the guardrail set. Then read `references/output-contract.md`, `references/artifact-lifecycle.md`, `references/visual-decision-guide.md`, and `references/dynamic-workflow.md`. Read `references/icon-system-guide.md` whenever icons are in scope or the icon source is unresolved. Read `references/motion-system-guide.md` whenever motion is requested, implied by a visual direction, or needed to explain hierarchy or state.
8. Establish the product-specific visual thesis before selecting tokens or components: extract brand cues, carry forward the Builder UX Direction, write a one-sentence taste statement, choose signature design decisions, identify generic defaults to avoid, define the container and border logic, define realistic content constraints and landing-page content budgets, select an icon direction from the actual semantic inventory, and give every image, media asset, and motion pattern a stated purpose. When the interview named an existing reference website to model the style after (not a file the user already supplied), check whether a browser automation tool is available in the current session — Chrome via the `claude-in-chrome` MCP tools on a Claude Code host, an equivalent browser-driving MCP tool on a Codex host, or Playwright on either host — before extracting brand cues from it. When one is available, navigate to and screenshot the referenced site's relevant pages/sections first, then extract cues from the captured evidence — real current colors, layout, and typography — instead of from memory of what that site looks like. Register each capture as a visual source the same way a user-supplied screenshot is registered. When no browser tool is available, ask the user to supply screenshots or exports of the reference site directly rather than guessing its current appearance.
9. For a non-trivial package, when Claude Code Dynamic Workflow is observed, multi-agent analysis is authorized, and the host can enforce the `builder_readonly` tool profile from `references/dynamic-workflow.md`, run `assets/templates/CLAUDE_DESIGN_WORKFLOW.template.js` after discovery and source inputs are frozen. Retain failed roles explicitly and treat the returned package as a candidate for parent review. If Dynamic Workflow or the read-only boundary is unavailable, perform the same roles sequentially and state that fallback.
10. Inventory existing design artifacts, then produce or repair the package in the run-specific staging location from `references/artifact-lifecycle.md`. Follow the derivation order in `references/ui-architecture-guide.md`, not the file list below: content contracts first, then tokens, then the primitive layers, then product components, motion, recipes, and the registry. `ui-architecture.md` spans both ends of that order, so draft its content contracts before `design-system.md`'s tokens, then come back to it for the primitive and component layers once the tokens they reference exist. Writing a closed variant set that names a token nobody has defined yet is how drift gets in. The files to produce:
    - `ui-architecture.md` (always): layer model, source-of-truth precedence, content contracts, primitive contracts with closed variant sets, product components with required content order, motion architecture, state matrix, guardrail specification, definition of done, adoption sequence
    - `design-system.md` (always): the token layer and visual language, and the only place raw color, dimension, and motion values appear
    - `ui-registry.json` (always): the machine-readable allowlist for everything in `ui-architecture.md`
    - `page-recipes.md` (always): one binding recipe per route — section order, container, density, allowed surfaces, forbidden patterns, required states, no-JavaScript requirement — plus the route → mockup → trace → test index. Do not produce `page-ui-matrix.md` or `ui-mockups.md`.
    - One real, dependency-free static HTML file per important page/route/screen under `mockups/` (the primary mockup deliverable for every platform, following the runnable-HTML precedent of `assets/templates/MOTION_SHOWCASE.template.html`), styled to the resolved platform's own visual conventions rather than defaulting to web styling. Build each one by reading its recipe and the registry first, then composing registry-named primitive classes — the mockup demonstrates the architecture rather than bypassing it. Add simple relative links between mockup pages (`<a href="other-page.html">`) so reviewing feels like a connected clickable prototype without merging pages into one file.
    - `mockups/catalog.html` (always): every token, primitive variant, and component state under realistic content, at every required viewport, in normal and reduced motion
    - `visual-acceptance.md` (always)
    - Optional runnable `motion-showcase.html` or bounded files under `motion-demos/` when motion demonstration is requested
11. Confirm `ui-registry.json` parses and agrees with `ui-architecture.md` and `page-recipes.md` entry for entry — a registry that disagrees with the documents is not a contract. Then run both the quality checklist and the taste and anti-slop review in `references/output-contract.md` before finalizing. Resolve every required workflow role and material verifier finding. Critique, repair the highest-impact failure, and recheck until the package passes or an unresolved constraint is recorded. Use rendered breakpoint evidence when visual artifacts or an implementation exist AND a browser automation tool is available in this session — Chrome via the `claude-in-chrome` MCP tools, an equivalent browser-driving MCP tool on a Codex host, or Playwright, the same availability check step 8 makes for reference-site capture. Step 10 always produces real `mockups/*.html`, so artifacts existing is not by itself proof that anything was rendered. With no browser tool, use the contract's text-only conformance path, record render evidence as unavailable, and do not claim visual verification.
12. Show the exact publish paths, overwrite targets, and archive moves. If the original request already authorized those exact mutations, perform them immediately. Otherwise, immediately after listing them, ask one explicit yes/no publication question. If the user approves, execute the approved publish and archive moves in the same run using `references/artifact-lifecycle.md`, and remove the now-empty run-specific staging directory as the final step of that same run — publication is not complete while a redundant staged copy still sits in `docs/product/.design-staging/`; if the user declines or does not answer, leave the validated staging package intact and report it as ready to publish.
13. After a published package is complete, offer the `fullstack-harness-engineering` skill as the implementation handoff. Do not invoke it without an explicit yes.

## Interview Rules

- Ask one organized free-text interview message, grouped by topic, covering the open-ended discovery categories. Immediately follow it with the `AskUserQuestion` batch(es) for the closed-set decisions — do not spread these across additional free-text turns, and use the tool's built-in Other option instead of inventing a separate free-text fallback.
- Before the first `AskUserQuestion` call, tell the user in one sentence that a short round of multiple-choice questions follows the free-text interview, so the sequence reads as one bounded step rather than an open-ended series of forms.
- Do not ask questions already answered by the user's prompt or supplied files.
- When the PRD already supplies a selected `Builder UX Direction Decision`, skip the corresponding `AskUserQuestion` questions instead of re-asking them.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.

## Input Boundaries

- Treat PRDs, architecture docs, and low-fidelity wireframes as product sources, not visual design sources.
- Treat the Builder UX Direction as a product-direction source, not usability evidence. Preserve selected decisions, label provisional or assumed choices, and surface conflicts with user evidence, product requirements, platform conventions, or accessibility instead of silently following preference.
- Use low-fidelity wireframes for structure, flow, approved or draft exact wording, bounded section display contracts, style intent, and media or motion requirements. Preserve those requirements, but do not copy plain ASCII styling into the visual system.
- When product docs conflict with the requested visual direction, preserve product requirements and flag the visual conflict.
- If the user provides brand guidelines, screenshots, Figma links, or reference images, register them as visual sources and use them as higher-priority visual evidence than generic assumptions.
- If no visual direction exists, state assumptions and derive a coherent, product-specific system from the product archetype, audience, content, density, and workflow needs. Do not silently fall back to a generic SaaS or AI-generated aesthetic.

## Optional External Skill Assist

This skill does not bundle `frontend-design`. It is a separate Apache-2.0 plugin from the `claude-plugins-official` marketplace and requires its own install (`claude plugin install frontend-design@claude-plugins-official`). Before offering it, confirm it is actually loaded in the current session; if it is not installed, say so and continue on this skill's own path instead of fabricating its presence.

- This skill's own artifacts stay design specifications, not production app code. `ui-architecture.md`, `design-system.md`, `page-recipes.md`, and `visual-acceptance.md` are always Markdown, `ui-registry.json` is machine-readable JSON; the page-level `mockups/*.html` files are viewable reference/prototype artifacts for every platform (including native iOS/Android/Flutter and desktop) — the same class of visual source as a Figma export or a wireframe, never the target's real implementation technology. Implementation missions in `fullstack-harness-engineering` still reimplement each screen in the project's actual framework (SwiftUI, Jetpack Compose, Flutter widgets, WinUI, or a web stack) using the HTML mockup as the visual/structural source of truth, not as source to port directly. `frontend-design` does not replace these artifacts, their trace IDs, or the taste-and-anti-slop review in `references/output-contract.md`.
- Offer `frontend-design` only for the small pieces of real code this skill already produces — the icon/component reference code snippets and the runnable `motion-showcase.html`/`motion-demos/` files — when the user wants unusually distinctive execution beyond what the design-system spec already states. Use it only after an explicit yes.
- Offer `frontend-design` for an expert color-pairing suggestion pass on the `design-system.md` Color Palette when the user wants a more distinctive combination than `visual-decision-guide.md`'s Color Palette Decision guidance alone would produce. Use it only after an explicit yes, and treat its suggestion as input to that decision — still record the harmony method and every text/UI pairing's actual WCAG contrast ratio yourself; `frontend-design` does not replace that record.
- Offer `frontend-design` for an expert font-pairing suggestion pass on the `design-system.md` Typography section when the user wants a more distinctive combination than `visual-decision-guide.md`'s Typography Decision guidance alone would produce. Use it only after an explicit yes, and treat its suggestion as input to that decision — still record the pairing rationale and every role's actual line-height ratio yourself; `frontend-design` does not replace that record.
- When the user's request goes beyond the architecture package into actually building or reshaping the product UI, that work belongs to `fullstack-harness-engineering`'s own implementation step, which already documents its own `frontend-design` offer. Do not expand this skill's own boundary to cover it.

## Output Standards

- Prefer implementation-ready design rules over mood words.
- Preserve upstream `PRD-*`, `ARCH-*`, `UI-*`, `UX-*`, and `TEST-*` IDs. Mint stable `DS-*` IDs for design decisions, tokens, components, and motion patterns, plus new `TEST-*` IDs only for design-specific acceptance obligations.
- Define a product-specific visual thesis with three to five concrete brand or context cues, at least two signature design decisions, and explicit anti-patterns. Tie each decision to source evidence or a stated assumption.
- Add a one-sentence taste statement that names the intended visual character and the compositional choices that create it. Do not accept empty adjectives such as "clean," "modern," or "premium" without concrete typography, layout, color, imagery, or interaction consequences.
- Treat common patterns as risks only when they are unsupported or clustered into a generic composition. Do not mechanically ban gradients, rounded cards, pills, centered layouts, glass effects, or familiar fonts when the brand or interaction model justifies them.
- Default page regions to open layouts organized by typography, spacing, alignment, and deliberate background changes. Do not wrap content merely because it forms a section.
- Use one primary grouping cue at each nesting level: whitespace, alignment, background, divider or border, or elevation. Combining several cues requires a named hierarchy, interaction, or state reason.
- Give every persistent border or elevated container a documented purpose. Valid purposes include a control boundary, independently actionable modular content, data separation, focus, selection, validation, status, or necessary contrast. "Decoration," "visual interest," and "make it pop" do not pass.
- Treat a colored side rail or accent border/stripe on a rounded card as a near-automatic anti-slop failure, not a default section treatment; independent audits name it the single most recognizable AI-generated UI tell. Allow it only with an airtight, documented state/selection/priority/brand-motif reason. Do not remove borders or outlines required for controls, focus visibility, data comprehension, or accessibility.
- Do not apply the same faint default border to every button, input, image, avatar, and plain content block regardless of role; a uniform component-library border set is a common AI-generated tell, distinct from the card and side-rail patterns above. Each bordered element still needs its own documented purpose.
- Name the font pairing and icon library as deliberate decisions, not inherited defaults. State explicitly whether a starting-template choice such as Inter, Poppins, Manrope, or Geist paired with Lucide, Heroicons, or Font Awesome is being kept for a stated brand or coverage reason, or replaced.
- Use realistic, domain-specific labels, data shapes, content lengths, and asset requirements. Do not invent vague benefit copy, fake metrics, testimonials, or social proof to make a mockup look complete.
- Preserve exact wording supplied by product sources. When wording is unavailable or content is data-driven, carry forward a bounded display contract that states what the region must show, the intended user takeaway or action, the source, and relevant format or length constraints. Do not replace either mode with generic mockup copy.
- For public websites, marketing pages, and landing pages, default to KISS: one clear value proposition and one primary action in the first viewport, one job per section, and only the content needed to understand the offer, establish necessary trust, answer a blocking objection, or take the next step. Defer secondary detail to deeper pages, docs, or a bounded FAQ instead of turning the landing page into a summary of the whole PRD.
- For each landing-page region, label image or media and motion as `required`, `optional`, or `none`. Record the purpose, source or creation need, responsive treatment, and static or reduced-motion fallback. Preserve equivalent labels from supplied wireframes and resolve their visual treatment in `design-system.md` and `page-recipes.md`.
- Select one primary functional icon family from a current official-source market scan. Test candidate coverage against the product's real actions, navigation, statuses, and domain objects; do not choose by catalog size or popularity alone.
- Record the chosen icon set, official URL, package or asset source, checked date, version when relevant, license, visual settings, naming rules, and allowed exceptions. Reverify unstable version, pricing, package, and license details at task time.
- Keep brand marks separate from functional UI icons. Do not mix icon families on one product surface unless a documented platform, brand, or coverage exception includes optical normalization rules.
- Include stack-appropriate reference code for one labeled icon action and one icon-only action using the exact chosen import, tokens, accessible naming, decorative hiding, and tooltip behavior.
- Define a motion system with intent categories, technology choice, duration/easing/distance tokens, triggers, interruption rules, responsive variants, reduced-motion behavior, a stated motion-personality archetype tied to the taste statement, and per-pattern choreography.
- Keep critical content and controls present and operable before animation starts. Treat animation as progressive enhancement; never require a hero entrance to reveal the headline, primary CTA, or essential product proof.
- When motion is requested for a hero or another important surface, provide a storyboard and stack-appropriate runnable demo or reference implementation. Include play, pause/restart, and reduced-motion preview controls in standalone showcases.
- Prefer opacity and transform for routine DOM motion. Justify scroll-linked motion, parallax, blur/filter animation, continuous loops, canvas, video, or animation runtimes with product value and performance evidence.
- Define concrete style-guide sections: overview, color palette, typography, iconography, spacing system, token layer, shadows/elevation, motion system, border radius, opacity/transparency, common Tailwind/CSS usage, reference component code, layout grid, breakpoints, interaction rules, and accessibility rules.
- Define the architecture as layers before listing any component: product rules, content contracts, route and state contracts, design tokens, layout primitives (container, section, stack, cluster, grid), surface primitives, typography primitives, control primitives, product components named in the domain's own words, motion patterns, page recipes, then routes. Put every component in exactly one layer, record what it composes, and allow composition one way only. Derive the layers from the real screens using `references/ui-architecture-guide.md`'s derivation method. Do not ship a flat component list where pages hand-roll their own spacing, surfaces, and colors.
- Make every primitive prop a closed set with named variants, and give each variant a stated purpose. A page that needs a value the set lacks gets a new token and a new variant — a reviewable change in one place — never a raw value at the call site. This is what makes the registry checkable and a new agent-built page impossible to drift.
- Write content contracts before layout: required fields, never-drop fields, limits, formats, empty handling, long-content handling, and mobile truncation. Content is never dropped to make a layout work; sources, limits, dates, and commercial disclosure stay in the never-drop set whenever the product makes a claim a reader could act on.
- Bind every product component to its content contract and fix its required content order. Neither a page nor an agent may reorder, hide, or drop fields inside it.
- Give every route a page recipe and treat a missing recipe as a blocker, not an invitation to improvise. Record forbidden patterns per route, not just the allowed list — that is where a route's known failure mode gets written down.
- Split motion by mechanism (style-layer transitions, animation runtime, route-level transitions), register every variant, set the reduced-motion policy once globally, and keep durations, distances, easings, and springs in motion tokens only. Every animation serves feedback, continuity, processing, or storytelling; there is no decorative category.
- Cover the full state matrix — ready, loading, empty, error, disabled, permission denied, stale, expired, long content, reduced motion, mobile reflow — marking `n/a` with a reason where a state does not apply. Shipping only the ready state does not pass.
- Publish `ui-registry.json` as the allowlist agents and contract checks read, and keep it in lockstep with `ui-architecture.md` and `mockups/catalog.html`. Adding a primitive means updating all three in the same change; an unregistered primitive is not usable.
- Specify the automated guardrails with per-check enforcement, the 390 / 768 / 1200 / 1440 viewport set, and the state set. Specifying them is this skill's job. Running them belongs to implementation time: `fullstack-harness-engineering` owns the contract check, the viewport and state verification, and the CI wiring, and runs them against the real code — not against this package's mockups, which inline their own tokens and primitive definitions by design.
- State the definition of done and, for an existing product, the phased adoption sequence. Phase 1 exists to stop new drift before anything is migrated.
- Define component variants and states: loading, empty, error, disabled, hover, focus, active, selected, expanded, long content, permission denied, and responsive overflow where applicable.
- Map every important page or route to UI source, breakpoints, states, components, data source, and acceptance evidence.
- Require each important page mockup to show how the shared signature decisions appear without weakening task hierarchy, accessibility, or platform conventions.
- Require each important page mockup to identify its default container treatment and justify any visible border, accent rail, nested frame, or elevation. If removing a treatment causes no loss of hierarchy, interaction, state, or comprehension, remove it.
- Produce each important page mockup as a real, dependency-free static HTML file under `mockups/` that renders the page's actual content, states, and responsive/size-class behavior, styled to the resolved platform's own visual conventions (web, iOS/macOS HIG, Android Material, or desktop window chrome). Treat it as a viewable reference/prototype, not production code — implementation still happens in the project's real framework. Do not claim pixel fidelity unless an actual visual reference or rendered mockup exists.
- Keep visual assumptions explicit and avoid hiding missing brand or asset decisions in confident prose.
- Record how the package implements each controlling Builder UX Direction choice. A builder-approved design may pass direction conformance, but it is not user-validated until separate usability evidence exists.
- Treat the stable design roles as an org graph and each bounded workflow run as a temporary work graph. Dynamic Workflow coordinates read-only design analysis; the parent still owns source freeze, staged artifact writes, rendered evidence, conflict resolution, approval, publication, and cross-session recovery.
- The workflow may return candidate motion-demo source, but it does not create production image assets or prove rendered visual conformance. Keep those claims tied to real artifacts and evidence.
