# PRD Builder

## Overview

Use this skill to turn a user's product idea or requirement into a buildable Markdown product definition. For a UI-bearing complete package, hand the frozen product inputs to `product-design-builder`; do not author its wireframes or design system here. Default all generated artifacts to English unless the user explicitly requests another language.

## Workflow

1. Read `references/interview-guide.md` before asking discovery questions.
2. Read `references/artifact-lifecycle.md`'s Detect Enhancement Mode section, then check whether `docs/product/PRD.md`, or another Markdown document whose title or content clearly describes the same product, already exists in the repository. Check `docs/product/.prd-staging/` in the same step: a validated but unpublished package left by an earlier run is the newer baseline, and resuming, publishing, or discarding it is the user's call before this run drafts anything. If one does, treat this run as an **enhancement** of that package, not a new one: read the existing `PRD.md`, `architecture.md`, `stack-decisions.md`, and — when present — `wireframes.md`, `design-system.md`, `design-system.json`, and `market-research.md` in full before asking anything else. Carry forward their content, decisions, and trace IDs unchanged, and scope every remaining step — interview, `AskUserQuestion` calls, drafting — to only what the new request adds, changes, or removes. Never restart discovery from a blank slate or regenerate the whole package from scratch when an existing package for the same product is found.
3. Conduct a complete but concise product interview before drafting, unless the user explicitly says to skip questions, make assumptions, or produce a first draft immediately. In enhancement mode (step 2), skip this in favor of a short delta interview covering only what the new idea touches — do not re-ask what the existing package already answers. Scope this free-text message to the open-ended discovery categories in `references/interview-guide.md` (goal, users/roles, workflows, data/integrations, business rules, delivery and release targets, success metrics, and confirmation/recovery expectations). Tell the user that the applicable multiple-choice decisions will follow after their reply. The free-text interview must be the only discovery interaction in this turn: end the turn and wait for the user's reply before any `AskUserQuestion` call.
4. After the user replies to the free-text interview, use their answers to skip resolved or inapplicable decisions, then issue the first `AskUserQuestion` call (max 4 questions per call) resolving the remaining closed-set decisions marked `(AskUserQuestion)` in `references/interview-guide.md` that depend on no other answer: product archetype and validation depth. Do not issue this call in the same turn as the free-text interview message. Keep the deployment platform out of this call. It only means something once the archetype is known, so step 6 carries it. Do not ask the user to choose from a fixed high-fidelity style catalog during discovery; `product-design-builder` owns the later product-specific visual-direction work. In enhancement mode, only re-ask a closed-set decision the new idea actually reopens; otherwise keep the existing package's answer.
5. For a UI-bearing product, capture a `Builder UX Direction Decision` before the design handoff. Resolve the builder to the human product/design decision owner or commissioning team. Use a second `AskUserQuestion` call (4 questions, at cap) for the closed dimensions — experience priority, guidance versus expert control, information density, and preferred layout/interaction pattern — and capture confirmation/recovery behavior as free text, since it varies too much by action to enumerate further. Validation depth is already answered by step 4's call; carry that answer forward instead of re-asking it. Mark every decision `selected`, `provisional`, or `assumed`. In enhancement mode, only revisit a dimension the new idea actually affects. `product-design-builder` consumes this decision and does not replace it with agent taste.
6. Issue a third `AskUserQuestion` call (at most 4 questions) for the closed-set decisions that depend on step 4's archetype answer, marked `(AskUserQuestion)` in `references/interview-guide.md`:
    - the deployment platform (Cloudflare / Vercel / AWS / Self-hosted, plus the tool's built-in Other for anything else, including an explicit stage-to-provider mapping) when the resolved surface includes a deployable web, API, or hosted backend target;
    - the mobile platform follow-up when an archetype is a mobile app, and the desktop platform follow-up when one is a desktop app;
    - the database category and auth strategy for a product with a backend, persistent data, or auth requirement — evident from the free-text interview's data/integrations and business-rules answers, or the archetype captured in step 4.

    Skip any question the archetype makes inapplicable, or that the user's prompt, the existing package, or the current repository already answers. Local persistence or local-only auth may require the backend/data decision pair and backend analysis without creating a hosted deployable surface; `has_backend` alone never triggers the deployment-platform question. Skip the database-category and auth-strategy pair only when the product provably has no backend, persistent data, or auth surface, such as a purely static content or marketing site with no forms, accounts, or dynamic data. Skip the whole call only when none of its questions apply. Do not silently pick a database category or auth strategy on the user's behalf. Only a hybrid spanning web, mobile, and desktop surfaces with a backend leaves five questions unresolved; five against a four-question cap drops exactly one, per the drop order in `references/interview-guide.md`, instead of opening a fourth call.
7. Classify the product as one or more archetypes: web app, mobile app, desktop app, internal tool, automation or agent workflow, API or backend service, or hybrid. For a mobile app, also record the resolved mobile platform (native iOS, native Android, Flutter, or React Native); for a desktop app, the resolved desktop platform (macOS, Windows, or cross-platform), since these select the matching pattern in `references/architecture-playbook.md`. Record whether it has any public-facing marketing, landing, or SEO-relevant page as distinct from purely internal or authenticated-only surfaces; this gates the SEO copy review below.
8. After discovery, read `references/output-contract.md`, `references/architecture-playbook.md`, `references/dynamic-workflow.md`, and `references/market-research-guide.md`, plus the rest of `references/artifact-lifecycle.md`. For a web app, internal tool, public website, or hybrid with a browser frontend, also read `references/frontend-stack-selection.md`. For any product with a backend, persistent data, or auth requirement — most products other than a purely static content site — also read `references/backend-stack-selection.md`. For a mobile-app or desktop-app surface, also read `references/mobile-stack-selection.md`; its desktop platform patterns live in `references/architecture-playbook.md`.
9. Before drafting, inventory earlier documents related to the same product as described in `references/artifact-lifecycle.md`. Do not move anything yet. In enhancement mode, this still includes the existing package identified in step 2 — it will be archived for history once the enhanced draft is published, even though its content already carried forward into that draft.
10. For a non-trivial package, when Claude Code Dynamic Workflow is observed, multi-agent analysis is authorized, and the host can enforce the `builder_readonly` tool profile from `references/dynamic-workflow.md`, run `assets/templates/CLAUDE_PRD_WORKFLOW.template.js` after the interview, the `AskUserQuestion` decisions, source inputs, explicit expected deployable-surface inventory, and provider-neutral release targets are frozen. Skip the workflow in enhancement mode: its lanes generate fresh content, which is exactly what step 2 forbids. Perform the roles sequentially against the existing package instead. Retain failed lanes explicitly and treat the returned package as a candidate for parent review. If Dynamic Workflow or the read-only boundary is unavailable, perform the same roles sequentially and state that fallback.
11. Draft or repair the core Markdown package in the staging location defined by `references/artifact-lifecycle.md`:
    - `PRD.md`
    - `architecture.md`
    - `stack-decisions.md`
    - For a UI-bearing product, do not invoke `product-design-builder` yet. Complete the market-research gap pass in step 13 first; step 14 owns the design handoff.
    - For a product with no UI surface — a headless API or backend service, or an automation whose only surfaces are notifications it sends into someone else's UI — do not invoke `product-design-builder`; record the skip in `PRD.md` and publish no placeholder design files. A UI-bearing product skips the design handoff only when the user explicitly overrides it, for example because implementation uses a design system this package does not own. Record the requester, reason, and replacement visual contract in `PRD.md`'s `## Assumptions`.

    A product is UI-bearing when a person interacts with a surface this product ships. A native mobile or desktop app is UI-bearing without a browser frontend; an internal tool with one admin screen is UI-bearing; a service whose only output is an API response, a webhook, or a message posted into a third-party client is not.

    In enhancement mode, start from the existing package's content: preserve unaffected sections, `PRD-*`, `ARCH-*`, `UI-*`, `UX-*`, `TEST-*`, `DS-*`, `MR-*` IDs, and stable release target IDs verbatim, edit or add only what the new discovery changed, mint new TEST IDs only for newly uncovered obligations, and add release target IDs only for new destinations.
12. Produce `implementation-plan.md` only when the user explicitly asks for delivery sequencing or implementation planning. Its test strategy must reuse the canonical `TEST-*` IDs from `PRD.md`; it may add sequencing and implementation detail but must not create anonymous replacements or duplicate TEST identities. Its release plan must also reuse the stable release target IDs from `architecture.md` rather than renaming destinations.
13. Run the market-research gap pass against the drafted package, following `references/market-research-guide.md`. It is on by default for a non-trivial package; skip it only when the user declined it, no web search or fetch tool is available, or the package is a trivial stub, and record which reason applied. Delegate it to one bounded read-only researcher — the `market-research` lane of `assets/templates/CLAUDE_PRD_WORKFLOW.template.js` when step 10 ran the workflow, otherwise a single read-only subagent, otherwise the parent doing the same role inline. The researcher reads the drafted `PRD.md` and returns `market-research.md` plus gap findings; it never edits a file. Stage `market-research.md` with the rest of the package, apply the findings the user's scope allows, cite the supporting `MR-*` IDs in the sections they change, and record anything that would widen scope as an open question instead of acting on it. Every claim carries a source URL, publisher, and retrieval date, or it is recorded `UNVALIDATED` — never invent a competitor, price, or market figure. If the role returns blocked, publish without the artifact and record the unvalidated market context in `PRD.md`'s `## Assumptions`.
14. For a UI-bearing product, after the core documents and market-research gap pass are resolved, load `product-design-builder`. That skill must load `frontend-design` before any design work and owns `wireframes.md`, `design-system.md`, and `design-system.json` in the same staging package. Pass it the staged PRD, architecture, stack decisions, Builder UX Direction Decision, `market-research.md` and its `MR-*` evidence when produced, the recorded skipped/blocked research status otherwise, platform and release constraints, stable upstream trace IDs, existing design artifacts for an enhancement, and approved references with their declared use as `design inspiration` or `page-faithful target` when known. It asks the human owner once for style preferences and visual references, waits for the answer, then recommends exactly three product-specific, current-reference-informed directions before selection. It may call a direction market-supported only when valid `MR-*` evidence applies; a market-research URL is not visual evidence until `product-design-builder` separately inspects it. If `frontend-design` is unavailable, stop with the core documents staged and report the blocked design dependency; do not create substitute design artifacts here.
15. Run the quality checklist in `references/output-contract.md` against the staged package. Resolve every required workflow lane and material verifier finding before finalization.
16. After validation, show the exact publish paths, overwrite targets, and archive moves. If the original request already authorized those exact mutations, perform them immediately. Otherwise, immediately after listing them, ask one explicit yes/no publication question. If the user approves, execute the approved publish and archive moves in the same run using `references/artifact-lifecycle.md`, and remove the now-empty run-specific staging directory as the final step of that same run — publication is not complete while a redundant staged copy still sits in `docs/product/.prd-staging/`; if the user declines or does not answer, leave the validated staging package intact and report it as ready to publish. Never archive documents when the workflow is incomplete, paused, failing validation, or awaiting approval.
17. In the same publish move set, seed a missing root `AGENTS.md` and a missing root `CLAUDE.md` from `../fullstack-harness-engineering/assets/templates/PROJECT_AGENTS.template.md` — the same runtime-neutral project-rules template `fullstack-harness-engineering` uses at first bootstrap — so both files exist before any implementation run starts. List them with step 16's publish paths; they are new-file creations only and add no overwrite or archive move. Skip either file that already exists; never overwrite an established root `AGENTS.md` or `CLAUDE.md`. If the user declines publication, seed nothing.
18. Report the final artifact paths, every seeded root rules file, and every archived path.
19. After reporting a completed package, ask whether the user wants to run `fullstack-harness-engineering` next using the new package as its product input, naming the published folder (`docs/product/`) so the harness's document-folder step has an explicit path rather than waiting for the user to supply one. State what it consumes: `PRD.md`, `architecture.md`, and `stack-decisions.md` for scope, plus — for a UI-bearing product — `wireframes.md` for screen structure and `design-system.md` and `design-system.json` as the binding visual contract its UI Implementation Contract enforces. When `implementation-plan.md` exists, the harness also reads its Harness Handoff Signals as non-canonical planning hints. `market-research.md` and the `MR-*` citations in `PRD.md` are informational for human readers; the harness does not consume them. If a UI-bearing product skipped the design system under the explicit user override in step 11, record that gap before offering the Harness, because the harness will classify the design input as `missing` and stop for acceptance. Do not invoke another skill without an explicit yes, and do not offer the handoff while the PRD workflow is incomplete, paused, failing validation, or awaiting publish approval.

## Interview Rules

- Run discovery in two phases. First, ask one organized free-text interview message, grouped by topic, covering the open-ended discovery categories (goal, users/roles, workflows, data/integrations, business rules, delivery constraints, success metrics, confirmation/recovery). Tell the user that the applicable multiple-choice decisions come next, then end the turn and wait for their reply. Do not call `AskUserQuestion` in the same turn as the free-text interview. After the user replies, use those answers to determine which closed-set decisions still apply, then run the `AskUserQuestion` batch(es) for platform, archetype, validation depth, database category and auth strategy when the product has a backend/data/auth surface, and the closed Builder UX Direction dimensions. Use the tool's built-in Other option instead of inventing a separate free-text fallback. Do not run a fixed high-fidelity visual-style questionnaire here.
- Step 6's questions are always their own third `AskUserQuestion` call — never fold them into step 4 or step 5. The deployment platform and the mobile/desktop platform follow-up depend on step 4's archetype answer, so asking them in that batch asks about a surface nobody has named yet; and step 4 plus the database/auth pair, or step 5 plus anything, would exceed the 4-question cap. Three calls is the cap for the whole interview: step 6 drops a question per `references/interview-guide.md` rather than opening a fourth. The first `AskUserQuestion` call starts only after the user has replied to the free-text interview, so the sequence gives them a clear response window before any multiple-choice form appears.
- Do not ask questions already answered by the user's prompt.
- Before drafting, finish the free-text release discovery with a complete expected deployable-surface inventory using stable surface IDs, then stable development and production target IDs for every expected surface. Keep each target's stable `surface` separate from its stage-specific `provider`; providers may differ by stage. Record each target's source policy as the exact branch or ref the release builds from — for example the pushed integration-branch head for development and the default-branch head after merge for production — and record any other source rule, such as a signed tag, explicitly. Also close artifact and signing, exact channel/track, release gate path, actual availability, rollout, and rollback or forward-fix. These are not extra closed-set `AskUserQuestion` calls.
- Mark optional questions clearly when they would improve quality but should not block progress.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.
- If the user gives conflicting requirements, resolve them before drafting or call out the conflict in `open questions`.
- Treat builder preference as a direction input, not as proof that users find the result usable. When it conflicts with user evidence or an accessibility requirement, record the conflict and validation need instead of silently following preference.
- In enhancement mode (Workflow step 2), never repeat questions the existing package already answers. Scope the free-text message and every `AskUserQuestion` call to what the new idea adds, changes, or leaves genuinely unresolved.

## Reference Routing

- Use `references/interview-guide.md` for required discovery questions and readiness criteria.
- Use `references/output-contract.md` for the exact artifact names, headings, and final quality checklist.
- Use `references/artifact-lifecycle.md` for detecting an existing package to enhance, staging, final `docs/product/` locations, safe identification of superseded documents, and post-validation archival.
- Use `references/architecture-playbook.md` for implementation-ready architecture content across web, mobile (native iOS, native Android, Flutter), desktop (macOS, Windows, cross-platform), internal tools, and automations, including the development-to-production release contract for deployable web products (Cloudflare given as the worked example; substitute the resolved platform) and the app-store/signed-installer distribution discipline for native mobile and desktop targets.
- Use `references/frontend-stack-selection.md` to separate frontend technology layers, recommend one product-fit stack, and verify current Cloudflare support when that platform is in scope.
- Use `references/backend-stack-selection.md` to decide service topology first, then separate backend runtime, database, and auth technology layers, resolve the database category and auth strategy, recommend one product-fit stack for the backend framework, database engine, and auth provider, and verify current platform/vendor support.
- Use `references/mobile-stack-selection.md` for a mobile-app surface: separate cross-platform-vs-native, framework (Flutter vs React Native), and the React Native Expo-vs-bare workflow layers, recommend one product-fit stack, and verify current Expo/React Native/Flutter support. It pairs with `architecture-playbook.md`'s React Native / Expo, Flutter, and native patterns.
- Use `../product-design-builder/SKILL.md` for every wireframe or design-system handoff. It owns the structural and visual guides, templates, and deterministic design-system checks, and it fails closed unless `frontend-design` is loaded.
- Use `references/dynamic-workflow.md` for the stable PRD role graph, bounded Claude Code workflow, failure handling, and sequential fallback.
- Use `references/market-research-guide.md` for the post-draft market-research gap pass: what to research, the source and anti-fabrication rules, `MR-*` IDs, which PRD section each finding lands in, and when the role returns blocked.

## Output Standards

- Write each artifact for the primary reader named in `references/output-contract.md`'s "How To Read This Package", and respect its length budget. Completeness is not the only bar — a document nobody finishes reading has not delivered its requirements.
- Put meaning before bookkeeping in every artifact. Open with what a human needs to understand the product; close with the ID matrices and decision records that machines, auditors, and downstream skills need. Never open a document with a trace table.
- Keep tables at seven columns or fewer. When a row needs more fields than that, write one block per item instead of widening the table.
- Prefer specific, buildable requirements over vague product language.
- Keep the current PRD package directly under `docs/product/`; reserve `docs/product/archived/` for superseded documents only.
- Tie every major requirement to a user need, workflow, metric, or constraint.
- Mint stable upstream trace IDs: `PRD-*` for product requirements, `ARCH-*` for architecture contracts, `UX-*` for usability requirements, `TEST-*` for test obligations, and `MR-*` for market-research findings. `product-design-builder` owns `UI-*`, `DS-*`, and `DS-COMP-*`. Preserve every family across revisions and never reuse a retired ID for a different meaning.
- Keep market research evidence in `market-research.md` and conclusions in the artifact they affect. `PRD.md` cites the `MR-*` ID behind a statement; it does not restate the competitor table, the sources, or the retrieval dates. A market claim with no source is recorded `UNVALIDATED` with what was searched, never stated as fact and never invented.
- Keep `## Non-Functional Requirements` in every `PRD.md`, immediately after Functional Requirements. Use `PRD-*` IDs and record every applicable quality attribute with a scoped measure and target; record non-applicable categories explicitly as `N/A` with a reason. Vague words such as `fast`, `secure`, `reliable`, or `scalable` are invalid without measurable units, population or traffic shape, measurement window, and percentile where applicable.
- Keep `## Test Obligations` in every `PRD.md`, after Open Questions and before the trailing Builder UX decision. Use the canonical columns from `references/output-contract.md`. Map every `Must` functional requirement and every applicable NFR to at least one `TEST-*` row marked required, with upstream trace IDs and a literal or measurable expected signal.
- For every UI-bearing product, record the Builder UX Direction Decision and pass it to `product-design-builder`. Do not let a design or implementation agent invent its own taste when the human decision owner has not answered; use an explicit provisional assumption only when assumption mode is authorized.
- Include loading, empty, error, permission, and edge states when a UI or workflow has them.
- Treat `PRD.md` as canonical for product scope and Builder UX Direction. `product-design-builder` owns the canonical structure and visual implementation sources and preserves `UI-*`, `UX-*`, `DS-*`, and `DS-COMP-*` across revisions. A conflict returns to the owning source instead of being resolved by whichever file was opened last.
- This skill owns the product definition, not design authoring or implementation. It creates no wireframe, design-system, production component, Harness plan, mission map, PLAN/RUN state, or E2E evidence register. `product-design-builder` creates the design contract with mandatory `frontend-design`; `fullstack-harness-engineering` implements the frozen result.
- Keep assumptions explicit and avoid hiding unresolved decisions in confident prose.
- Architecture may remain technology-neutral overall. For every product with a browser frontend, record the required or already selected frontend stack, or recommend one explicit stack when the user has not chosen and discovery provides enough evidence. On every layer row record Selection, Status, cited Authority/evidence, Why it fits, and Constraint/follow-up; sections may mix statuses, authority is a cited source rather than a status label, and a recommendation is not misrepresented as a fixed requirement. Record the deployment platform, rendering model, framework, UI library, build tool, and key supporting choices as separate layers.
- For every deployable web, API, mobile, or desktop surface, close a provider-neutral release-target contract before drafting. Record the complete expected deployable-surface inventory with stable surface IDs, then give every target a stable target ID and a `development` or `production` stage. Record stable `surface` separately from stage-specific `provider`, the source policy (the exact branch or ref each stage's release builds from), artifact kind, signing requirement, exact channel or track, submission/promotion/review or manual-approval path, actual availability signal, rollout, and rollback or forward-fix path. Require development and production targets for every expected surface; reject missing surfaces. Providers may differ by stage. Preserve surface and target IDs across revisions and never reuse an ID for a different meaning. An upload, submission, or approval is not availability by itself.
- For a deployable web or API target, resolve the deployment platform explicitly via the interview's platform `AskUserQuestion` step (see Workflow step 6, after the archetype is known) unless the user or current repository already names one. Never silently assume a platform, and do not invent platform-specific requirements for docs-only work. Record one codebase promoted through separate development and production environments (named Workers for Cloudflare, or the platform's equivalent unit), exact release sources, isolated bindings and secrets, data/auth/payment modes, migration order, deployed-environment checks, and rollback.
- Keep native mobile and desktop targets in the provider-neutral release-target contract rather than forcing them into the hosted web/API environment table. For store or signed-installer delivery, production availability means the approved artifact is actually installable or downloadable through the named channel and passes its smoke check. When instant rollback is impossible, record rollout halt plus a signed forward-fix through the same review or distribution path.
- For every product with a backend, persistent data, or auth requirement, record the required/selected backend stack, or recommend one explicit stack when evidence supports it, following the same per-layer status and cited-authority discipline as the frontend. Record service topology first — monolith versus named services and monorepo versus polyrepo organization — followed by backend runtime/framework, database category, database engine, auth strategy, auth provider, and key supporting choices (API style, background jobs/queue, file/object storage) as separate layers.
- For a product with a backend, persistent data, or auth requirement, resolve the database category and auth strategy explicitly via the interview's backend/data `AskUserQuestion` step (see Workflow step 6) unless the user or current repository already names them. Never silently default to a specific database engine or auth vendor.
- For every product with a mobile app or desktop app target, record the required or already selected mobile/desktop stack in a `Mobile/Desktop Technology Decision` section, or recommend one explicit stack per `references/mobile-stack-selection.md` when the user has not chosen and discovery provides enough evidence, following the same per-layer status and cited-authority discipline as the frontend and backend sections. Record the platform, toolchain, distribution mechanism, backend/API integration, push/offline-sync approach, and testing as separate layers. This section may be added in a later revision after `Frontend Technology Decision` is already frozen, when a mobile or desktop target is added to an existing web product.
- Do not present Cloudflare, Astro, React, and Vite as peer alternatives: Cloudflare is a deployment/runtime platform, Astro is a web framework, React is a UI library, and Vite is a build tool that can be paired with React or used by frameworks.
- Keep a decision technology-neutral only when evidence is genuinely insufficient. In that case, document the missing evidence, decision owner, decision deadline, and a time-boxed spike with pass/fail criteria.
- When recommending a fast-moving hosted platform or framework, verify current official documentation and record the check date and sources in `stack-decisions.md`.
- Treat the stable PRD roles as an org graph and each bounded workflow run as a temporary work graph. Dynamic Workflow coordinates read-only analysis; the parent still owns source freeze, staged artifact writes, conflict resolution, approval, publication, and cross-session recovery.
- When `implementation-plan.md` is requested, include non-canonical Harness handoff signals for dependency order, parallel candidates, shared resources, required reviews, and human gates. Do not create PLAN/RUN mission maps in this skill.
