# PRD Builder

## Overview

Use this skill to turn a user's product idea or requirement into a complete Markdown PRD package. Default all generated artifacts to English unless the user explicitly requests another language.

## Workflow

1. Read `references/interview-guide.md` before asking discovery questions.
2. Read `references/artifact-lifecycle.md`'s Detect Enhancement Mode section, then check whether `docs/product/PRD.md`, or another Markdown document whose title or content clearly describes the same product, already exists in the repository. If one does, treat this run as an **enhancement** of that package, not a new one: read the existing `PRD.md`, `architecture.md`, `stack-decisions.md`, `wireframes.md`, and — when present — `design-system.md` and `design-system.json` in full before asking anything else. Carry forward their content, decisions, and trace IDs unchanged, and scope every remaining step — interview, `AskUserQuestion` calls, drafting — to only what the new request adds, changes, or removes. Never restart discovery from a blank slate or regenerate the whole package from scratch when an existing package for the same product is found.
3. Conduct a complete but concise product interview before drafting, unless the user explicitly says to skip questions, make assumptions, or produce a first draft immediately. In enhancement mode (step 2), skip this in favor of a short delta interview covering only what the new idea touches — do not re-ask what the existing package already answers. Scope this free-text message to the open-ended discovery categories in `references/interview-guide.md` (goal, users/roles, workflows, data/integrations, business rules, delivery and release targets, success metrics, and confirmation/recovery expectations).
4. Immediately after the free-text interview message — not interleaved with it as separate turns — issue the first `AskUserQuestion` call (max 4 questions per call) resolving the closed-set decisions marked `(AskUserQuestion)` in `references/interview-guide.md` that depend on no other answer: product archetype and validation depth. Keep the deployment platform out of this call. It only means something once the archetype is known, so step 6 carries it. Do not ask the user to choose from a fixed high-fidelity style catalog; the optional downstream `frontend-design` exploration derives product-specific preference choices after the PRD and wireframes are stable. In enhancement mode, only re-ask a closed-set decision the new idea actually reopens; otherwise keep the existing package's answer.
5. For a UI-bearing product, capture a `Builder UX Direction Decision` before drafting wireframes, following `references/wireframe-guide.md`'s Builder UX Direction Gate. Resolve the builder to the human product/design decision owner or commissioning team. Use a second `AskUserQuestion` call (4 questions, at cap) for the closed dimensions — experience priority, guidance versus expert control, information density, and preferred layout/interaction pattern — and capture confirmation/recovery behavior as free text, since it varies too much by action to enumerate further. Validation depth is already answered by step 4's call; carry that answer forward instead of re-asking it. Mark every decision `selected`, `provisional`, or `assumed`. In enhancement mode, only revisit a dimension the new idea actually affects.
6. Issue a third `AskUserQuestion` call (at most 4 questions) for the closed-set decisions that depend on step 4's archetype answer, marked `(AskUserQuestion)` in `references/interview-guide.md`:
    - the deployment platform (Cloudflare / Vercel / AWS / Self-hosted, plus the tool's built-in Other for anything else, including an explicit stage-to-provider mapping) when the resolved surface includes a deployable web, API, or hosted backend target;
    - the mobile platform follow-up when an archetype is a mobile app, and the desktop platform follow-up when one is a desktop app;
    - the database category and auth strategy for a product with a backend, persistent data, or auth requirement — evident from the free-text interview's data/integrations and business-rules answers, or the archetype captured in step 4.

    Skip any question the archetype makes inapplicable, or that the user's prompt, the existing package, or the current repository already answers. Local persistence or local-only auth may require the backend/data decision pair and backend analysis without creating a hosted deployable surface; `has_backend` alone never triggers the deployment-platform question. Skip the database-category and auth-strategy pair only when the product provably has no backend, persistent data, or auth surface, such as a purely static content or marketing site with no forms, accounts, or dynamic data. Skip the whole call only when none of its questions apply. Do not silently pick a database category or auth strategy on the user's behalf. Only a hybrid spanning web, mobile, and desktop surfaces with a backend leaves five questions unresolved; in that case follow the drop order in `references/interview-guide.md` instead of opening a fourth call.
7. Classify the product as one or more archetypes: web app, mobile app, desktop app, internal tool, automation or agent workflow, API or backend service, or hybrid. For a mobile app, also record the resolved mobile platform (native iOS, native Android, Flutter, or React Native); for a desktop app, the resolved desktop platform (macOS, Windows, or cross-platform), since these select the matching pattern in `references/architecture-playbook.md`. Record whether it has any public-facing marketing, landing, or SEO-relevant page as distinct from purely internal or authenticated-only surfaces; this gates the SEO copy review below.
8. After discovery, read `references/output-contract.md`, `references/architecture-playbook.md`, and `references/dynamic-workflow.md`, plus the rest of `references/artifact-lifecycle.md` and `references/wireframe-guide.md` beyond the sections steps 2 and 5 already used. For a UI-bearing product, also read `references/design-system-guide.md` before drafting the design system. For a web app, internal tool, public website, or hybrid with a browser frontend, also read `references/frontend-stack-selection.md`. For any product with a backend, persistent data, or auth requirement — most products other than a purely static content site — also read `references/backend-stack-selection.md`. For a mobile-app or desktop-app surface, also read `references/mobile-stack-selection.md`; its desktop platform patterns live in `references/architecture-playbook.md`.
9. Before drafting, inventory earlier documents related to the same product as described in `references/artifact-lifecycle.md`. Do not move anything yet. In enhancement mode, this still includes the existing package identified in step 2 — it will be archived for history once the enhanced draft is published, even though its content already carried forward into that draft.
10. For a non-trivial package, when Claude Code Dynamic Workflow is observed, multi-agent analysis is authorized, and the host can enforce the `builder_readonly` tool profile from `references/dynamic-workflow.md`, run `assets/templates/CLAUDE_PRD_WORKFLOW.template.js` after the interview, the `AskUserQuestion` decisions, source inputs, explicit expected deployable-surface inventory, and provider-neutral release targets are frozen. Skip the workflow in enhancement mode: its lanes generate fresh content, which is exactly what step 2 forbids. Perform the roles sequentially against the existing package instead. Retain failed lanes explicitly and treat the returned package as a candidate for parent review. If Dynamic Workflow or the read-only boundary is unavailable, perform the same roles sequentially and state that fallback.
11. Draft or repair the core Markdown package in the staging location defined by `references/artifact-lifecycle.md`:
    - `PRD.md`
    - `architecture.md`
    - `stack-decisions.md`
    - `wireframes.md`
    - `design-system.md` and `design-system.json` for a UI-bearing product, following `references/design-system-guide.md` and the two templates. Draft them after `wireframes.md`, because the primitive inventory is derived from the screens the wireframes actually contain. Publish the pair together — neither file may carry a token, primitive, or variant the other does not. For a product with no UI surface, skip both and record that in the package.

    In enhancement mode, start from the existing package's content: preserve unaffected sections, `PRD-*`, `ARCH-*`, `UI-*`, `UX-*`, `TEST-*`, `DS-*` IDs, and stable release target IDs verbatim, edit or add only what the new discovery changed, mint new TEST IDs only for newly uncovered obligations, and add release target IDs only for new destinations.
12. Produce `implementation-plan.md` only when the user explicitly asks for delivery sequencing or implementation planning. Its test strategy must reuse the canonical `TEST-*` IDs from `PRD.md`; it may add sequencing and implementation detail but must not create anonymous replacements or duplicate TEST identities. Its release plan must also reuse the stable release target IDs from `architecture.md` rather than renaming destinations.
13. Run the quality checklist in `references/output-contract.md` against the staged package. Resolve every required workflow lane and material verifier finding before finalization.
14. After validation, show the exact publish paths, overwrite targets, and archive moves. If the original request already authorized those exact mutations, perform them immediately. Otherwise, immediately after listing them, ask one explicit yes/no publication question. If the user approves, execute the approved publish and archive moves in the same run using `references/artifact-lifecycle.md`, and remove the now-empty run-specific staging directory as the final step of that same run — publication is not complete while a redundant staged copy still sits in `docs/product/.prd-staging/`; if the user declines or does not answer, leave the validated staging package intact and report it as ready to publish. Never archive documents when the workflow is incomplete, paused, failing validation, or awaiting approval.
15. Report the final artifact paths and every archived path.
16. After reporting a completed package, ask whether the user wants to run `fullstack-harness-engineering` next using the new package as its product input, naming the published folder (`docs/product/`) so the harness's document-folder step has an explicit path rather than waiting for the user to supply one. State what it consumes: `PRD.md`, `architecture.md`, `stack-decisions.md`, `wireframes.md` for scope and structure, and — for a UI-bearing product — `design-system.md` and `design-system.json` as the binding visual contract its UI Implementation Contract enforces. If a UI-bearing product deliberately skipped the design system, record that gap before offering the Harness, because the harness will classify the design input as `missing` and stop for acceptance. Do not invoke another skill without an explicit yes, and do not offer the handoff while the PRD workflow is incomplete, paused, failing validation, or awaiting publish approval.

## Interview Rules

- Ask one organized free-text interview message, grouped by topic, covering the open-ended discovery categories (goal, users/roles, workflows, data/integrations, business rules, delivery constraints, success metrics, confirmation/recovery). Immediately follow it with the `AskUserQuestion` batch(es) for the closed-set decisions (platform, archetype, validation depth, database category and auth strategy when the product has a backend/data/auth surface, and the closed Builder UX Direction dimensions) — do not spread these across additional free-text turns, and use the tool's built-in Other option instead of inventing a separate free-text fallback. Do not run a fixed high-fidelity visual-style questionnaire here.
- Step 6's questions are always their own third `AskUserQuestion` call — never fold them into step 4 or step 5. The deployment platform and the mobile/desktop platform follow-up depend on step 4's archetype answer, so asking them in that batch asks about a surface nobody has named yet; and step 4 plus the database/auth pair, or step 5 plus anything, would exceed the 4-question cap. Three calls is the cap for the whole interview: step 6 drops a question per `references/interview-guide.md` rather than opening a fourth. Before the first `AskUserQuestion` call, tell the user in one sentence that a short round (or rounds) of multiple-choice questions follows the free-text interview, so the sequence reads as one bounded step rather than an open-ended series of forms.
- Do not ask questions already answered by the user's prompt.
- Before drafting, finish the free-text release discovery with a complete expected deployable-surface inventory using stable surface IDs, then stable development and production target IDs for every expected surface. Keep each target's stable `surface` separate from its stage-specific `provider`; providers may differ by stage. Use only current PLAN-v5 source policies (`pr_head` or `integration_head` for development; `merged_main` for production), and record a signed-tag or other unsupported source requirement as an unresolved engineering-handoff gap. Also close artifact and signing, exact channel/track, release gate path, actual availability, rollout, and rollback or forward-fix. These are not extra closed-set `AskUserQuestion` calls.
- Mark optional questions clearly when they would improve quality but should not block progress.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.
- If the user gives conflicting requirements, resolve them before drafting or call out the conflict in `open questions`.
- Treat builder preference as a direction input, not as proof that users find the result usable. When it conflicts with user evidence or an accessibility requirement, record the conflict and validation need instead of silently following preference.
- In enhancement mode (Workflow step 2), never repeat questions the existing package already answers. Scope the free-text message and every `AskUserQuestion` call to what the new idea adds, changes, or leaves genuinely unresolved.

## Reference Routing

- Use `references/interview-guide.md` for required discovery questions and readiness criteria.
- Use `references/output-contract.md` for the exact artifact names, headings, and final quality checklist.
- Use `references/artifact-lifecycle.md` for detecting an existing package to enhance, staging, final `docs/product/` locations, safe identification of superseded documents, and post-validation archival.
- Use `references/architecture-playbook.md` for implementation-ready architecture content across web, mobile (native iOS, native Android, Flutter), desktop (macOS, Windows, cross-platform), internal tools, and automations, including the development-to-production release contract for deployable web products (Cloudflare given as the worked example; substitute the resolved platform) and the app-store/signed-installer distribution discipline for native mobile and desktop targets.
- Use `references/frontend-stack-selection.md` to separate frontend technology layers, recommend one product-fit stack, and verify current Cloudflare support when that platform is in scope.
- Use `references/backend-stack-selection.md` to decide service topology first, then separate backend runtime, database, and auth technology layers, resolve the database category and auth strategy, recommend one product-fit stack for the backend framework, database engine, and auth provider, and verify current platform/vendor support.
- Use `references/mobile-stack-selection.md` for a mobile-app surface: separate cross-platform-vs-native, framework (Flutter vs React Native), and the React Native Expo-vs-bare workflow layers, recommend one product-fit stack, and verify current Expo/React Native/Flutter support. It pairs with `architecture-playbook.md`'s React Native / Expo, Flutter, and native patterns.
- Use `references/wireframe-guide.md` for each screen's main-purpose reasoning, its matching layout skeleton, Mermaid flows, and required UI states. Write the main purpose and structural rationale before drawing the ASCII box, not after.
- Use `references/design-system-guide.md` for the design-target archetype rules, the responsive verification set, the color and typography decision discipline, the four primitive layers and the closed-variant rule, and the taste and anti-slop guardrails. It pairs with `assets/templates/DESIGN_SYSTEM.template.md` and `assets/templates/DESIGN_SYSTEM.template.json`.
- Use `references/dynamic-workflow.md` for the stable PRD role graph, bounded Claude Code workflow, failure handling, and sequential fallback.

## Output Standards

- Write each artifact for the primary reader named in `references/output-contract.md`'s "How To Read This Package", and respect its length budget. Completeness is not the only bar — a document nobody finishes reading has not delivered its requirements.
- Put meaning before bookkeeping in every artifact. Open with what a human needs to understand the product; close with the ID matrices and decision records that machines, auditors, and downstream skills need. Never open a document with a trace table.
- Keep tables at seven columns or fewer. When a row needs more fields than that, write one block per item instead of widening the table.
- Prefer specific, buildable requirements over vague product language.
- Keep the current PRD package directly under `docs/product/`; reserve `docs/product/archived/` for superseded documents only.
- Tie every major requirement to a user need, workflow, metric, or constraint.
- Mint stable upstream trace IDs: `PRD-*` for product requirements, `ARCH-*` for architecture contracts, `UI-*` for screens or visible regions, `UX-*` for usability requirements, and `TEST-*` for test obligations. Preserve them across revisions and never reuse a retired ID for a different meaning.
- Keep `## Non-Functional Requirements` in every `PRD.md`, immediately after Functional Requirements. Use `PRD-*` IDs and record every applicable quality attribute with a scoped measure and target; record non-applicable categories explicitly as `N/A` with a reason. Vague words such as `fast`, `secure`, `reliable`, or `scalable` are invalid without measurable units, population or traffic shape, measurement window, and percentile where applicable.
- Keep `## Test Obligations` in every `PRD.md`, after Open Questions and before the trailing Builder UX decision. Use the canonical columns from `references/output-contract.md`. Map every `Must` functional requirement and every applicable NFR to at least one `TEST-*` row marked required, with upstream trace IDs and a literal or measurable expected signal.
- For every UI-bearing product, record the Builder UX Direction Decision and carry it into `wireframes.md`. Do not let the implementation agent invent its own taste when the human decision owner has not answered; use an explicit provisional assumption only when assumption mode is authorized.
- Include loading, empty, error, permission, and edge states when a UI or workflow has them.
- Keep every low-fidelity wireframe structurally simple. Record brand references, hard limits, and product-specific visual goals, but defer high-fidelity preference discovery to the optional downstream `frontend-design` exploration. Do not use `modern-minimal` as a default.
- Treat `wireframes.md` as the canonical source for product scope, screen structure, visible-region responsibilities, actions, states, and trace IDs, and `design-system.md` plus `design-system.json` as the canonical source for the visual layer. Structure comes from the wireframes; tokens, primitives, and variants come from the design system. Neither overrides the other — a conflict is resolved by `references/design-system-guide.md`'s Conflict Rules, not by whichever file the drafter opened last.
- An explicitly authorized `frontend-design` exploration may inform the visual direction before the tokens are fixed. Its HTML is non-canonical design-stage evidence: it never replaces or silently edits the wireframes, and only `design-system.md` and `design-system.json` bind implementation.
- Keep public-site and landing-page wireframes simple: one clear value proposition and one primary action in the first viewport, one job per section, and secondary detail deferred instead of copying the whole PRD into the page.
- Make every visible wireframe region implementation-ready with either exact UI wording or a bounded display contract that states what the region must show, the intended user takeaway or action, the content or data source, and relevant format or length constraints. Do not leave generic labels such as `Main content`, `Feature section`, or `Card 1` in a final wireframe.
- In each relevant wireframe, label image/media and motion as `required`, `optional`, or `none`, and state the purpose. Also label the intended style direction for each visually important region, such as editorial split, full-bleed product proof, dense comparison, or unframed text. Keep these labels structural; the token values, primitive contracts, asset art direction, and detailed choreography belong in `design-system.md`, not in the wireframe.
- Do not use boxes in ASCII wireframes as automatic decoration. A drawn container must represent real grouping, interaction, state, or hierarchy. Do not imply repeated bordered panels with a colored side rail or accent stripe unless the stripe has a named semantic or approved brand role.
- This skill owns the product spec and the design system. It does not own implementation: no production component code, no harness plans, no mission maps, no PLAN/RUN state, no E2E evidence registers. `fullstack-harness-engineering` implements what the design system specifies.
- Keep the design system at the system level, not the page level. Define tokens, primitives with closed variant sets, product components, the state matrix, and the responsive verification set once. Do not write a per-route recipe, a per-route HTML mockup, or a page-level visual acceptance spec — implementation composes routes from the wireframes plus the design system, and a route that needs something the system lacks comes back as a design-system change.
- Mint `DS-*` trace IDs for design-system decisions: `DS-*` for a signature visual decision, `DS-LAY-*`, `DS-SUR-*`, `DS-TYP-*`, `DS-CTL-*` for primitives by layer, and `DS-COMP-*` for product components. Preserve them across revisions like every other trace family.
- Do not add candidate or selected `frontend-design` HTML to the staged or published package. If exploration exposes a structural problem, return a finding tied to the affected `UI-*` IDs to the PRD owner. Only the parent or human product/design owner may approve a bounded wireframe revision; preserve unaffected scope and IDs, then rerun the quality checklist.
- Keep assumptions explicit and avoid hiding unresolved decisions in confident prose.
- Architecture may remain technology-neutral overall. For every product with a browser frontend, record the required or already selected frontend stack, or recommend one explicit stack when the user has not chosen and discovery provides enough evidence. On every layer row record Selection, Status, cited Authority/evidence, Why it fits, and Constraint/follow-up; sections may mix statuses, authority is a cited source rather than a status label, and a recommendation is not misrepresented as a fixed requirement. Record the deployment platform, rendering model, framework, UI library, build tool, and key supporting choices as separate layers.
- For every deployable web, API, mobile, or desktop surface, close a provider-neutral release-target contract before drafting. Record the complete expected deployable-surface inventory with stable surface IDs, then give every target a stable target ID and a `development` or `production` stage. Record stable `surface` separately from stage-specific `provider`, the PLAN-v5 source policy, artifact kind, signing requirement, exact channel or track, submission/promotion/review or manual-approval path, actual availability signal, rollout, and rollback or forward-fix path. Require development and production targets for every expected surface; reject missing surfaces. Providers may differ by stage. Preserve surface and target IDs across revisions and never reuse an ID for a different meaning. An upload, submission, or approval is not availability by itself.
- For a deployable web or API target, resolve the deployment platform explicitly via the interview's platform `AskUserQuestion` step (see Workflow step 6, after the archetype is known) unless the user or current repository already names one. Never silently assume a platform, and do not invent platform-specific requirements for docs-only work. Record one codebase promoted through separate development and production environments (named Workers for Cloudflare, or the platform's equivalent unit), exact release sources, isolated bindings and secrets, data/auth/payment modes, migration order, deployed-environment checks, and rollback.
- Keep native mobile and desktop targets in the provider-neutral release-target contract rather than forcing them into the hosted web/API environment table. For store or signed-installer delivery, production availability means the approved artifact is actually installable or downloadable through the named channel and passes its smoke check. When instant rollback is impossible, record rollout halt plus a signed forward-fix through the same review or distribution path.
- For every product with a backend, persistent data, or auth requirement, record the required/selected backend stack, or recommend one explicit stack when evidence supports it, following the same per-layer status and cited-authority discipline as the frontend. Record service topology first — monolith versus named services and monorepo versus polyrepo organization — followed by backend runtime/framework, database category, database engine, auth strategy, auth provider, and key supporting choices (API style, background jobs/queue, file/object storage) as separate layers.
- For a product with a backend, persistent data, or auth requirement, resolve the database category and auth strategy explicitly via the interview's backend/data `AskUserQuestion` step (see Workflow step 6) unless the user or current repository already names them. Never silently default to a specific database engine or auth vendor.
- For every product with a mobile app or desktop app target, record the required or already selected mobile/desktop stack in a `Mobile/Desktop Technology Decision` section, or recommend one explicit stack per `references/mobile-stack-selection.md` when the user has not chosen and discovery provides enough evidence, following the same per-layer status and cited-authority discipline as the frontend and backend sections. Record the platform, toolchain, distribution mechanism, backend/API integration, push/offline-sync approach, and testing as separate layers. This section may be added in a later revision after `Frontend Technology Decision` is already frozen, when a mobile or desktop target is added to an existing web product.
- Do not present Cloudflare, Astro, React, and Vite as peer alternatives: Cloudflare is a deployment/runtime platform, Astro is a web framework, React is a UI library, and Vite is a build tool that can be paired with React or used by frameworks.
- Keep a decision technology-neutral only when evidence is genuinely insufficient. In that case, document the missing evidence, decision owner, decision deadline, and a time-boxed spike with pass/fail criteria.
- When recommending a fast-moving hosted platform or framework, verify current official documentation and record the check date and sources in `stack-decisions.md`.
- Treat the stable PRD roles as an org graph and each bounded workflow run as a temporary work graph. Dynamic Workflow coordinates read-only analysis; the parent still owns source freeze, staged artifact writes, conflict resolution, approval, publication, and cross-session recovery.
- When `implementation-plan.md` is requested, include non-canonical Harness handoff signals for dependency order, parallel candidates, shared resources, required reviews, and human gates. Do not create PLAN/RUN mission maps in this skill.
