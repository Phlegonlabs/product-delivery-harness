# Deployment Contract

Use this reference when a delivery will be deployed, verified, or moved between platforms. Harness 0.38+ RUNs end local-only at C. `branch-promotion-contract.md` controls candidate verification, exact-candidate Preview acceptance and separately authorized promotion to protected `main`; promotion does not require prior run-branch publication of A, which is needed only when a candidate environment must build from the remote run branch. This contract maps those SHAs to environments and verifies what the platform serves.

## Model

- Production tracks `main`; the production pipeline deploys only the exact candidate SHA promoted there after all candidate verification passes.
- During managed execution, the isolated internal environment tracks the exact candidate run branch or immutable candidate SHA. In `main-preview/1`, PR or branch Preview replaces protected-development landing. Production remains `refs/heads/main`; no permanent development branch is required. Pinned historical RUNs retain their original promotion contract.
- A git-connected or CI-connected platform maps the candidate run branch/SHA to the isolated non-production environment and `main` to production. The bootstrap deploy remains a separately authorized owner action when required; branch promotion adds no RUN authorization keys and never reuses the run-branch grant.
- Development and production are separate environments with separate URLs, builds, stateful resources, auth, and payment modes. A development PASS never proves production; development never binds production databases, buckets, secrets, or domains.
- Every independently released unit has one lowercase kebab-case surface name. Production uses the canonical `<product-slug>-<surface-suffix>` name without `-prod`; development uses that exact name plus `-dev`; distinct surfaces never share a release name. Use `web`, `api`, and `extension` as the normal suffixes. Use another descriptive suffix only for a separately released unit; native artifacts use their platform suffix while a separately hosted backend remains `api`. Provider and store names stay in provider/channel fields unless artifacts actually differ by provider. Long-lived staging or QA may use its real stage suffix; ephemeral candidate previews keep platform-generated identities.
- When `docs/product/architecture.md` is available, `docs/DEPLOYMENT.md` also carries **Release Target Status**, one row per exact architecture target. The architecture `release_targets.py` parser is authoritative: no invented, missing, or duplicate target IDs may pass. The `Provider / channel` cell is the exact stage-specific `Provider;Exact channel / track` pair. Production hosted web/API targets and every publicly discoverable hosted target require a credential-free HTTPS URL or hostname. Plain HTTP is valid only for a non-public development target on `localhost` or an IP loopback address. Worker/job/webhook/realtime rows require a substantive typed resource identity. Native/browser-extension PASS rows allow only a credential-free HTTPS listing/download URL, exact `n/a — artifact-only:<artifact>; no network endpoint`, or (only when artifact is `n/a`) exact `n/a — channel-only:<Provider;channel>; no network endpoint`. A current PASS binds Release target ID, surface, stage, provider/channel, target-specific endpoint/domain, Expected SHA, Deployed SHA, artifact/build identity, availability evidence, checked time, and status, with Expected equal to Deployed. In both this table and the legacy **Environment Status** table, Checked is an RFC3339 timestamp with a timezone, such as `2026-09-03T14:05:00Z`; a bare date fails `check_deployment.py`. Artifact `n/a` is valid only when the architecture target's `Artifact kind` is exactly `no independent artifact`; all other targets require a concrete artifact/build identity.
- A `deployment/2` record also carries **Release Source Provenance**, one row per architecture target, with `Release target | Source ref | Source SHA | Authority evidence`. The ref must equal the target's selected candidate/1 or dual-branch/1 authority. Preparation may leave Source SHA and evidence `pending`; a PASS and strict readiness require a full lowercase Source SHA equal to Expected SHA and Deployed SHA. Authority evidence references a bounded regular retained observation file and its SHA-256. The closed `deployment-source-observation/1` JSON binds repository, source/ref authorities, full SHA, artifact, observed RFC3339 time, and the actual read-only command/provider result. The caller independently supplies expected repository and, for candidate/1 development, the concrete candidate ref. The checker reads structure only: it never executes evidence, fetches a provider, deploys, reads credentials, or treats command spelling or prose alone as proof.
- Strict readiness proof evaluates the explicitly requested target subset. Activation, SEO, and Outcome pass only targets for which they claim ready or verified readiness. The provenance inventory and Target Readiness inventory still cover every architecture target.
- CLI or console deploys remain explicit user machine mutations outside the RUN ledger, like any other installed-software operation. The Harness never triggers, rolls back, or reconfigures a deployment.

## Platform Abstraction

Any lowercase platform id is valid. Each section below names that platform's native preview and production mechanics; `generic` covers everything else. Adding a platform adds one section, not a new flow — the model above does not change.

## Human Configuration Handoff

`docs/DEPLOYMENT.md` is both the deployment record and the operator handoff. `product-definition-builder` seeds it from the product and architecture decisions. Before every deployable push, `delivery-harness` reconciles it against the implementation whenever the change adds, removes, renames, or changes the use of configuration, auth, a binding, an integration, or a deploy workflow. After deployment, the parent records the observed environment result and leaves every external-console task truthfully `pending`, `configured`, `verified`, or `n/a`. A later `product-activation` run may consume those rows, but it receives no authorization from their presence or status.

The reconciliation is name-only and read-only:

1. Inspect tracked declaration surfaces: `.env.example` or another committed example, typed environment schemas, platform config, CI workflows, and the code paths that read configuration or call auth and external services.
2. Never open value-bearing local files such as `.env`, `.env.local`, `.dev.vars`, exported platform secrets, or credential stores to populate the document. Never copy a value into Markdown, Git, logs, command transcripts, or evidence.
3. In **Required Secrets and Variables**, record each exact key name, classify it as a secret or non-secret variable, name its consumer, identify the exact preview and production placement, name where the human obtains it, and record status. Include CI deploy credentials as well as application runtime configuration. Browser-exposed keys are variables even when their provider calls them keys.
4. In **External Console Setup**, record every non-code action with its exact system and environment: auth application or tenant creation, callback and logout URLs, allowed origins, webhook registration, domain/DNS attachment, role grants, payment mode, or another provider-side setting.
5. When no rows apply, keep an explicit `none` / `n/a` row. Never omit either section, and never invent a key or callback URL that the product or implementation has not defined.

A `pending` row is allowed in the record because it is an honest human handoff. It is also an availability gate: if the row is required for the target environment, that environment cannot be reported ready until the human finishes it and a behavior-level smoke check passes. The Harness reports the exact pending names and console tasks; it never fills, rotates, reveals, or guesses their values and never reconfigures the platform.

## Platform: cloudflare

- The default Cloudflare route is Workers with Static Assets. Pages requires the owner's recorded stack decision.
- The following Wrangler procedure applies to non-Void Workers. Void projects use the tool-specific route below; never inherit Wrangler commands automatically.
- Prefer [Workers Previews](https://developers.cloudflare.com/workers/previews/) for PR or branch review. The project dependency must be Wrangler 4.135.0 or later. `wrangler preview` creates or updates the branch Preview; `wrangler deploy` remains the separately configured main production command.
- Configure the complete non-production binding set in `previews`. Previews do not inherit production settings. Keep variables, secrets, auth and sandbox payments separate. Record canonical development release names as logical target identities; provider-generated Preview names and deployment IDs are separate evidence.
- Resource isolation is configured, not assumed. Native Previews isolate Durable Object namespaces and Containers. Bind D1, KV and R2 explicitly to separate non-production resources. Record production and development resource IDs in Resource Isolation; any production ID appearing in a development binding is a blocker, not a configuration preference. `check_deployment.py` rejects shared IDs.
- Review [resource limitations](https://developers.cloudflare.com/workers/previews/resources/) before choosing Previews. Service bindings call the bound Worker's production deployment. Workflow bindings use existing Workflows, Queue consumers cannot target a Preview, and Cron Triggers and routes target production. A required journey that cannot avoid production side effects needs an isolated alternative or remains blocked. Never count unsupported behavior as accepted.
- Adding a binding follows this order: create the non-production resource, declare it, deploy the exact candidate branch/SHA, and verify its Preview. For D1, use `wrangler d1 create <resource-name>-dev` or the approved equivalent before declaring its ID. Prepare production resources and declarations in the same candidate lineage; repeat candidate checks if bytes change. Then separately land the verified candidate on main. Development secrets stay fake or dedicated. D1 migrations run against the non-production database first; production schema must exist before dependent production code serves traffic.
- If native Previews cannot satisfy the product or its installed tooling, record the reason and use an isolated named environment such as `env.development`. Named environments do not inherit bindings. A separately named branch Worker may be used for unsupported preview topologies; reserve its prefix and protect all permanent Workers. Creating or deleting it requires exact authorization.
- Version URLs are distinct from native Previews. Version previews inherit the Worker's existing bindings; a production Worker Version URL shares live bindings. Do not use it for stateful review. `wrangler versions upload --env development` is valid only against an independently verified non-production Worker.
- Void is an optional project-local SDK/CLI choice. Direct Cloudflare remains `cloudflare` and uses `void deploy --platform cloudflare`; a team Void platform is a separate deployment decision mapped through the generic contract. This adds no stage, gate, schema or agent role. Pin the installed package and CLI together. Review `void init`/`void migrate` changes to manifests, config, AGENTS and skill links. Do not use automatic global skill linking or default adoption. Run `void prepare` before typechecking; preserve project tests and browser checks.
- Treat `void.config.ts`, `void.lock.json`, resource/DO migration history and the package's state guidance as release inputs. Commit those files; keep generated `.void/` types/local state and `.void-wrangler.jsonc` out of Git, while preserving required `.void/` recovery files on disk for a failed deploy. Do not delete local state automatically, and never commit secret values. `void deploy` can create resources, upload builds or apply migrations before a failed validation. One integration owner runs a first deployment one machine at a time. After failure, cancellation or timeout, inspect remote resources and lock/migration state, then resume or retry only under existing authority. A missing completion report is not proof of no side effects.
- Direct Cloudflare supports neither named environments nor `--project`. Use one verified separate project config and `void.lock.json` mapping per isolated target. Complete its non-production resources and secrets, and use an approved isolated alternative when native Previews cannot be proven. Worker direct deploys need a fresh build; `--skip-build` is only for existing static output. Normal readiness stages, but `--atomic` and first-worker bootstrap may send traffic before checks, so preserve explicit deployment authorization.
- For Void candidate review, prove native Workers Preview support for the pinned package, framework, build, and generated config before selecting it. Generated config alone is insufficient. Otherwise record an approved isolated development Worker with separate config/lock root, resources, secrets, routes, and triggers. From that root, use the project-local `void deploy --platform cloudflare` for the exact candidate, including its fresh build and authorized provisioning/migrations. Read back the fixed deployment ID, SHA, and resource mapping before smoke checks. Do not substitute raw `wrangler preview`, a production config, or `--skip-build` for this route. Keep unsupported native Preview journeys blocked.
- One integration owner serializes schema, migration, lock, resource and trigger changes and deploys per application; workers do not deploy independently. Record candidate/main source SHAs, the immutable deploy ID/artifact, actual read-back and smoke. Code rollback does not reverse DB migrations, and Durable Object transitions have migration limits; record compatibility, forward-fix and recovery. Never equate a production Worker's Version URL with an isolated Preview.
- Pages preview deployments use the candidate PR/branch; main remains the configured production branch. CI Direct Upload uses `wrangler pages project create <name> --production-branch main`. A Direct Upload project cannot later become git-connected.
- Record both the moving branch Preview URL and the fixed deployment URL/ID from platform output. Read back the actual candidate SHA; never guess the URL. Verify smoke, auth, bindings and applicable UI evidence before main landing. A preview upload or PR comment alone is not acceptance.
- Production build, deployment read-back and smoke bind the actual main SHA separately. CI connections do not authorize new external actions or bootstrap deployments.

## Platform: vercel

- Git-connected: the exact candidate run branch supplies the internally verified preview and `main` supplies production.
- Keep preview and production environment variables and domains separate in the project settings; the protected-production boundary is the platform's environment scoping, not a Harness action.
- Deployed-commit check: `vercel inspect <url>` or the Vercel API.

## Platform: aws

- Amplify, git-connected: map the exact candidate run branch to an isolated non-production environment and `main` to production.
- Preview and production use separate backend environments and secrets; never point a preview branch mapping at production resources.
- Deployed-commit check: `aws amplify list-jobs` / the Amplify API.

## Platform: generic

- Assume branch-build semantics when the platform supports them: the exact candidate run branch for internal verification and `main` for production. Otherwise record `mode: manual` with the separately authorized deploy command and read-only check.
- Record what is known; never invent a platform capability the project has not configured.

## Release And Recovery Readiness

Before an applicable release, record migration ordering and compatibility, backup/restore or forward-fix strategy, deploy command, health and user-flow probes, monitoring owner, alert destination, cost thresholds and rollback trigger in the existing deployment record. Use approved environments and exact action grants. A rollback of code is insufficient if data or an external side effect cannot roll back; name the safe forward-fix and decision owner. Exercise feasible recovery in the isolated candidate environment and retain its result. Record genuine non-applicability instead of generating empty plans for a small local-only project.

After release, read back the actual build/artifact and verify health and required smoke against it. Report implementation delivery, release availability, operational activation and measured product outcomes separately. Green CI, a started deployment or successful upload proves none of the later stages.

## Post-Deploy Verification (read-only)

Verify the candidate environment before promotion when it applies, then verify production after the separately authorized `main` promotion:

1. The expected environment URL resolves — the isolated non-production URL for the exact candidate SHA, then the production URL for the promoted `main` head.
2. The deployed commit equals the expected head, read from the platform API/CLI, store/build API, response headers, or signed installer metadata, and recorded bound to that SHA. A mismatch or a stale build is a finding for the user or a new mission, never a redeploy order.
3. For a hosted-browser UI candidate, the production check may re-capture parity against the approved design reference at the production URL (`scripts/parity_capture.py --out docs/goal/evidence/production`) and records the pairs and board as production evidence; a visual mismatch is a finding, never a silent acceptance. Browser-extension, native, and desktop targets do not have URL parity: use their installed extension/device/app UI-test or labeled manual capture mechanism and bind the result to the exact artifact/build and Git SHA.
4. Verify required human configuration through non-secret evidence: platform metadata that exposes names but not values, plus behavior-level checks such as a completed auth redirect or integration smoke. Never print or retrieve a secret value. Keep an unverified requirement `pending` even when the build itself succeeded.
5. Record evidence with the exact target, stage/provider/channel, environment or channel, URL or artifact/build identity, deployed SHA, expected SHA, availability proof, check time, and retained observation — the same evidence discipline as any other gate. Hosted web/API targets prove route or API smoke. Native `ios`, `android`, `macos`, and `windows` targets prove install/download or exact artifact/build identity plus their smoke; URL parity is not native availability. Reconcile the Required Secrets and Variables and External Console Setup statuses with what was actually verified. `scripts/check_deployment.py --deployment <path>` structurally validates the legacy record read-only; `scripts/check_deployment.py --deployment <path> --architecture docs/product/architecture.md` also validates the exact per-target architecture join without ever running the recorded command. A `deployment/2` record adds source provenance; `--require-source-provenance` requires architecture plus `--repo-root` and `--expected-repository`, and `--candidate-ref` resolves candidate/1 development proof.
6. Report the observed non-production or production URL with its exact SHA and every remaining human action. When the build has not finished or the URL cannot be observed, leave the record pending; never construct or guess a URL.

Writing the observed result into the tracked deployment record does not authorize or require another push. A later commit of that operational update is a new change under the ordinary branch, verification, commit, and push boundaries; its status row describes the deployment it observed and never pretends to be a self-reference to the document commit.

## Product Activation Handoff

Deployment and activation are separate. The RUN closes local-only; archive-candidate publication, `main` promotion, and deployment verification follow under separate action-time authorization. The sibling `product-activation` skill owns explicitly requested external setup and `docs/ACTIVATION.md`; it never reopens the archived PLAN/RUN.

After RUN close, provide one bounded handoff when the product has deployable surfaces:

- the exact delivered and, when available, deployed full Git SHA;
- stable release target IDs, environments or channels, and observed URLs;
- deployment-check evidence and every unresolved environment mismatch;
- implemented analytics, consent, crash, store, email, payment, webhook, monitoring, or other activation hooks; and
- every pending Required Secrets and Variables or External Console Setup row, naming configuration only and never a value.

When requested, `product-activation` may enter `preparation` at a fixed implementation SHA and artifact identity before deployment, including separately authorized DNS, auth, or payment prerequisites. Keep target readiness in preparation until required branch promotion and exact deployment verification complete. Rebind and reverify any release identity changed by promotion. No predeployment setup proves activation readiness or a verified measurement handoff. Otherwise report the exact handoff and suggest the explicit next invocation. Tool availability, a signed-in browser, a deployment PASS, and RUN authorization do not authorize an external console mutation. Product Activation probes connector/API/CLI/Browser/Computer Use routes separately, binds approval to each exact target and action, and writes `verified` only after independent read-back and behavior evidence.

An absent `docs/ACTIVATION.md` remains valid for legacy or non-applicable products. Product Definition may create the first seed when the path is absent; Product Activation bootstraps it when needed. Neither absence nor a pending activation task keeps the delivery RUN open.

## Recording The Model In A Repository

Two records carry the deployment model. `docs/DEPLOYMENT.md`, seeded during PRD creation and reconciled before promotion, is the detailed instance: candidate/protected-branch roles, platform record, name-only configuration inventory, external-console tasks, internal-test evidence, and environment status. The seeded `AGENTS.md` routes to the same candidate-Preview/main governance. Keep both filled from live evidence; an unfilled record means the model is unknown. `docs/ACTIVATION.md` remains separate.

## Moving Between Platforms

Migrating — Cloudflare to AWS or Vercel, or anywhere else — changes the record and platform section, not the flow: map the exact candidate run branch/SHA to isolated non-production and `main` to production, update the deployment record, and re-verify both exact SHAs. No promotion or authorization rule changes with the platform.
