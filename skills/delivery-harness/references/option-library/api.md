# API 選型參考：REST/OpenAPI、GraphQL、gRPC、tRPC、Webhook/事件、SSE/WebSocket

狀態：Reference only · 核對日期 2026-09-25。本文件是研究參考，不是技術棧決策、安裝授權、採購授權或驗收授權。專案必須先在既有 PRD、API 契約、Architecture 與 Integration 文件中記錄採納範圍，再進入實作。所有參考為建議性質；不因本文存在而自動導入任何 SDK、工具或服務。

## 適用範圍與 PRD 提問

本參考覆蓋 HTTP 資源介面、型別化 RPC、查詢導向 API、伺服器對伺服器通知、單向串流與雙向連線。它不取代需求定義，也不把某一項協定視為預設答案。

沿用既有 reference baseline `api.md` 中對應 PRD 的追問，仍需按實際 PRD 覆核：誰呼叫 API？是否公開？同步還是非同步？是否有串流？使用者與租戶如何識別？哪些動作有副作用？哪些呼叫可重試？哪些錯誤要讓使用者看懂？

## 主要比對矩陣

| 選項 | 適合 | 避免/重訪條件 | 架構與整合義務 | 營運與成本面 | 遷移與鎖定 |
| --- | --- | --- | --- | --- | --- |
| REST/HTTP + OpenAPI | 資源導向產品 API、多客戶端、外部整合、SDK 或文件需求強的場景 | 若資料讀取形狀高度分歧、或內部 TypeScript 前後端已由同團隊掌控，應重新比較查詢/型別 RPC；若團隊只想靠「最新版」解決問題，先停下 | 記錄 request/response schema、錯誤語意、認證授權、分頁、版本、限流、逾時、冪等鍵；OpenAPI 為機器可讀描述，不應被手改副本取代 | 版本治理、棄用公告、相容性測試、SDK 重生成、閘道與日誌是主要長期成本 | OpenAPI 本身語言中立；鎖定主要來自生成工具鏈與 API 版本政策 |
| GraphQL | 多端需要彈性組合讀取、畫面資料形狀差異大、有明確查詢治理能力 | 若查詢成本、深度限制、快取、欄位授權尚未設計，不建議公開；若僅是簡單 CRUD，會增加治理負擔 | schema 為契約；要設計 resolver 授權、查詢複雜度限制、持久化查詢、錯誤與分頁語意 | resolver 數量、N+1、快取命中率與查詢分析會直接影響營運負擔 | schema 與客戶端快取/生成器形成耦合；變更需搭配相容性檢查 |
| gRPC | 服務間高效通訊、強 schema、跨語言團隊、內部可信邊界 | 不應只因「效能高」套用到瀏覽器或公開整合；若外部需要簡單 HTTP/JSON 除錯體驗，先驗證代理與 SDK | 定義 proto 與版本策略、錯誤映射、壓縮、逾時、重試、認證、串流與部分失敗語意 | proto 變更治理、多語言套件發佈、連線健康檢查與觀測是主要成本 | proto 契約與生成碼耦合；升級需兼顧新舊服務 |
| tRPC | TypeScript 全端、內部同團隊、型別即契約可加速迭代 | 若供跨語言合作方使用，單靠 TypeScript 型別無法提供其所需契約；若介面要長期穩定，先補外部 schema | 前後端共享程序契約；仍要記錄授權、輸入驗證、錯誤、限流、冪等與部署邊界 | 開發速度高，但缺開放 schema 時會增加外部整合與跨語言成本 | 共享 TypeScript 型別與語言耦合較強；tRPC 的型別推導不要求程式碼生成；對外遷移需重訂契約 |
| Webhook/事件通知 | 長任務完成、外部系統主動通知、非同步工作流 | 若呼叫方需要即時同步答案，不應用通知代替回應；若缺少重送、簽章、去重與補償，不建議進生產 | 設定事件 envelope、版本、時間、簽章、端點憑證、至少一次語意、順序與補償；接收端要回應與處理分離 | 重送風暴、死信、時序、監控與金鑰輪替是長期成本 | 事件 schema 是外部契約；刪欄位或改語意需要版本與遷移 |
| SSE | 伺服器到瀏覽器的單向進度、通知或文字串流 | 若需要客戶端高頻上行或複雜雙向控制，改評估 WebSocket；若僅是簡單輪詢，不必增加常駐連線 | 記錄連線恢復、斷線、最後事件、取消、授權與代理逾時 | 連線數、代理緩衝、重連頻率與背壓會影響成本 | 依賴瀏覽器/代理行為；後端可替換但事件語意需穩定 |
| WebSocket | 協作、聊天、即時控制、高頻雙向狀態同步 | 若只是伺服器單向更新，SSE 可能較簡單；若無法處理重連、狀態恢復與權限變更，不建議公開 | 定義訊息類型、版本、心跳、斷線恢復、房間/頻道授權、背壓與可觀測性 | 有狀態連線、水平擴展、廣播層與連線維護成本較高 | 訊息協定與客戶端耦合；替換伺服器時需保留握手與恢復語意 |

## 來源事實與研究判斷

來源事實：本次讀取 OpenAPI 頁面顯示 v3.2.1；OpenAPI 描述可支援文件、客戶端/伺服器程式碼生成與測試工具，且描述可用 JSON 或 YAML 表示。見 [OpenAPI Specification](https://spec.openapis.org/oas/latest.html)。這些僅是能力描述，不代表本專案應升級到該版本。

補查結果：GraphQL 文件描述 schema 與 resolver；gRPC 文件描述 proto 與跨語言生成的 client/server；tRPC 以 TypeScript 推導提供型別；MDN 說明 SSE 為單向串流。矩陣中的適配與治理建議是整理判斷。採納前仍需以 [GraphQL Learn](https://graphql.org/learn/)、[gRPC Introduction](https://grpc.io/docs/what-is-grpc/introduction/)、[tRPC Docs](https://trpc.io/docs/)、[MDN Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events)、[MDN WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) 覆核版本、SDK、框架與部署支援。不得只憑本表宣稱相容性或供應商優勢。

安全設計可作為跨選項方法，不綁品牌：以最小權限、租戶範圍、短期憑證、簽章驗證、輸入驗證、限流與稽核追溯為共同義務。介面選型不能抵銷這些控制。

## 三個條件式情境示例

1. 若產品要對外部合作方提供穩定資源 API，並且需要文件、SDK 與相容性檢查，可優先評估 REST/HTTP + OpenAPI；前提是實際 PRD 確認公開邊界、版本與錯誤契約。這不是所有產品的預設。
2. 若 TypeScript 前後端屬於同一產品團隊、介面只供自家 Web 客戶端使用，且部署邊界單純，可評估 tRPC；若使用原生 Swift/Kotlin 客戶端、跨語言合作方或公開介面，另比較公開 schema；TypeScript 的 React Native 客戶端仍可評估 tRPC，不因平台名稱直接排除。
3. 若流程包含付款回呼、報表生成、大量匯入或第三方非同步通知，可評估 Webhook/事件契約；必須先接受至少一次、可能亂序與需要補償的現實，不把通知當成同步回應。

## 失敗與核對清單

- 契約：成功、無效輸入、無權限、重複請求、逾時、限流、取消與部分完成是否有可測試定義？
- 版本：舊客戶端在升級後如何繼續可用？欄位新增、刪除、語意變更與棄用流程是否已記錄？
- 認證授權：每一個操作、欄位、事件與連線是否都有主體、範圍與審計？
- 非同步：重送、亂序、死信、冪等、補償與查詢進度是否可運作？
- 串流：斷線、恢復、背壓、取消、代理逾時與部分輸出是否可驗證？
- 相容性：框架版本、Runtime、SDK、OpenAPI 工具、GraphQL/gRPC 生成器、tRPC 型別與 adapter、瀏覽器與代理支援是否逐項核對？
