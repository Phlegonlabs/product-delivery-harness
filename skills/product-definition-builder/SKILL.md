# Product Definition Builder

## Installed Commands

Resolve `<product-definition-builder-skill-root>` to the absolute directory containing this installed SKILL.md. Resolve sibling skill roots from the same installation (normally `~/.agents/skills/`). Quote script paths, keep the working directory and `--repo-root` at the target project, and never assume that project contains `skills/`. In references, `skills/<name>/scripts/`, `<name>/scripts/`, and bare `scripts/` are logical installed-skill paths: expand them to the observed absolute skill root before execution. Repository maintenance and CI commands still run from this source repository.

## Overview

At every invocation, apply `../delivery-harness/references/document-sync-contract.md`. For accepted enhancement delivery, use `../delivery-harness/references/bounded-enhancement.md`: preserve the current PRD and IDs, reuse decisions already made, and avoid repeated approval for same-scope implementation repairs. A genuinely changed product decision is a next-round contract gap, not permission to forge approval.

For a UI enhancement, hand off the added/changed UI IDs and necessary entry or return paths, with all other surfaces explicitly preserved. Follow `../ui-design-builder/references/enhancement-recommendations.md`'s Incremental UI Scope for the downstream boundary; do not request a fresh all-screen design package or reset unaffected approvals. Select the Epic or small-fix record before implementation using the shared bounded-enhancement rule.

Before approval, define test personas (role, tenant, account/data state), applicable Web/native/agent journeys, observable success and denial/no-side-effect assertions, and mock versus real-sandbox obligations in the existing TEST rows and architecture testing section. Record non-applicability rather than inventing login for a headless or unauthenticated product. The downstream Harness freezes the executable matrix and owns fixtures and evidence through `../delivery-harness/references/delivery-acceptance-contract.md`; this skill creates no accounts or evidence register.

Use this skill to turn a product idea into a decision-ready package, not an agent-selected implementation guess. Define product scope, journeys, UI surface responsibilities, routes, actions, states, data, trust, and security boundaries, acceptance signals, implementation architecture, release targets, and technology constraints. Draft and reconcile `PRD.md`, `architecture.md`, and `stack-decisions.md`; present coherent frontend, backend/data/auth, mobile/desktop, AI, deployment, and commercial technology options; then obtain an explicit Stack Decision Checkpoint and Product Definition Approval. Stop there. A later explicit UI request invokes `ui-design-builder`; a later implementation request invokes `delivery-harness` against approved inputs.

## Workflow

1. Read `references/interview-guide.md` before asking discovery questions.
2. Read `references/artifact-lifecycle.md`'s Detect Enhancement Mode section, then check whether `docs/product/PRD.md`, or another Markdown document whose title or content clearly describes the same product, already exists. Check `docs/product/.prd-staging/` in the same step. If a matching package exists, enhance it: read `PRD.md`, `architecture.md`, `stack-decisions.md`, `market-research.md`, `research-assessment.md`, and every retained `docs/product/outcomes/*.md` record in full. Read current `docs/design/ui-design.md`, wireframe, and design-system files only to identify downstream impact; do not carry or rewrite them here. Read `docs/ACTIVATION.md` for operational context without overwriting it. Preserve unaffected content, decisions, and trace IDs; never restart from a blank package.
3. Conduct exactly three bounded free-text turns from `references/interview-guide.md` unless the user explicitly authorizes assumptions: **Product and users**; **Workflows, data, and rules**; then **Delivery, success, and risk**. Ask one segment per turn, wait for its reply, dynamically omit answered prompts, and do not call `AskUserQuestion` during any free-text segment. Capture product, workflow, data/trust, security, AI/automation, delivery, measurement, cost, licensing, and ownership constraints. In enhancement mode, record the complete Enhancement Impact Record first, including the existing `none` / `structure` / `style` / `both` UI classification, then ask only what the delta changes; stale product, stack, data, commercial, release, wireframe, or visual contracts never publish silently.
4. Run the research-first assessment before any closed-set decision. First perform its Research Disclosure Check and use only a public-safe query summary; never send confidential product inputs, personal data, customer names, internal metrics, secrets, or contract terms to a search provider. Skip with the recorded reason when the user declines, no web tool exists, the package is trivial, or useful research cannot be sanitized. Include the applicable feature baseline, differentiation, pricing/business-model baseline, and category benchmarks as research inputs useful before drafting; do not turn them into speculative final requirements. The researcher recommends and the human owner decides `go | clarify | stop` as specified in `references/research-first-guide.md`; stage `research-assessment.md` with stable `RA-*` findings when produced. In enhancement mode, skip this step entirely and research only the delta after drafting.
5. After all applicable free-text segments have replies and the final coverage check has no material gap, use their aggregate answers to skip resolved or inapplicable decisions, then issue the first `AskUserQuestion` call, sized to the question tool's actual per-call question and option limits, resolving the remaining closed-set decisions marked `(AskUserQuestion)` in `references/interview-guide.md` that depend on no other answer: product archetype and validation depth. Do not issue this call in the same turn as any free-text segment or targeted free-text follow-up. Keep deployment and UI design preferences out of this call. UI layout, style, motion, and media choices belong to the later `ui-design-builder` intake. In enhancement mode, only re-ask a closed-set decision the new idea actually reopens; otherwise keep the existing package's answer.
6. For a UI-bearing product, capture only product-level UI obligations: human decision owner, required surfaces, route and state behavior, content responsibilities, validation depth, accessibility, localization, responsive destinations, confirmation/recovery rules, and exact or bounded copy. Bind each surface to its exact architecture release surface, surface class, derived capture mode, and its own responsive set; a hybrid package never flattens web, extension, native, and desktop surfaces into one global capture contract. Defer information density, layout preference, visual character, imagery, iconography, motion treatment, media placeholders, wireframes, themes, and tokens to `ui-design-builder`. Product Definition may record hard brand or platform constraints, but it never turns them into a visual direction.
7. Issue the next `AskUserQuestion` call or calls, each sized to the question tool's actual per-call limit, for every applicable closed-set decision that depends on step 5's archetype answer, marked `(AskUserQuestion)` in `references/interview-guide.md`:
    - an evidence-narrowed deployment-platform choice for hosted surfaces, including an explicit recommendation option and the tool's built-in Other;
    - target operating systems for mobile/desktop, native versus cross-platform strategy after those targets are known, and browser targets for extensions;
    - database category and auth strategy, each including an evidence-backed recommendation choice when the owner does not already have one;
    - the monetization model when the product has commercial intent or an unresolved pricing strategy, and the partner channel when outside promoters or sellers may contribute revenue. These decisions select a model, not a provider; apply `references/monetization-and-partner-channel-guide.md` afterward to recommend RevenueCat or another current fit.
    - the Stack Decision Mode: owner review of one coherent recommendation plus alternatives, layer-by-layer owner selection, or explicit delegation to this skill. Delegation never skips Product Definition Approval.

    Skip resolved or inapplicable questions, but do not drop an applicable decision to fit an invented call budget. Do not silently select a provider, framework, component system, CSS approach, database/auth implementation, mobile framework, commercial provider, or browser target. Local persistence/auth may require backend analysis without a hosted deployment question; skip database/auth questions only when the product provably has no backend, persistence, or auth.
8. Classify the product as web app, mobile app, desktop app, browser extension, internal tool, automation or agent workflow, API/backend service, or hybrid. Record target destinations separately from implementation strategy: operating systems or browsers first, then native/cross-platform, framework, and toolchain in the later Stack Decision Checkpoint. Record public marketing/SEO scope, Data and Trust, Security Requirements, and AI and Automation Gate applicability.
9. After discovery, read `references/output-contract.md`, `references/architecture-playbook.md`, the agent work-graph contract in `references/dynamic-workflow.md`, `references/research-first-guide.md`, and `references/market-research-guide.md`, plus the rest of `references/artifact-lifecycle.md`. When monetization or partner distribution may apply, also read `references/monetization-and-partner-channel-guide.md`. For a web app, internal tool, public website, browser extension, or hybrid with a browser frontend, also read `references/frontend-stack-selection.md`. For any product with a backend, persistent data, or auth requirement — most products other than a purely static content site — also read `references/backend-stack-selection.md`. For a mobile-app or desktop-app surface, also read `references/mobile-stack-selection.md`; its desktop platform patterns live in `references/architecture-playbook.md`. For an AI or automation surface, also read `references/agentic-runtime-selection.md`.
10. Before drafting, inventory earlier documents related to the same product as described in `references/artifact-lifecycle.md`. Do not move anything yet. In enhancement mode, this still includes the existing package identified in step 2 — it will be archived for history once the enhanced draft is published, even though its content already carried forward into that draft.
11. For a non-trivial new package, run the bounded read-only agent work graph only under its explicit multi-agent and `builder_readonly` gates. Use the current host's native sibling-agent surface: parent-dispatched subagents in Codex or a generic host, the installed read-only roles in Pi, or `assets/templates/CLAUDE_PRD_WORKFLOW.template.js` through the Claude Code adapter. Freeze the interview, Stack Decision Mode, Data and Trust Gate input, Security Requirements Gate and Security scope, AI and Automation Gate input, release targets, and commercial models first. Every host runs the same role, input, result, and parent-ownership contract. The graph may return candidate Markdown and coherent technology options; it cannot ask the owner, mark a new choice `Approved`, pass either approval checkpoint, or authorize publication. Skip it in enhancement mode and perform the same roles sequentially against the existing package.
12. Draft or repair the core Markdown package using the discovery decisions and available research-first evidence, in the staging location defined by `references/artifact-lifecycle.md`:
    - `PRD.md`
    - `architecture.md`
    - `stack-decisions.md`
    - Every PRD records Data and Trust and AI and Automation gates as `required`, `not_required`, or `blocked`, with a human owner and reason. Required gates carry their concrete product, architecture, technology, UI, and test obligations; a blocked gate prevents Product Definition Approval.
    - Every PRD records the Security Requirements Gate and Security scope from `references/output-contract.md`. Executable software is security-required even when it has no personal data or authentication. Legacy packages may be read as history, but current Product Definition Approval requires the section and a new explicit owner decision.
    - For every UI-bearing package, finish the complete UI Surface Contract and the product-level accessibility, responsive, copy, and recovery requirements. Motion treatment, media placeholders, wireframes, page theme, and design tokens are downstream UI design decisions.
    - In every package, record the Monetization Infrastructure Gate and Partner Channel Gate in `PRD.md`, including explicit `not_required` reasons. When either applies, carry its separately selected layers into `architecture.md` and `stack-decisions.md`; do not collapse billing, entitlement, merchant-of-record, affiliate, referral, and reseller responsibilities into one vendor label.
    - Do not prepare wireframe data or create `wireframes.html`. Record `UI design: pending explicit ui-design-builder request` for a UI-bearing product.
    - Do not invoke `ui-design-builder` or `design-system-compiler` automatically. UI work remains a later explicit phase.
    - For a product with no UI surface — a headless API or backend service, or an automation whose only surfaces are notifications it sends into someone else's UI — record the UI-design handoff as `not_required` and publish no placeholder UI or design files.
    - Draft `DEPLOYMENT.md` from `../delivery-harness/assets/templates/DEPLOYMENT.template.md` when the package has a deployable surface: record the platform chosen in the deployment decision; seed the Required Secrets and Variables inventory with every exact name already established by the product or architecture; record known auth callbacks, allowed origins, webhooks, domains, roles, and other provider-side work in External Console Setup; and leave their human-owned statuses plus the remaining Human Setup Checklist for the owner. Record names and destinations only, never values. Do not invent implementation-owned key names or URLs: leave them visibly unresolved for `delivery-harness` to reconcile from the finished code before the first deployable push. A purely local product records `manual` mode or skips the file with a note in `stack-decisions.md`. Publish it to `docs/DEPLOYMENT.md` with the package.
    - When the package has any release target with an activation scope and `docs/ACTIVATION.md` does not already exist, resolve `../product-activation/assets/templates/ACTIVATION.template.md` and create one `ACTIVATION.md` seed. Fill the product, owner when known, `core`, every applicable surface profile (including `web`, `api / backend`, `ios`, `android`, `macos`, `windows`, `browser extension`, `cli/toolchain`, `agent/automation`, and `other_nonpublic` when the matrix requires them), and only those supported release target IDs. Include one Outcome Coverage row for every PRD metric and required `TEST-*` signal scoped to the complete supported target set, including hybrids; a concrete `n/a — reason` is allowed only when the architecture proves that no activation scope applies. Preserve each metric's source/method and owner. Leave implementation-owned actions, routes, accounts, queries, release SHAs, artifact/build identities, sources, and evidence visibly pending. Run `python "<product-activation-skill-root>/scripts/check_activation.py" --activation <staged ACTIVATION.md> --prd <staged PRD.md> --architecture <staged architecture.md> --deployment <staged DEPLOYMENT.md> --stack-decisions <staged stack-decisions.md> --repo-root <repository-root>` before publication so target/profile drift and unapproved package/deployment inputs fail closed. Publish the seed to `docs/ACTIVATION.md`. If the live path already exists, preserve it byte-for-byte, stage no replacement, and record in `DOCUMENTS.md` that `product-activation` must reconcile it after delivery.
    - Draft `DOCUMENTS.md` from `../delivery-harness/assets/templates/DOCUMENTS.template.md` as the manifest of every flow document, publish it to `docs/DOCUMENTS.md`, and fill the status column for each document this package creates; keep it current through publish and archive.

    A product is UI-bearing when a person interacts with a surface this product ships. A native mobile or desktop app is UI-bearing without a browser frontend; an internal tool with one admin screen is UI-bearing; a service whose only output is an API response, a webhook, or a message posted into a third-party client is not.

    At this point the core artifacts are candidates, not approved implementation authority.

    In enhancement mode, preserve unaffected content and stable IDs, mint new TEST IDs only for newly uncovered obligations, and apply the complete Enhancement Impact Record. Every changed product, UI, data, stack, trust/AI, security, commercial, or release row names the artifacts and owner gates that must refresh. No stale decision remains effective by omission.
13. Run the post-draft market-research reconciliation now, before any stack or Product Definition approval. Apply `references/market-research-guide.md`, including its Research Disclosure Check. Delegate it to the authorized agent work-graph lane, a single read-only subagent only when the parent has a separate explicit subagent/delegation authorization, or the parent inline when no delegation authorization is present. Read the candidate PRD plus `research-assessment.md` when the pre-draft pass ran. The pass is a reconciliation: carry valid `RA-*` evidence forward, research only newly raised, stale, or `UNVALIDATED` gaps, and compare the candidate against both evidence sets. Produce evidence-based Platform Optimization Recommendations with exact affected PRD sections/IDs and expected-benefit hypotheses, then present the complete candidate and every recommendation to the owner using verified absolute Markdown links to the actual staged PRD and `market-research.md`. Verify the links before requesting a choice. Record each proposal as `pending | accepted | revise | deferred | rejected`, and wait for an explicit owner choice; `pending` is not a decision. A `revise` choice changes the proposal, then returns it for explicit acceptance before changing the PRD. An evidence-backed no-recommendation result needs no proposal-choice round. Apply only an owner-recorded accepted proposal, including its affected acceptance criteria, metrics, architecture, and stack; a deferred or rejected proposal does not change the candidate and cannot erase an approval-blocking gap. Never infer approval from silence, automatically accept a proposal, or treat a recommendation as implementation authority. Carry in-scope findings, including evidence that strengthens or contradicts a `stack-decisions.md` layer row or alternative, into the later checkpoint without accepting a stack choice. Every factual claim carries publisher, URL, and retrieval date or is `UNVALIDATED`; never invent a competitor, price, or market figure, and never claim a measured benefit. A scope-changing finding becomes a blocking Open Question for the owner. Record a safe skip or blocked result explicitly.
14. Run the Stack Decision Checkpoint. For each applicable frontend, backend/data, mobile/desktop, toolchain, AI/automation, or commercial area that is not already `Required` or `Selected`, present two or three coherent bundles with every coupled layer, fit, tradeoffs, cost/license/data constraints, maintenance and operations owner, serious alternatives, and revisit triggers. Follow the recorded Stack Decision Mode. Mark an accepted new choice `Approved`; keep an unaccepted proposal `Recommended`; keep missing-evidence choices `Provisional`. After recording an accepted new bundle, derive its map for checkpoint review with `python "<product-definition-builder-skill-root>/scripts/render_stack_option_map.py" --stack-decisions <staged stack-decisions.md>`; it reads approved option rows and executable layer rows, writes the candidate map to stdout only, and cannot approve, rewrite, or bind a digest. If no new bundle is approved and every applicable layer remains `Selected` or `Required`, keep the existing `None` option-map case and skip this optional generator; no repeat approval is needed. Record the machine-anchored checkpoint, owner, date, approved areas, delegation source, and open areas. `Recommended` or `Provisional` blocks the checkpoint and implementation.
15. Run Product Definition Approval for every product, including headless products. Send one proactive user-visible review response containing verified absolute Markdown links to the complete actual current PRD, architecture, stack decisions, every produced market/research artifact, and its Platform Optimization Recommendations with their explicit decision statuses; when an operational seed applies, include the staged Deployment, Documents, and Activation paths. Use staging paths while the candidate remains staged. State in one short paragraph what is ready and the review focus, then ask explicitly for Product Definition Approval. Opening a file or browser panel is convenience only and never replaces that response or those links. If a required artifact or link target cannot be verified or opened, report that blocker instead of asking for approval. Wait for the owner's explicit decision before continuing; presenting the package is not approval. A substantive change renews this presentation and reopens the gate. After the decision, record the machine-anchored decision and package revision. Approval requires an approved stack checkpoint, no blocking question/gate, and resolved research. Then run the core package checker with `--repo-root <repository-root> --require-filled --require-approved`.

    The checker derives one release-surface applicability matrix from `architecture.md`: hosted web and extensions require frontend layers; native mobile/desktop requires mobile or desktop layers; API, worker, job, webhook, and realtime targets require backend/data layers; agents add AI/automation; CLI and other non-public artifacts require an explicit toolchain decision. Product, architecture, and stack identities must match. When an approval carries a `sha256:` package or checkpoint digest, it is calculated over the canonical approved bytes with its own marker block excluded, and the digest is checked before execution.
16. After step 15 passes, create no UI artifact. For a UI-bearing product, prepare the approved Product Definition paths for a later explicit `ui-design-builder` request covering UI intake, motion/media intent, wireframes, Style Integration, HiFi review, scoring, and visual approval. Continue only with the core package validation and publication steps below. A headless product records the UI handoff as not required.
17. Produce `implementation-plan.md` only when the user explicitly asks for delivery sequencing. Reuse canonical `TEST-*` and release-target IDs; it must not create anonymous replacements or duplicate TEST identities.
18. A later UI request belongs to `ui-design-builder`, not this skill. Do not create wireframes, select a page theme, invoke frontend-design, generate media, review HiFi, score UI, or compile design tokens from Product Definition Builder.
19. Run the `references/output-contract.md` checklist and the core package checker with `--repo-root`. Resolve every required lane and material verifier finding. The checker requires substantive core sections, complete UI surface fields, stable gate-area test traces, closed Release Target source policies, and live repository path/revision evidence for every `Selected` stack row. An approved core package contains only `Required`, `Selected`, or `Approved` executable stack rows; `Recommended`, `Provisional`, or a blocked checkpoint remains staged and cannot enter Harness.
20. After validation, show exact publish paths, overwrite targets, and archive moves. This Publication Authorization Gate is separate from Product Definition Approval. If those exact mutations are not already authorized, ask one explicit yes/no publication question. On approval, execute the approved publish and archive moves in the same run; otherwise leave the approved package staged.
21. In the same authorized publish move set, run `python "<delivery-harness-skill-root>/scripts/configure_project_context.py" --root <target-root> --check`. Create only missing files, using `PROJECT_AGENTS.template.md` for `AGENTS.md` and the distinct `PROJECT_CLAUDE.template.md` for `CLAUDE.md`; never copy one template to both files or reopen an established context file. List locally installed binding candidates, confirm each binding with the owner in one `AskUserQuestion`, and leave any slot without an installed owner-confirmed candidate unresolved; it blocks that dependent stage and never falls back to a bundled default. Record confirmed SHA-256 pins and finish with `--check --require-resolved --stage product-definition`. Future slots may remain `pending` in both binding and pin cells; they block their dependent stage, not Product Definition publication. Before a later stage, run `check_skill_bindings.py --stage <stage>` against installed trees. Omitted stage checks every slot; `backend` is only for a scope with no UI work, proven by the approved product contract.
22. Report published canonical absolute Markdown links after publication; if publication is deferred, report the actual staging links instead. Include the complete package, applicable operational/context files, archived paths, and Product Definition and Stack Decision approval status.
23. After reporting a completed package, stop. State that UI design and implementation are separate optional phases; do not invoke either. A later UI request uses `ui-design-builder`; a later Harness request consumes the approved Product Definition plus any separately approved UI sources.
24. When the owner asks for an outcome review after deployment, read every retained `docs/product/outcomes/*.md` input and `docs/ACTIVATION.md` in full. After the real measurement window closes, compare actuals with every metric's baseline, target/guardrail, window, source/method, owner, and required `TEST-*` signal; never leave a run open waiting for adoption. For every reviewed target, require matching verified `MS-*` sources and exact numeric window duration/start-after-deployment checks. Write a new dated release-set record or prove an exact prior digest with `--prior-outcome`; lifecycle schema 2 carries a typed `## Verdict History` table whose prior rows remain byte-identical and ordered and whose final row is derived from the immediately prior authoritative `## Verdict` section. A multi-target product uses one ordered target-review set, binds each signal only to the release targets listed by Activation Outcome Coverage, and derives one deterministic aggregate verdict. Record exactly one `no_change`, `enhancement`, or `incident` verdict and route it to the required enhancement or incident record.

## Interview Rules

- When the owner has no technology preference, use the recommendation-review path: one coherent product-fit bundle plus one or two serious alternatives. Explain cost assumptions, maintenance, compatibility and change consequences in plain language. Reuse an explicit recommendation request for unresolved platform/database/auth questions; accept the resulting choices at the existing Stack Decision Checkpoint. No preference never means approval or delegated final selection.

- Run discovery in two phases. First, ask the three bounded free-text segments in order: **Product and users**; **Workflows, data, and rules**; **Delivery, success, and risk**. Ask one segment per turn and wait for its reply. Dynamically omit already answered or inapplicable prompts from later segments, but do not merge multiple planned segments into one long message. After segment 3, compare the aggregate answers with `references/interview-guide.md`'s completeness criteria. If a material item is still missing and assumptions are not authorized, ask one compact targeted free-text follow-up containing only those gaps. Only after all applicable segments and that optional follow-up are complete may the closed `AskUserQuestion` batches begin. Use the tool's built-in Other option instead of inventing a separate free-text fallback. Do not run a fixed design-reference visual-style questionnaire here.
- Step 7's questions always come after the archetype and validation-depth call. Resolve target operating systems/browsers before native-versus-cross-platform or framework choices, and record how the owner wants technology recommendations decided. Batch to the question tool's actual capacity without dropping applicable decisions.
- Do not ask questions already answered by the user's prompt.
- Before drafting, finish release discovery with stable surface IDs and development/production target IDs. Keep `surface` separate from stage-specific `provider`. The release-source policy is closed: development builds from the exact candidate run branch/SHA, production builds from `refs/heads/main` only after candidate verification and separately authorized fast-forward, and both initial delivery and enhancements start from observed remote `main`. Do not record or accept a tag or alternative production ref. Also close artifact/signing, channel, release gates, availability, rollout, and recovery. These are not extra closed-set `AskUserQuestion` calls.
- Mark optional questions clearly when they would improve quality but should not block progress.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.
- If the user gives conflicting requirements, resolve them before drafting or call out the conflict in `open questions`.
- Treat builder preference as a direction input, not as proof that users find the result usable. When it conflicts with user evidence or an accessibility requirement, record the conflict and validation need instead of silently following preference.
- In enhancement mode (Workflow step 2), never repeat questions the existing package already answers. Scope the free-text message and every `AskUserQuestion` call to what the new idea adds, changes, or leaves genuinely unresolved.

## Output Standards

- Write each artifact for the primary reader named in `references/output-contract.md`'s "How To Read This Package", and respect its length budget. Completeness is not the only bar — a document nobody finishes reading has not delivered its requirements.
- Put meaning before bookkeeping in every artifact. Open with what a human needs to understand the product; close with the ID matrices and decision records that machines, auditors, and downstream skills need. Never open a document with a trace table.
- Keep tables at seven columns or fewer, except the mandated hosted environment contract in `architecture.md`, whose columns are all release-critical. When a row needs more fields than that, write one block per item instead of widening the table.
- Prefer specific, buildable requirements over vague product language.
- Keep the current PRD package directly under `docs/product/`; reserve `docs/product/archived/` for superseded documents only.
- Tie every major requirement to a user need, workflow, metric, or constraint.
- Mint stable upstream trace IDs: `PRD-*` for product requirements, `ARCH-*` for architecture contracts, `UI-*` for UI surfaces, `UX-*` for usability requirements, `TEST-*` for test obligations, `MR-*` for market-research findings, and `RA-*` for research-first assessment findings. `design-system-compiler` owns `DS-*` and `DS-COMP-*`. Preserve every family across revisions and never reuse a retired ID for a different meaning.
- Keep market research evidence in `market-research.md` and conclusions in the artifact they affect. `PRD.md` cites the `MR-*` ID behind a statement; it does not restate the competitor table, the sources, or the retrieval dates. A market claim with no source is recorded `UNVALIDATED` with what was searched, never stated as fact and never invented.
- Keep Platform Optimization Recommendations in `market-research.md`: at most five useful, evidence-based proposals; explicit no-recommendation results; expected-benefit hypotheses; and an explicit owner decision before any candidate change. They never bypass Research Gate, Stack Decision Checkpoint, Product Definition Approval, or publication authorization.
- Keep `## Non-Functional Requirements` in every `PRD.md`, immediately after Functional Requirements. Use `PRD-*` IDs and record every applicable quality attribute with a scoped measure and target; record non-applicable categories explicitly as `N/A` with a reason. Vague words such as `fast`, `secure`, `reliable`, or `scalable` are invalid without measurable units, population or traffic shape, measurement window, and percentile where applicable.
- Keep `## Test Obligations` in every `PRD.md`, after Open Questions and before Product Definition decisions. Use the canonical columns from `references/output-contract.md`. Map every `Must` functional requirement and applicable NFR to a required `TEST-*` row with an observable signal.
- For every UI-bearing product, record the complete product-level UI Surface Contract and a pending or not-required `ui-design-builder` handoff. Do not record UI layout, visual style, motion/media treatment, wireframe approval, or design tokens as if Product Definition had decided them.
- Keep Copy Freeze ownership separate: the PRD `copy` status records the product-approved or draft copy responsibility. A later schema-4 wireframe approval owned by `ui-design-builder` may advance a PRD draft responsibility to approved exact copy without changing the PRD status; PRD `revision_requested` or `blocked` copy stops UI work.
- Include loading, empty, error, permission, and edge states when a UI or workflow has them.
- Treat `PRD.md` as canonical for product scope, UI behavior, routes, states, content responsibilities, and the exact responsive set. `ui-design-builder` owns the structural projection and visual decisions; PRD wins whenever they conflict.
- This skill owns Product Definition, including frontend and backend architecture, technology stacks, release targets, and the UI Surface Contract. It creates no wireframe, UI design contract, visual target, design-system pair, production component, Harness plan, mission map, PLAN/RUN state, or E2E evidence register.
- Keep assumptions explicit and avoid hiding unresolved decisions in confident prose.
- Every package records a Data and Trust Gate and AI and Automation Gate with human ownership. Required gates carry concrete architecture, stack, UI, and test obligations; `blocked` prevents Product Definition Approval.
- Every executable package records human-owned Security Requirements tied to existing `PRD-*` and required security `TEST-*` IDs. `not_required` is reserved for documentation-only packages with no executable or deployable surface; `blocked` prevents Product Definition Approval.

Every release target records a typed `Surface class` and `Public discoverability: yes|no`; downstream Deployment, Activation, Outcome, and SEO checks join those fields instead of inferring from names. Every assumption and open question records ownership and approval impact; an unresolved blocking question prevents approval.
- Architecture may remain technology-neutral while evidence is incomplete. For every applicable technology area, produce coherent bundles rather than disconnected menus, recommend one, and present it under the Stack Decision Mode. New accepted choices are `Approved`; adopted repository choices remain `Selected`; hard constraints are `Required`; `Recommended` and `Provisional` are non-executable draft states.
- For a browser frontend, separate deployment/runtime, rendering, language, package manager, framework, UI library, component foundation (including shadcn/ui when chosen), styling approach, build tool, routing/data, and testing. Do not collapse component source and CSS into one row.
- For every deployable web, API, mobile, desktop, or browser-extension surface, close a provider-neutral release-target contract before drafting. Record the complete expected deployable-surface inventory with stable surface IDs, then give every target a stable target ID, an explicit lowercase kebab-case surface suffix, a lowercase kebab-case release name, and a `development` or `production` stage. A production release name is the unqualified canonical `<product-slug>-<surface-suffix>` name and never ends in `-prod`; development uses that exact name plus `-dev`. Release names are globally unique across distinct surface IDs. Use `web`, `api`, and `extension` as the normal surface suffixes. Use another descriptive suffix such as `admin`, `worker`, `jobs`, `agent`, `webhook`, `realtime`, or `cli` only when that artifact is independently released. Native release artifacts may use `ios`, `android`, `macos`, or `windows`; their separately hosted backend remains `api`. Record stable `surface` separately from stage-specific `provider`, the source policy (the exact branch or ref each stage's release builds from), artifact kind, signing requirement, exact channel or track, submission/promotion/review or manual-approval path, actual availability signal, rollout, and rollback or forward-fix path. Require development and production targets for every expected surface; reject missing surfaces. Providers may differ by stage. Preserve surface and target IDs across revisions and never reuse an ID for a different meaning. An upload, submission, or approval is not availability by itself.
- For a deployable web or API target, resolve the deployment platform explicitly via the interview's platform `AskUserQuestion` step (see Workflow step 7, after the archetype is known) unless the user or current repository already names one. Never silently assume a platform, and do not invent platform-specific requirements for docs-only work. For store or signed-installer delivery, production availability means the approved artifact is actually installable or downloadable through the named channel and passes its smoke check. - For every product with a backend, persistence, or auth, compare coherent backend bundles and record the owner-approved result. Record service topology first — monolith versus named services, and monorepo versus polyrepo — then keep runtime/framework, database category/engine, auth strategy/provider, API style, jobs/queue, and storage separate.
- For a product with a backend, persistent data, or auth requirement, resolve the database category and auth strategy explicitly via the interview's backend/data `AskUserQuestion` step (see Workflow step 7) unless the user or current repository already names them. Do not silently pick a database category or auth strategy on the user's behalf. Never silently default to a specific database engine or auth vendor.

Record navigation/state, persistence, secure storage, sync, push/native modules, backend integration, distribution, and testing separately, with the same checkpoint approval discipline.
