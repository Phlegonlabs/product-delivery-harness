# Product Definition Builder

## Overview

Use this skill to turn a product idea into a decision-ready package, not an agent-selected implementation guess. Define routes, screen structure, flows, data and trust boundaries, acceptance signals, and implementation constraints; draft and reconcile `PRD.md`, `architecture.md`, and `stack-decisions.md`; show coherent technology options; obtain an explicit Stack Decision Checkpoint and Product Definition Approval; then, only for a UI-bearing product, project the approved revision into `wireframes.html` and obtain structural approval. Headless products still require Product Definition Approval. Continue into visual design or implementation only on a later explicit owner request.

## Workflow

1. Read `references/interview-guide.md` before asking discovery questions.
2. Read `references/artifact-lifecycle.md`'s Detect Enhancement Mode section, then check whether `docs/product/PRD.md`, or another Markdown document whose title or content clearly describes the same product, already exists in the repository. Check `docs/product/.prd-staging/` in the same step: a validated but unpublished package left by an earlier run is the newer baseline, and resuming, publishing, or discarding it is the user's call before this run drafts anything. If one does, treat this run as an **enhancement** of that package, not a new one: read the existing `PRD.md`, `architecture.md`, `stack-decisions.md`, and — when present — `wireframes.html`, `design-system.md`, `design-system.json`, `market-research.md`, `research-assessment.md`, and `outcome-review.md` in full before asking anything else. Also read an existing `docs/ACTIVATION.md` for current operational context, but never regenerate or overwrite it from enhancement mode. Carry forward the product package's content, decisions, and trace IDs unchanged, and scope every remaining step to only what the new request adds, changes, or removes. Never restart discovery from a blank slate or regenerate the whole package from scratch when an existing package for the same product is found.
3. Conduct exactly three bounded free-text turns from `references/interview-guide.md` unless the user explicitly authorizes assumptions: **Product and users**; **Workflows, data, and rules**; then **Delivery, success, and risk**. Ask one segment per turn, wait for its reply, dynamically omit answered prompts, and do not call `AskUserQuestion` during any free-text segment. Capture product, workflow, data/trust, AI/automation, delivery, measurement, cost, licensing, and ownership constraints. In enhancement mode, record the complete Enhancement Impact Record first, including the existing `none` / `structure` / `style` / `both` UI classification, then ask only what the delta changes; stale product, stack, data, commercial, release, wireframe, or visual contracts never publish silently.
4. Run the research-first assessment before any closed-set decision. First perform its Research Disclosure Check and use only a public-safe query summary; never send confidential product inputs, personal data, customer names, internal metrics, secrets, or contract terms to a search provider. Skip with the recorded reason when the user declines, no web tool exists, the package is trivial, or useful research cannot be sanitized. The researcher recommends and the human owner decides `go | clarify | stop` as specified in `references/research-first-guide.md`; stage `research-assessment.md` with stable `RA-*` findings when produced. In enhancement mode, skip this step entirely and research only the delta after drafting.
5. After all applicable free-text segments have replies and the final coverage check has no material gap, use their aggregate answers to skip resolved or inapplicable decisions, then issue the first `AskUserQuestion` call, sized to the question tool's actual per-call question and option limits, resolving the remaining closed-set decisions marked `(AskUserQuestion)` in `references/interview-guide.md` that depend on no other answer: product archetype and validation depth. Do not issue this call in the same turn as any free-text segment or targeted free-text follow-up. Keep the deployment platform out of this call. It only means something once the archetype is known, so step 7 carries it. Do not ask the user to choose from a fixed design-reference style catalog during discovery; the later UI Design Pass derives a product-specific direction from the approved wireframes. In enhancement mode, only re-ask a closed-set decision the new idea actually reopens; otherwise keep the existing package's answer.
6. For a UI-bearing product, capture a `Builder UX Direction Decision` before visual work. Resolve the builder to the human product/design decision owner or commissioning team. Use the minimum number of `AskUserQuestion` calls permitted by the tool's actual per-call limit for the closed dimensions — experience priority, guidance versus expert control, information density, preferred layout/interaction pattern, and motion direction — and capture confirmation/recovery behavior as free text, since it varies too much by action to enumerate further. Motion direction asks whether the product stays quiet with necessary functional feedback, uses expressive motion where justified, or delegates that recommendation to the AI. Validation depth is already answered by step 5's call; carry that answer forward instead of re-asking it. Mark every decision `selected`, `provisional`, or `assumed`. In enhancement mode, only revisit a dimension the new idea actually affects. The UI Design Pass and any later `design-system-compiler` compilation consume this decision and do not replace it with agent taste.
7. Issue the next `AskUserQuestion` call or calls, each sized to the question tool's actual per-call limit, for every applicable closed-set decision that depends on step 5's archetype answer, marked `(AskUserQuestion)` in `references/interview-guide.md`:
    - an evidence-narrowed deployment-platform choice for hosted surfaces, including an explicit recommendation option and the tool's built-in Other;
    - target operating systems for mobile/desktop, native versus cross-platform strategy after those targets are known, and browser targets for extensions;
    - database category and auth strategy, each including an evidence-backed recommendation choice when the owner does not already have one;
    - the monetization model when the product has commercial intent or an unresolved pricing strategy, and the partner channel when outside promoters or sellers may contribute revenue. These decisions select a model, not a provider; apply `references/monetization-and-partner-channel-guide.md` afterward to recommend RevenueCat or another current fit.
    - the Stack Decision Mode: owner review of one coherent recommendation plus alternatives, layer-by-layer owner selection, or explicit delegation to this skill. Delegation never skips Product Definition Approval.

    Skip resolved or inapplicable questions, but do not drop an applicable decision to fit an invented call budget. Do not silently select a provider, framework, component system, CSS approach, database/auth implementation, mobile framework, commercial provider, or browser target. Local persistence/auth may require backend analysis without a hosted deployment question; skip database/auth questions only when the product provably has no backend, persistence, or auth.
8. Classify the product as web app, mobile app, desktop app, browser extension, internal tool, automation or agent workflow, API/backend service, or hybrid. Record target destinations separately from implementation strategy: operating systems or browsers first, then native/cross-platform, framework, and toolchain in the later Stack Decision Checkpoint. Record public marketing/SEO scope, Data and Trust Gate applicability, and AI and Automation Gate applicability.
9. After discovery, read `references/output-contract.md`, `references/wireframe-guide.md`, `references/ui-design-pass.md`, `references/ui-grading-rubric.md`, `references/architecture-playbook.md`, `references/dynamic-workflow.md`, `references/research-first-guide.md`, and `references/market-research-guide.md`, plus the rest of `references/artifact-lifecycle.md`. When monetization or partner distribution may apply, also read `references/monetization-and-partner-channel-guide.md`. For a web app, internal tool, public website, browser extension, or hybrid with a browser frontend, also read `references/frontend-stack-selection.md`. For any product with a backend, persistent data, or auth requirement — most products other than a purely static content site — also read `references/backend-stack-selection.md`. For a mobile-app or desktop-app surface, also read `references/mobile-stack-selection.md`; its desktop platform patterns live in `references/architecture-playbook.md`.
10. Before drafting, inventory earlier documents related to the same product as described in `references/artifact-lifecycle.md`. Do not move anything yet. In enhancement mode, this still includes the existing package identified in step 2 — it will be archived for history once the enhanced draft is published, even though its content already carried forward into that draft.
11. For a non-trivial new package, run `assets/templates/CLAUDE_PRD_WORKFLOW.template.js` only under its explicit multi-agent and `builder_readonly` gates. Freeze the interview, Stack Decision Mode, Data and Trust Gate input, AI and Automation Gate input, release targets, and commercial models first. The workflow may return candidate Markdown and coherent technology options; it cannot ask the owner, mark a new choice `Approved`, pass either approval checkpoint, or authorize publication. Skip it in enhancement mode and perform the same roles sequentially against the existing package.
12. Draft or repair the core Markdown package in the staging location defined by `references/artifact-lifecycle.md`:
    - `PRD.md`
    - `architecture.md`
    - `stack-decisions.md`
    - Every PRD records Data and Trust and AI and Automation gates as `required`, `not_required`, or `blocked`, with a human owner and reason. Required gates carry their concrete product, architecture, technology, UI, and test obligations; a blocked gate prevents Product Definition Approval.
    - For every UI-bearing package, record a Motion Need Gate in `PRD.md` for each key surface: `required`, `recommended`, `not_required`, or `blocked`, with purpose, trigger, decision source, and reduced-motion fallback. The AI may recommend within delegated authority, but generated motion, autoplay/sound, material performance budgets, accessibility exceptions, and scope changes remain human decisions. A `blocked` row prevents Product Definition Approval.
    - In every package, record the Monetization Infrastructure Gate and Partner Channel Gate in `PRD.md`, including explicit `not_required` reasons. When either applies, carry its separately selected layers into `architecture.md` and `stack-decisions.md`; do not collapse billing, entitlement, merchant-of-record, affiliate, referral, and reseller responsibilities into one vendor label.
    - For a UI-bearing product, the drafting workflow may prepare candidate wireframe data, but keep `wireframes.html` at draft status. Do not run the Reference Pass, browser/grading gate, or human Wireframe Approval until the post-draft research, Stack Decision Checkpoint, Product Definition Approval, and core package checker all pass.
    - Do not start UI Design Pass or invoke `design-system-compiler` automatically. Visual work remains a later explicit phase.
    - For a product with no UI surface — a headless API or backend service, or an automation whose only surfaces are notifications it sends into someone else's UI — do not create `wireframes.html`, run a UI Design Pass, or invoke `design-system-compiler`; record the skip in `PRD.md` and publish no placeholder UI or design files.
    - Draft `DEPLOYMENT.md` from `../delivery-harness/assets/templates/DEPLOYMENT.template.md` when the package has a deployable surface: record the platform chosen in the deployment decision; seed the Required Secrets and Variables inventory with every exact name already established by the product or architecture; record known auth callbacks, allowed origins, webhooks, domains, roles, and other provider-side work in External Console Setup; and leave their human-owned statuses plus the remaining Human Setup Checklist for the owner. Record names and destinations only, never values. Do not invent implementation-owned key names or URLs: leave them visibly unresolved for `delivery-harness` to reconcile from the finished code before the first deployable push. A purely local product records `manual` mode or skips the file with a note in `stack-decisions.md`. Publish it to `docs/DEPLOYMENT.md` with the package.
    - When the package has a web, iOS, or browser-extension release target and `docs/ACTIVATION.md` does not already exist, resolve `../product-activation/assets/templates/ACTIVATION.template.md` and create one `ACTIVATION.md` seed. Fill the product, owner when known, selected `core` plus surface profiles, only those supported release target IDs, and one Outcome Coverage row for every PRD metric and required `TEST-*` signal scoped to that supported target subset. Leave Android, desktop, API-only, and other unsupported targets outside the Activation seed, including in a hybrid package. Leave implementation-owned actions, routes, accounts, queries, release SHAs, artifact/build identities, sources, and evidence visibly pending. Run the sibling `product-activation/scripts/check_activation.py --activation <staged ACTIVATION.md> --prd <staged PRD.md>` before publication. Publish the seed to `docs/ACTIVATION.md`. If the live path already exists, preserve it byte-for-byte, stage no replacement, and record in `DOCUMENTS.md` that `product-activation` must reconcile it after delivery.
    - Draft `DOCUMENTS.md` from `../delivery-harness/assets/templates/DOCUMENTS.template.md` as the manifest of every flow document, publish it to `docs/DOCUMENTS.md`, and fill the status column for each document this package creates; keep it current through publish and archive.

    A product is UI-bearing when a person interacts with a surface this product ships. A native mobile or desktop app is UI-bearing without a browser frontend; an internal tool with one admin screen is UI-bearing; a service whose only output is an API response, a webhook, or a message posted into a third-party client is not.

    At this point the core artifacts are candidates, not approved implementation authority.

    In enhancement mode, preserve unaffected content and stable IDs, mint new TEST IDs only for newly uncovered obligations, and apply the complete Enhancement Impact Record. Every changed product, UI, data, stack, trust/AI, commercial, or release row names the artifacts and owner gates that must refresh. No stale decision remains effective by omission.
13. Run the post-draft market-research reconciliation now, before any stack or product approval and before Wireframe Approval. Apply `references/market-research-guide.md`, including its Research Disclosure Check. Delegate it to the authorized Dynamic Workflow lane, a single read-only subagent only when the parent has a separate explicit subagent/delegation authorization, or the parent inline when no delegation authorization is present. Read the candidate PRD plus `research-assessment.md` when the pre-draft pass ran. The pass is a reconciliation: carry valid `RA-*` evidence forward, research only new or unresolved claims, and apply in-scope findings — including evidence that strengthens or contradicts a `stack-decisions.md` layer row or alternative — to the candidate. Every factual claim carries publisher, URL, and retrieval date or is `UNVALIDATED`; never invent a competitor, price, or market figure. A scope-changing finding becomes a blocking Open Question for the owner. Record a safe skip or blocked result explicitly.
14. Run the Stack Decision Checkpoint. For each applicable frontend, backend/data, mobile/desktop, AI/automation, or commercial area that is not already `Required` or `Selected`, present two or three coherent bundles with every coupled layer, fit, tradeoffs, cost/license/data constraints, maintenance and operations owner, serious alternatives, and revisit triggers. Follow the recorded Stack Decision Mode. Mark an accepted new choice `Approved`; keep an unaccepted proposal `Recommended`; keep missing-evidence choices `Provisional`. Record the machine-anchored checkpoint, owner, date, approved areas, delegation source, and open areas. `Recommended` or `Provisional` blocks the checkpoint and implementation.
15. Run Product Definition Approval for every product, including headless products. Present scope, Must requirements, trust/AI/commercial gates, metrics/tests, architecture/release targets, approved stack, risks, assumptions, and open questions. Record the machine-anchored decision and package revision. Approval requires an approved stack checkpoint, no blocking question/gate, and resolved research. A substantive product/architecture/stack change reopens the gate; appending later wireframe or visual evidence does not unless it changes those approved contents. Then run the core package checker with `--require-filled --require-approved`.
16. Only after step 15 passes, create or refresh `wireframes.html` for a UI-bearing product using `references/wireframe-guide.md` and `assets/templates/WIREFRAMES.template.html`. Run the Reference Pass before drafting the HTML: fetch two to four mainstream comparable screen structures, then lower-ranked gallery composition references, and record each adopted/rejected pattern or skip reason in `PRD.md`'s `Wireframe references consulted:` line. The one self-contained file contains every `UI-*` surface, page/target/state controls, visible section-purpose labels, runtime QA, and working PRD actions mapped to `page`, `overlay`, or `feedback`. Before the human Wireframe Approval Gate, bind it to the approved Product Definition revision, run the full browser matrix, and—when multi-agent browser capability exists and dispatch is authorized—one complete diagnostic wave, one consolidated ledger, one repair batch, and one re-review; record the capability-unavailable path otherwise. Obtain human approval and run `check_wireframe_html.py --require-filled --require-approved`. If wireframe work reveals a product gap, update the PRD first, reopen Product Definition Approval on a new revision, and then regenerate the affected pages. An approved `wireframes.html` completes the wireframe stage; a headless product records the UI skip and completes without one.
17. Produce `implementation-plan.md` only when the user explicitly asks for delivery sequencing. Reuse canonical `TEST-*` and release-target IDs; it must not create anonymous replacements or duplicate TEST identities.
18. Only when the owner explicitly requests visual design, and after Product Definition Approval plus applicable Wireframe Approval are resolved, run `references/ui-design-pass.md` directly. The pass must respect the approved component foundation and styling layers; a direction requiring a stack change returns to steps 14 and 15 before continuing. Otherwise record `Visual design phase: not requested` and complete the package at the approved product/wireframe stage.

    Resolve the design-direction skill from the repository's Skill Bindings table in its `AGENTS.md` when one is bound; otherwise use the bundled default `design-taste-frontend`, and record `applicable`, `partially_applicable`, or `n/a: <reason>`. The visual phase opens from the approved PRD package and runs as one combined pass with both skills: the design-direction skill leads the overall direction, and the frontend-implementation skill covers the direction skill's excluded surfaces. Apply it to landing, portfolio, editorial, public marketing, and compatible redesign surfaces. For dashboards, data tables, multi-step product UI, native mobile, or another declared exclusion, load the bound frontend-implementation skill (default `frontend-design`) for the uncovered surfaces instead of forcing Taste to apply. Never combine two design-direction skills — an alternative such as `gpt-taste` is an explicit owner-selected swap for a named scope only.

    Ask the human owner once for style preferences and visual references. Reuse the PRD Motion Need Gate and ask the closed key-surface treatment question from `references/ui-design-pass.md` only where that gate remains `blocked` or the owner wants to change it — hero first: motion-led, imagery-led, both, or quiet. Treatments already annotated in `wireframes.html` as `mediaIntent` arrive pre-answered, and their draft prompts are refined into a deferred later MCP-generation handoff; this pass does not invoke a generation provider. Also inspect relevant readable candidates under `docs/design/`, any user-named design folder, and obvious in-scope design images found during the normal bounded scan; repository presence alone never makes one binding. Then produce one recommended product-specific direction by default. Produce three comparable directions only when the owner requests alternatives or a recorded visual conflict needs comparison. A direction may call itself market-supported only when valid `MR-*` evidence applies; a market-research URL is not visual evidence until it is separately inspected. Choose iconography through `references/ui-design-pass.md`'s online lookup as part of the direction: recommend one primary icon set plus a named fallback from the closed candidate set — Lucide, Phosphor, Heroicons, and Tabler — record them in the handoff's `Iconography:` line with cited official sources, and never silently default to a remembered library. Choose typography with the same lookup discipline — display/body pairing, Latin plus CJK coverage, loading strategy — and record the color derivation and dark-mode scope, in the handoff's `Typography:` and `Color & dark mode:` lines.

    Run the UI Preview Gate for every in-scope `UI-*` screen and its complete responsive-target and non-`n/a` state matrix. Login, registration, recovery, and authentication-error previews are omitted and recorded `n/a` for this visual pass without deleting production authentication requirements. Every UI-bearing product — web, native or cross-platform mobile, and desktop — uses one self-contained design-reference HTML review file as the implementation reference. It contains complete CSS and review JavaScript, a left sidebar, working page and state switching, and every product action needed to traverse the approved flows; visible controls navigate, switch state, open the documented modal or drawer, or show recorded feedback. Required functional UI motion may run as deterministic local CSS or JavaScript so its purpose and reduced-motion fallback can be reviewed. Generated media or motion positions remain visible static placeholders carrying dedicated prompts, source decisions, triggers or placements, reduced-motion expectations, and `generationStatus: deferred`; do not invoke a generation provider or claim generated output during this pass. Render every in-scope page-target-state and overlay in a real browser and reject dead controls, broken navigation, unintended overlap, clipping, occlusion, or horizontal overflow. Before the human visual decision, bind the candidate to the exact PRD revision or hash and apply `references/ui-grading-rubric.md`: run one complete diagnostic wave, consolidate all findings before editing, and allow one repair batch and one re-review on the new SHA. If that re-review still blocks, stop for a PRD correction or explicit owner-approved structural strategy; never continue an open-ended refinement loop. When capability is unavailable, record the exact skip and continue with the non-grading gates. Record path, SHA-256, limitations, browser evidence, diagnostic and repair/re-review history or skip, deferred generation handoff, and the human decision. Preview artifacts remain outside `docs/product/`.

    After approval, record the selected direction and immutable page-faithful HTML target in `PRD.md`'s `### UI Design Handoff`, including frozen PRD identity, included and auth-preview-`n/a` scope, states, responsive coverage, working interaction evidence, grading scores or capability-unavailable skip, deferred image and motion handoff, tolerance, and allowed deviations. Then run the Design System Need Gate. Mark it `required` when the owner asks for a formal system, an existing pair is canonical, or shared tokens and closed variants are needed across multiple surfaces, themes, platforms, teams, or automated checks. Mark it `not_required` for a small or single-surface UI whose approved target plus PRD and `wireframes.html` are sufficient. Mark it `blocked` when the decision cannot yet be made.

    Only when the result is `required`, load `design-system-compiler` and pass it the approved UI Design Handoff plus the staged product sources. It owns `design-system.md` and `design-system.json` and compiles the selected direction without reopening visual exploration by default. When the result is `not_required`, publish no placeholder pair; the approved UI target is the replacement visual contract. If a required skill or preview decision is unavailable, stop with the core documents staged and report the blocker.
19. Run the `references/output-contract.md` checklist and both core checkers. Resolve every required lane and material verifier finding. An approved core package contains only `Required`, `Selected`, or `Approved` executable stack rows; `Recommended`, `Provisional`, or a blocked checkpoint remains staged and cannot enter Harness.
20. After validation, show exact publish paths, overwrite targets, and archive moves. This Publication Authorization Gate is separate from Product Definition Approval. If those exact mutations are not already authorized, ask one explicit yes/no publication question. On approval, execute the approved publish and archive moves in the same run; otherwise leave the approved package staged.
21. In the same authorized publish move set, run `python <delivery-harness-skill-root>/scripts/configure_project_context.py --root <target-root> --check`. Create only missing files, using `PROJECT_AGENTS.template.md` for `AGENTS.md` and the distinct `PROJECT_CLAUDE.template.md` for `CLAUDE.md`; never copy one template to both files or reopen an established context file. List locally installed binding candidates, confirm the bindings with the owner in one `AskUserQuestion`, and let slots with no candidate stay at the bundled default. Record SHA-256 pins and finish with `--check --require-resolved`.
22. Report final artifact, operational, seeded-context, and archived paths, plus Product Definition and Wireframe approval status.
23. After reporting a completed package, state that visual design and implementation are separate optional phases; do not invoke or automatically offer either. A later Harness request consumes the approved Product Definition revision, approved Stack Decision Checkpoint, architecture, and applicable approved wireframe/visual sources.
24. When the owner asks for an outcome review after deployment, read `outcome-review.md` inputs and any `docs/ACTIVATION.md` in full. After the real measurement window closes, compare actuals with every metric's baseline, target/guardrail, window, source/method, owner, and required `TEST-*` signal; never leave a run open waiting for adoption. For every reviewed target in its supported active target set, require matching verified `MS-*` sources with the Activation checker. Record exactly one `no_change`, `enhancement`, or `incident` verdict and route it to the next enhancement or incident record.

## Interview Rules

- Run discovery in two phases. First, ask the three bounded free-text segments in order: **Product and users**; **Workflows, data, and rules**; **Delivery, success, and risk**. Ask one segment per turn and wait for its reply. Dynamically omit already answered or inapplicable prompts from later segments, but do not merge multiple planned segments into one long message. After segment 3, compare the aggregate answers with `references/interview-guide.md`'s completeness criteria. If a material item is still missing and assumptions are not authorized, ask one compact targeted free-text follow-up containing only those gaps. Only after all applicable segments and that optional follow-up are complete may the closed `AskUserQuestion` batches begin. Use the tool's built-in Other option instead of inventing a separate free-text fallback. Do not run a fixed design-reference visual-style questionnaire here.
- Step 7's questions always come after the archetype and Builder UX calls. Resolve target operating systems/browsers before native-versus-cross-platform or framework choices, and record how the owner wants technology recommendations decided. Batch to the question tool's actual capacity without dropping applicable decisions.
- Do not ask questions already answered by the user's prompt.
- Before drafting, finish release discovery with stable surface IDs and development/production target IDs. Keep `surface` separate from stage-specific `provider`. Under the standard main-only promotion contract, development releases build from the exact candidate run branch/SHA and production builds from `main` only after candidate verification and separately authorized fast-forward; both initial delivery and enhancements start from observed remote `main`. Record any explicit alternative source rule. Also close artifact/signing, channel, release gates, availability, rollout, and recovery. These are not extra closed-set `AskUserQuestion` calls.
- Mark optional questions clearly when they would improve quality but should not block progress.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.
- If the user gives conflicting requirements, resolve them before drafting or call out the conflict in `open questions`.
- Treat builder preference as a direction input, not as proof that users find the result usable. When it conflicts with user evidence or an accessibility requirement, record the conflict and validation need instead of silently following preference.
- In enhancement mode (Workflow step 2), never repeat questions the existing package already answers. Scope the free-text message and every `AskUserQuestion` call to what the new idea adds, changes, or leaves genuinely unresolved.

## Reference Routing

- Use `references/interview-guide.md` for required discovery questions and readiness criteria.
- Use `references/monetization-and-partner-channel-guide.md` for commercial-model, pricing/offer, RevenueCat-or-alternative, merchant-of-record, affiliate, referral, and reseller decisions.
- Use `references/output-contract.md` for the exact artifact names, headings, and final quality checklist.
- Use `scripts/check_product_package.py` for core headings, Must/NFR-to-TEST coverage, metrics, decision tables, approval markers, executable stack statuses, and blocked trust/AI/commercial gates.
- Use `references/wireframe-guide.md` only after Product Definition Approval for the single-file `wireframes.html`, one-to-one `UI-*` coverage, working local actions, responsive/state review, structural boundaries, Reference Pass, and human Wireframe Approval.
- Use `scripts/check_wireframe_html.py` after wireframe approval to verify filled data, local-file self-containment, unique page/region/state IDs, action-to-flow mappings, deferred `mediaIntent`, one responsive set (web: at least three viewports; native/desktop: at least two size classes), complete per-target ordering and spans, never-drop visibility, runtime-QA markers, PRD agreement, and approval status.
- Use `references/ui-design-pass.md` only after wireframe approval and an explicit owner request to continue into visual design, for Taste applicability, the connected interactive design-reference HTML, auth-preview exclusion, deferred media and motion handoffs, iconography lookup, human visual approval, the page-faithful target record, and the Design System Need Gate.
- Use `references/ui-grading-rubric.md` for the PRD-bound diagnostic and grading stage before both human UI gates. The design-reference candidate first passes the rubric's Technical Hard Gate. When the host has the capability and dispatch is explicitly authorized, default to one fresh lead grader and add at most two non-overlapping specialists only for an owner request or recorded high-impact risk. Wireframe readiness keeps its structural overall threshold of 80. Design-reference human-gate readiness requires an overall score of at least 90, no dimension below 60, no block, and `H2` layout, `H4` responsive, and `H8` accessibility scores of at least 90. Scores summarize visual quality; explicit PRD, behavior, layout, state, motion, and accessibility obligations remain hard gates. All findings enter one consolidated diagnostic ledger before one repair batch and one re-review. When capability is unavailable, record the exact skip and continue. The parent preserves blocks, advisories, and disagreements in the recorded `UI grading:` line.
- Use `references/artifact-lifecycle.md` for detecting an existing package to enhance, staging, final `docs/product/` locations, safe identification of superseded documents, and post-validation archival.
- Use `references/architecture-playbook.md` for implementation-ready architecture content across web, mobile (native iOS, native Android, Flutter), desktop (macOS, Windows, cross-platform), browser extensions (Chrome with Manifest V3), internal tools, and automations, including the candidate-to-main release contract for deployable web products (Cloudflare given as the worked example; substitute the resolved platform) and the app-store/signed-installer distribution discipline for native mobile and desktop targets.
- Use `references/frontend-stack-selection.md` to separate frontend technology layers, recommend one product-fit stack, and verify current Cloudflare support when that platform is in scope.
- Use `references/backend-stack-selection.md` to decide service topology first, then separate backend runtime, database, and auth technology layers, resolve the database category and auth strategy, recommend one product-fit stack for the backend framework, database engine, and auth provider, and verify current platform/vendor support.
- Use `references/mobile-stack-selection.md` for a mobile-app surface: separate cross-platform-vs-native, framework (Flutter vs React Native), and the React Native Expo-vs-bare workflow layers, recommend one product-fit stack, and verify current Expo/React Native/Flutter support. It pairs with `architecture-playbook.md`'s React Native / Expo, Flutter, and native patterns.
- Use `../design-system-compiler/SKILL.md` only when the Design System Need Gate is `required`. It compiles the already approved UI direction into the design-system pair and owns its templates and deterministic checks.
- Use `references/dynamic-workflow.md` for the stable PRD role graph, bounded Claude Code workflow, failure handling, and sequential fallback.
- Use `references/market-research-guide.md` for the post-draft market-research gap pass: what to research, the source and anti-fabrication rules, `MR-*` IDs, which PRD section each finding lands in, and when the role returns blocked.

- Use the sibling `product-activation` template and checker only for the create-once operational seed and the later verified-source outcome handoff. `product-activation` owns all post-delivery reconciliation and external actions.

## Output Standards

- Write each artifact for the primary reader named in `references/output-contract.md`'s "How To Read This Package", and respect its length budget. Completeness is not the only bar — a document nobody finishes reading has not delivered its requirements.
- Put meaning before bookkeeping in every artifact. Open with what a human needs to understand the product; close with the ID matrices and decision records that machines, auditors, and downstream skills need. Never open a document with a trace table.
- Keep tables at seven columns or fewer, except the mandated hosted environment contract in `architecture.md`, whose columns are all release-critical. When a row needs more fields than that, write one block per item instead of widening the table.
- Prefer specific, buildable requirements over vague product language.
- Keep the current PRD package directly under `docs/product/`; reserve `docs/product/archived/` for superseded documents only.
- Tie every major requirement to a user need, workflow, metric, or constraint.
- Mint stable upstream trace IDs: `PRD-*` for product requirements, `ARCH-*` for architecture contracts, `UI-*` for UI surfaces, `UX-*` for usability requirements, `TEST-*` for test obligations, `MR-*` for market-research findings, and `RA-*` for research-first assessment findings. `design-system-compiler` owns `DS-*` and `DS-COMP-*`. Preserve every family across revisions and never reuse a retired ID for a different meaning.
- Keep market research evidence in `market-research.md` and conclusions in the artifact they affect. `PRD.md` cites the `MR-*` ID behind a statement; it does not restate the competitor table, the sources, or the retrieval dates. A market claim with no source is recorded `UNVALIDATED` with what was searched, never stated as fact and never invented.
- Keep `## Non-Functional Requirements` in every `PRD.md`, immediately after Functional Requirements. Use `PRD-*` IDs and record every applicable quality attribute with a scoped measure and target; record non-applicable categories explicitly as `N/A` with a reason. Vague words such as `fast`, `secure`, `reliable`, or `scalable` are invalid without measurable units, population or traffic shape, measurement window, and percentile where applicable.
- Keep `## Test Obligations` in every `PRD.md`, after Open Questions and before the trailing Builder UX and Product Definition decision records. Use the canonical columns from `references/output-contract.md`. Map every `Must` functional requirement and applicable NFR to a required `TEST-*` row with an observable signal.
- For every UI-bearing product, record the Builder UX Direction Decision, its Motion Need Gate, and Wireframe Approval. Record a UI Design Handoff only when the owner explicitly requests and completes the later visual-design phase. Do not let a design or implementation agent invent its own taste when the human decision owner has not answered; use an explicit provisional assumption only when assumption mode is authorized. When the owner explicitly delegates motion direction, the AI may recommend `required`, `recommended`, or `not_required` per key surface with reasons, but it cannot authorize generated motion, autoplay or sound, a material performance budget, an accessibility exception, or new scope.
- Include loading, empty, error, permission, and edge states when a UI or workflow has them.
- Treat `PRD.md` as canonical for product scope, UI behavior, the exact responsive set, and the approved UI Design Handoff. Treat `wireframes.html` as the single approved structural projection used to inspect page layout, per-target region order and spans, grouping, visibility, element inventory, states, responsive rearrangement, and runtime overlap/overflow status. `PRD.md` wins when scope or behavior conflicts with the HTML or a visual target. When required, `design-system-compiler` owns the formal design-system pair and preserves `DS-*` and `DS-COMP-*` across revisions.
- This skill owns the product definition, UI surface contract, structural wireframes, direct UI Design Pass, and Design System Need Gate, not production UI implementation. It creates no design system, production component, Harness plan, mission map, PLAN/RUN state, or E2E evidence register. `design-system-compiler` creates the pair only when required; `delivery-harness` implements either that pair or the approved replacement visual contract.
- Keep assumptions explicit and avoid hiding unresolved decisions in confident prose.
- Every package records a Data and Trust Gate and AI and Automation Gate with human ownership. Required gates carry concrete architecture, stack, UI, and test obligations; `blocked` prevents Product Definition Approval.
- Every success metric records baseline, target/guardrail, measurement window, source/method, and owner. Every assumption and open question records ownership and approval impact; an unresolved blocking question prevents approval.
- Architecture may remain technology-neutral while evidence is incomplete. For every applicable technology area, produce coherent bundles rather than disconnected menus, recommend one, and present it under the Stack Decision Mode. New accepted choices are `Approved`; adopted repository choices remain `Selected`; hard constraints are `Required`; `Recommended` and `Provisional` are non-executable draft states.
- For a browser frontend, separate deployment/runtime, rendering, language, package manager, framework, UI library, component foundation (including shadcn/ui when chosen), styling approach, build tool, routing/data, and testing. Do not collapse component source and CSS into one row.
- For every deployable web, API, mobile, desktop, or browser-extension surface, close a provider-neutral release-target contract before drafting. Record the complete expected deployable-surface inventory with stable surface IDs, then give every target a stable target ID, an explicit lowercase kebab-case surface suffix, a lowercase kebab-case release name, and a `development` or `production` stage. A production release name is the unqualified canonical `<product-slug>-<surface-suffix>` name and never ends in `-prod`; development uses that exact name plus `-dev`. Release names are globally unique across distinct surface IDs. Use `web`, `api`, and `extension` as the normal surface suffixes. Use another descriptive suffix such as `admin`, `worker`, `jobs`, `agent`, `webhook`, `realtime`, or `cli` only when that artifact is independently released. Native release artifacts may use `ios`, `android`, `macos`, or `windows`; their separately hosted backend remains `api`. Record stable `surface` separately from stage-specific `provider`, the source policy (the exact branch or ref each stage's release builds from), artifact kind, signing requirement, exact channel or track, submission/promotion/review or manual-approval path, actual availability signal, rollout, and rollback or forward-fix path. Require development and production targets for every expected surface; reject missing surfaces. Providers may differ by stage. Preserve surface and target IDs across revisions and never reuse an ID for a different meaning. An upload, submission, or approval is not availability by itself.
- For a deployable web or API target, resolve the deployment platform explicitly via the interview's platform `AskUserQuestion` step (see Workflow step 7, after the archetype is known) unless the user or current repository already names one. Never silently assume a platform, and do not invent platform-specific requirements for docs-only work. Record one codebase promoted through separate development and production environments (named Workers for Cloudflare, or the platform's equivalent unit), exact release sources, isolated bindings and secrets, data/auth/payment modes, migration order, deployed-environment checks, and rollback.
- Keep native mobile and desktop targets in the provider-neutral release-target contract rather than forcing them into the hosted web/API environment table. For store or signed-installer delivery, production availability means the approved artifact is actually installable or downloadable through the named channel and passes its smoke check. When instant rollback is impossible, record rollout halt plus a signed forward-fix through the same review or distribution path.
- For every product with a backend, persistence, or auth, compare coherent backend bundles and record the owner-approved result. Record service topology first — monolith versus named services, and monorepo versus polyrepo — then keep runtime/framework, database category/engine, auth strategy/provider, API style, jobs/queue, and storage separate.
- For a product with a backend, persistent data, or auth requirement, resolve the database category and auth strategy explicitly via the interview's backend/data `AskUserQuestion` step (see Workflow step 7) unless the user or current repository already names them. Do not silently pick a database category or auth strategy on the user's behalf. Never silently default to a specific database engine or auth vendor.
- For mobile or desktop, decide target operating systems first, native versus cross-platform second, and framework/toolchain third. Record navigation/state, persistence, secure storage, sync, push/native modules, backend integration, distribution, and testing separately, with the same checkpoint approval discipline.
- Do not present Cloudflare, Astro, React, and Vite as peer alternatives: Cloudflare is a deployment/runtime platform, Astro is a web framework, React is a UI library, and Vite is a build tool that can be paired with React or used by frameworks.
- Keep a decision technology-neutral only when evidence is genuinely insufficient. Record the missing evidence, owner, deadline, and time-boxed spike; keep the Stack Decision Checkpoint and Product Definition Approval blocked until the executable scope is resolved.
- When recommending a fast-moving hosted platform or framework, verify current official documentation and record the check date and sources in `stack-decisions.md`.
- Treat the stable PRD roles as an org graph and each bounded workflow run as a temporary work graph. Dynamic Workflow coordinates read-only analysis; the parent still owns source freeze, staged artifact writes, conflict resolution, approval, publication, and cross-session recovery.
- When `implementation-plan.md` is requested, include non-canonical Harness handoff signals for dependency order, parallel candidates, shared resources, required reviews, and human gates. Do not create PLAN/RUN mission maps in this skill.
