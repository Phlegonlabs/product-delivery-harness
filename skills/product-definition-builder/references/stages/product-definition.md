# Product Definition Stage

## Path Interpretation

Outside a real Markdown link, `references/...` and `../delivery-harness/...` are logical paths from `<product-definition-builder-skill-root>`, not from this stage file. Actual Markdown links resolve relative to this file.

## Workflow

Apply `references/bilingual-review.md` throughout, including its same-directory backfill for existing English-only sources at task entry. Keep `PRD.md` and `architecture.md` in English as the only downstream implementation sources. Keep complete `PRD.zh-TW.md` and `architecture.zh-TW.md` review copies beside every candidate; a revision updates the changed sections. Present the Chinese links first, with their English sources, and reconcile accepted Chinese feedback into English first. Run `scripts/check_review_translations.py` before owner review and before/after publication. Hash/ID agreement does not replace semantic translation review or Product Definition Approval.

At authorized session entry, entry bootstrap is the first source task for a new or existing target. Create a missing context file or review the existing AGENTS merge proposal before package processing; its merge rules preserve local authority and leave unresolved semantic conflicts explicit.

For website and app packages, read [Initial Product Foundations](../../../delivery-harness/references/initial-product-foundations.md) before drafting.
Plan AEO/public discovery, applicable deployment setup and Google Analytics in existing requirements, architecture, stack decisions and TEST obligations.
Product Definition plans these prerequisites; authorized implementation and fixed-build Activation preparation execute them before dependent features.

1. Read `references/interview-guide.md` before asking discovery questions.
2. Read `references/artifact-lifecycle.md`'s Detect Enhancement Mode section, then check whether `docs/product/PRD.md`, or another Markdown document whose title or content clearly describes the same product, already exists. Check `docs/product/.prd-staging/` in the same step. If a matching package exists, enhance it: read `PRD.md`, `architecture.md`, `stack-decisions.md`, `market-research.md`, `research-assessment.md`, and every retained `docs/product/outcomes/*.md` record in full. Read current `docs/design/ui-design.md`, wireframe, and design-system files only to identify downstream impact; do not carry or rewrite them here. Read `docs/ACTIVATION.md` for operational context without overwriting it. Preserve unaffected content, decisions, and trace IDs; never restart from a blank package.
3. Conduct exactly four bounded free-text turns from `references/interview-guide.md` unless the user explicitly authorizes assumptions: **Product and users**; **Workflows, data, and rules**; **Delivery, success, and risk**; then **Ambition**. Ask one segment per turn, wait for its reply, dynamically omit answered prompts, and do not call `AskUserQuestion` during any free-text segment. Capture product, workflow, data/trust, security, AI/automation, delivery, measurement, cost, licensing, and ownership constraints. In enhancement mode, create this round's PRD delta from `assets/templates/PRD_DELTA.template.md` with the baseline PRD hash first, record the complete Enhancement Impact Record in it, including the existing `none` / `structure` / `style` / `both` UI classification, then ask only what the delta changes; stale product, stack, data, commercial, release, wireframe, or visual contracts never publish silently.
4. Run the research-first assessment before any closed-set decision. First perform its Research Disclosure Check and use only a public-safe query summary; never send confidential product inputs, personal data, customer names, internal metrics, secrets, or contract terms to a search provider. Skip with the recorded reason when the user declines, no web tool exists, the package is trivial, or useful research cannot be sanitized. Include the applicable feature baseline, differentiation, pricing/business-model baseline, and category benchmarks as research inputs useful before drafting; do not turn them into speculative final requirements. The researcher recommends and the human owner decides `go | clarify | stop` as specified in `references/research-first-guide.md`; stage `research-assessment.md` with stable `RA-*` findings when produced. In enhancement mode, skip this step entirely and research only the delta after drafting.

    Research helpers follow `references/agent-work-graph.md`: one researcher covers the whole question inventory. A permitted skip and an evidence-backed `no_sources` result stay distinct.

    For an unresolved architecture, API, auth, frontend, backend, data, security, product runtime, agentic runtime, deployment, or integration choice, consult the optional reference-selection rule in `../delivery-harness/references/reference-selection.md` before closed-set stack questions. Load only the relevant domain under `../delivery-harness/references/option-library/`; compare coherent options or keep the existing stack. No provider is mandatory and this consultation is not a new gate.
5. After all applicable free-text segments have replies and the final coverage check has no material gap, use their aggregate answers to skip resolved or inapplicable decisions, then issue the first `AskUserQuestion` call, sized to the question tool's actual per-call question and option limits, resolving the remaining closed-set decisions marked `(AskUserQuestion)` in `references/interview-guide.md` that depend on no other answer: product archetype and validation depth. Do not issue this call in the same turn as any free-text segment or targeted free-text follow-up. When step 4's assessment recommends `go`, its gate decision is the first question of this call. Keep deployment and UI design preferences out of this call. UI layout, style, motion, and media choices belong to the later `ui-design-builder` intake. In enhancement mode, only re-ask a closed-set decision the new idea actually reopens; otherwise keep the existing package's answer.
6. For a UI-bearing product, capture only product-level UI obligations: human decision owner, required surfaces, route and state behavior, content responsibilities, validation depth, accessibility, localization, responsive destinations, confirmation/recovery rules, and exact or bounded copy. Bind each surface to its exact architecture release surface, surface class, derived capture mode, and its own responsive set; a hybrid package never flattens web, extension, native, and desktop surfaces into one global capture contract. Defer information density, layout preference, visual character, imagery, iconography, motion treatment, media placeholders, wireframes, themes, and tokens to `ui-design-builder`. Product Definition may record hard brand or platform constraints, but it never turns them into a visual direction.
7. Issue the next `AskUserQuestion` call or calls, each sized to the question tool's actual per-call limit, for every applicable closed-set decision that depends on step 5's archetype answer, marked `(AskUserQuestion)` in `references/interview-guide.md`:
    - an evidence-narrowed deployment-platform choice for hosted surfaces, including an explicit recommendation option and the tool's built-in Other;
    - target operating systems for mobile/desktop, native versus cross-platform strategy after those targets are known, and browser targets for extensions;
    - database category and auth strategy, each including an evidence-backed recommendation choice when the owner does not already have one;
    - the monetization model when the product has commercial intent or an unresolved pricing strategy, and the partner channel when outside promoters or sellers may contribute revenue. These decisions select a model, not a provider; apply `references/monetization-and-partner-channel-guide.md` afterward to recommend RevenueCat or another current fit.
    - the Stack Decision Mode: owner review of one coherent recommendation plus alternatives, layer-by-layer owner selection, or explicit delegation to this skill. Delegation never skips Product Definition Approval.

    Skip resolved or inapplicable questions, but do not drop an applicable decision to fit an invented call budget. Do not silently select a provider, framework, component system, CSS approach, database/auth implementation, mobile framework, commercial provider, or browser target. Local persistence/auth may require backend analysis without a hosted deployment question; skip database/auth questions only when the product provably has no backend, persistence, or auth.
8. Classify the product as web app, mobile app, desktop app, browser extension, internal tool, automation or agent workflow, API/backend service, or hybrid. Record target destinations separately from implementation strategy: operating systems or browsers first, then native/cross-platform, framework, and toolchain in the later Stack Decision Checkpoint. Record public marketing/SEO scope, Data and Trust, Security Requirements, and AI and Automation Gate applicability.
9. After discovery, read `references/output-contract.md` through How To Read This Package; read each artifact's section of it when drafting that artifact. Also read `references/architecture-playbook.md`, the helper rule in `references/agent-work-graph.md`, `references/research-first-guide.md`, and `references/market-research-guide.md`, plus the rest of `references/artifact-lifecycle.md`. When monetization or partner distribution may apply, also read `references/monetization-and-partner-channel-guide.md`. For a web app, internal tool, public website, browser extension, or hybrid with a browser frontend, also read `references/frontend-stack-selection.md`. For any product with a backend, persistent data, or auth requirement — most products other than a purely static content site — also read `references/backend-stack-selection.md`. For a mobile-app or desktop-app surface, also read `references/mobile-stack-selection.md`; its desktop platform patterns live in `references/architecture-playbook.md`. For an AI or automation surface, also read `references/agentic-runtime-selection.md`.
10. Before drafting, inventory earlier documents related to the same product as described in `references/artifact-lifecycle.md`. Do not move anything yet. A bounded enhancement (no stack change) skips this inventory: it edits the published files in place and Git is the archive.
11. Read-only helpers are optional under `references/agent-work-graph.md`. The parent drafts every artifact; a helper proposes and cannot ask the owner, mark a new choice `Approved`, pass either approval checkpoint, or authorize publication.
12. Draft or repair the core Markdown package using the discovery decisions and available research-first evidence, in the staging location defined by `references/artifact-lifecycle.md` (a bounded enhancement edits the published files in place):
    - `PRD.md`
    - `architecture.md`
    - `PRD.zh-TW.md` and `architecture.zh-TW.md` as non-canonical owner review copies
    - `stack-decisions.md`
    - Every PRD records Data and Trust and AI and Automation gates as `required`, `not_required`, or `blocked`, with a human owner and reason. Required gates carry their concrete product, architecture, technology, UI, and test obligations; a blocked gate prevents Product Definition Approval.
    - Apply `references/eval-policy-contract.md` before approval: freeze eval inputs, rubric, rate, repeat/slice/critical rules, judge identity, budgets and required quality/handoff TESTs. Ordinary products record a reasoned `not_required`.
    - Every PRD records the Security Requirements Gate and Security scope from `references/output-contract.md`. Executable software is security-required even when it has no personal data or authentication. Legacy packages may be read as history, but current Product Definition Approval requires the section and a new explicit owner decision.
    - For every UI-bearing package, finish the complete UI Surface Contract and the product-level accessibility, responsive, copy, and recovery requirements. Motion treatment, media placeholders, wireframes, page theme, and design tokens are downstream UI design decisions.
    - In every package, record the Monetization Infrastructure Gate and Partner Channel Gate in `PRD.md`, including explicit `not_required` reasons. When either applies, carry its separately selected layers into `architecture.md` and `stack-decisions.md`; do not collapse billing, entitlement, merchant-of-record, affiliate, referral, and reseller responsibilities into one vendor label.
    - Draft the PRD's `## Ambition` section and the Metrics `Stretch` column as `references/output-contract.md` defines; a package created or enhanced under this contract version requires `## Ambition`.
    - Do not prepare wireframe data or create `wireframes.html`. Record `UI design: pending explicit ui-design-builder request` for a UI-bearing product.
    - Do not invoke `ui-design-builder` or `design-system-compiler` automatically. UI work remains a later explicit phase.
    - For a product with no UI surface — a headless API or backend service, or an automation whose only surfaces are notifications it sends into someone else's UI — record the UI-design handoff as `not_required` and publish no placeholder UI or design files.
    - Draft `DEPLOYMENT.md` from `../delivery-harness/assets/templates/DEPLOYMENT.template.md` when the package has a deployable surface: record the platform chosen in the deployment decision; seed the Required Secrets and Variables inventory with every exact name already established by the product or architecture; record known auth callbacks, allowed origins, webhooks, domains, roles, and other provider-side work in External Console Setup; and leave their human-owned statuses plus the remaining Human Setup Checklist for the owner. Record names and destinations only, never values. Do not invent implementation-owned key names or URLs: leave them visibly unresolved for `delivery-harness` to reconcile from the first usable build before its separately authorized deployment. A purely local product records `manual` mode or skips the file with a note in `stack-decisions.md`. Publish it to `docs/DEPLOYMENT.md` with the package.

Fill the product, owner when known, `core`, every applicable surface profile (including `web`, `api / backend`, `ios`, `android`, `macos`, `windows`, `browser extension`, `cli/toolchain`, `agent/automation`, and `other_nonpublic` when the matrix requires them), and only those supported release target IDs. Include one Outcome Coverage row for every PRD metric and required `TEST-*` signal scoped to the complete supported target set, including hybrids; a concrete `n/a — reason` is allowed only when the architecture proves that no activation scope applies. Preserve each metric's source/method and owner. Target Readiness must cover every architecture release target; each active target gets readiness evidence and each inactive target gets a concrete `n/a` reason. Outcome Coverage is a signal subset; it does not define the Target Readiness target set. Leave implementation-owned actions, routes, accounts, queries, release SHAs, artifact/build identities, sources, and evidence visibly pending. Run `python "<product-activation-skill-root>/scripts/check_activation.py" --activation <staged ACTIVATION.md> --prd <staged PRD.md> --architecture <staged architecture.md> --deployment <staged DEPLOYMENT.md> --stack-decisions <staged stack-decisions.md> --repo-root <repository-root>` before publication so target/profile drift and unapproved package/deployment inputs fail closed. ## Self-Review Before Product Definition Approval

Apply `../delivery-harness/references/pre-delivery-self-review.md#prd-self-review` after step 13's post-draft market reconciliation and accepted revisions. Recheck only the affected scope after step 14's stack decisions, before presenting step 15's Product Definition Approval. This is the only author pass over the candidate: the same producing agent applies the UI and technical perspectives of `references/prd-refinement.md` and repairs in-scope defects before owner review. This self-review plus the owner's Product Definition Approval is the complete PRD review budget; no independent review wave follows it. A finding after approval routes through a PRD delta round in `references/prd-refinement.md`, not a re-review. Record the producing agent identity, equal self-check agent identity, final candidate hash, actual checks, findings, repairs and conclusion in the existing Epic or task record. The shared contract owns re-checks after changes, blocking findings and the research-skip rule.

## Interview Rules

- When the owner has no technology preference, use the recommendation-review path: one coherent product-fit bundle plus one or two serious alternatives. Explain cost assumptions, maintenance, compatibility and change consequences in plain language. Reuse an explicit recommendation request for unresolved platform/database/auth questions; accept the resulting choices at the existing Stack Decision Checkpoint. No preference never means approval or delegated final selection.

- Do not ask questions already answered by the user's prompt.
- Mark optional questions clearly when they would improve quality but should not block progress.
- If the user authorizes assumptions, draft with explicit assumptions and open questions instead of continuing the interview.
- If the user gives conflicting requirements, resolve them before drafting or call out the conflict in `open questions`.
- Treat builder preference as a direction input, not as proof that users find the result usable. When it conflicts with user evidence or an accessibility requirement, record the conflict and validation need instead of silently following preference.
- In enhancement mode (Workflow step 2), never repeat questions the existing package already answers. Scope the free-text message and every `AskUserQuestion` call to what the new idea adds, changes, or leaves genuinely unresolved.

## Current UI Preflight

Before a `ui-design/3` direction round, validate the approved product package with `--ui-contract ui-design/3` alongside `--require-filled --require-approved --repo-root <root>`. A retained `ui-design/2` direction round instead uses `--ui-contract ui-design/2` and keeps its original rules. Each UI surface supplies copy status, operations, states and its exact responsive set. `ui-design/3` also fails an unreachable surface or an opened state without an exit; see `references/output-contract.md#operations-for-new-design-rounds`. PRD owns data, chart meaning, agent behavior and integration responsibilities; design chooses composition. Read the PRD directly without creating a duplicate per-page specification. Omitting the flag retains legacy validation.
