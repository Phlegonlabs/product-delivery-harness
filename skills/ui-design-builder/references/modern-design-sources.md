# Modern Web, Native And AI-Assisted Design

Sources inspected 2026-09-25. Publication dates below are stated by the source; undated living references are dated by inspection only. These are selected primary sources, not a claim to cover every recent release. Modern means task-fit, adaptive and coherent, not a mandated visual style. Apply the relevant platform guidance through the existing Design Brief, Platform rules and H2/H4/H5/H7/H8/H9 evidence; no new gate or competing design document.

## Web Baseline

- [web.dev: Responsive web design basics](https://web.dev/articles/responsive-web-design-basics): derive breakpoints from content and use flexible layout. Keep 390/768/1024/1440 as the default authored review set, then inspect intermediate widths. Wide canvases need intentional content limits and density rather than endlessly stretched text. Preserve existing approved targets.
- [W3C: Reflow, SC 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html): for applicable Web content, verify reflow at an equivalent 320 CSS-pixel width without lost information/function or two-dimensional scrolling. Respect the criterion's essential two-dimensional-layout exceptions. Record this as an accessibility stress case, not a fifth authored viewport or a reason to change the PRD target set.
- [W3C: Target Size Minimum, SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html): check pointer targets against the 24 by 24 CSS-pixel minimum or a documented criterion exception, including spacing. This is an accessibility floor, not the preferred size for every button. Use the product/platform's larger usable controls where appropriate; CSS px, iOS pt and Android dp are different units.
- [Vercel: Web Interface Guidelines](https://vercel.com/design/guidelines): inspect deliberate edge/baseline/optical alignment, balanced icon-label relationships, intrinsic flex/grid layout, keyboard focus and safe areas. Check reduced motion and animate named properties rather than `transition: all`. Treat these as engineering guidance, not a required Vercel stack or branded aesthetic. Record justified optical corrections at component level.

## Native Platform Baseline

- [Apple: Principles of great design, WWDC26](https://developer.apple.com/videos/play/wwdc2026/250/): apply purpose, familiar behavior, flexibility and careful execution to the actual task. Keep repeated actions predictable and preserve recovery; do not sacrifice usability for novelty.
- [Apple: Communicate your brand identity on iOS, WWDC26](https://developer.apple.com/videos/play/wwdc2026/251/): use content, typography and imagery to express identity while keeping navigation and conventional actions familiar. Shared branding does not require identical Web/iOS/Android components. Customize where it serves the product, not merely to replace native controls.

- [Apple: Get to know the new design system, WWDC25](https://developer.apple.com/videos/play/wwdc2025/356/): distinguish navigation/control layers from content; group actions by purpose and frequency and keep a primary action legible. Liquid Glass is platform material guidance, not a requirement to blur every card or reproduce it on the Web. Respect the supported OS and selected framework; verify contrast, scrolling and open layers on the actual platform. Do not add unsupported APIs or change an approved stack to imitate an effect.
- [Apple: Get started with Dynamic Type, WWDC24](https://developer.apple.com/videos/play/wwdc2024/10074/): use scalable text roles and inspect larger accessibility text sizes. Reflow labels and controls instead of shrinking text to preserve a fixed screenshot. Include safe areas, keyboard avoidance and supported orientations in the platform cases. Consult current HIG Layout/Typography/Accessibility for the deployment target; their dynamic pages were only partially extractable in this research, so use the inspected official talks as evidence rather than claiming a complete HIG audit.
- [Android: Accessibility API defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults): Compose uses a 48 dp minimum touch target and may expand hit areas beyond visible bounds. Inspect actual neighboring hit regions as well as button drawings. This is Android evidence, not a mandate to adopt Compose or copy iOS component geometry.

## Recent AI Coding Guidance

- [Apple: Create UI prototypes using agents in Xcode, WWDC26](https://developer.apple.com/videos/play/wwdc2026/227/): give agents specific features and stylistic intent, test with real content, and critically inspect interactions. Apply this to the existing primary/stress studies and direction selection; do not copy the demo's number of alternatives, change tooling or treat generated previews as production acceptance.
- [Vercel: Teaching agents product design, 2026-06-25](https://vercel.com/blog/teaching-agents-product-design-at-vercel): retain the reasons behind accepted design decisions, route agents to canonical sources, and distinguish deterministic checks from contextual judgment. Record rationale and relevant before/after evidence in the existing UI handoff and Epic. Existing code is evidence, not automatic endorsement. Add automated checks only for defined, testable invariants; this document does not implement a new linter.

- [Anthropic: Improving frontend design through Skills, 2025-11-12](https://claude.com/blog/improving-frontend-design-through-skills): make typography, composition and visual intent explicit before generation. Adapt this into the existing selected direction and Adopt/Adapt/Avoid rationale. Do not import its illustrative font bans, mandatory external fonts or aesthetic exaggerations; system fonts and restrained designs remain valid.
- [Anthropic: Harness design for long-running application development, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps): distinguish design coherence, originality, execution and functionality, and evaluate a running page rather than trusting author self-praise. Map these lenses to existing H dimensions and independent review authorization. Retain the current bounded repair budget; do not copy the experiment's many iterations, prioritization over usability, scope expansion or agent topology.
- [Google Labs: Stitch skills](https://github.com/google-labs-code/stitch-skills): the observed repository supports extracting a design description from frontend source and managing design systems. Adopt the source-grounded handoff principle: inspect existing components/tokens before proposing replacements and record names, roles and usage in the current UI handoff. Do not introduce a parallel DESIGN.md authority, install Stitch or upload product code by implication. The living repository has no publication date asserted here.

## Taste Skills: Selective Adoption

Locally inspected `design-taste-frontend` on 2026-09-25: brief inference, configuration, component/layout rules, accessibility/layers, redesign preservation and preflight sections. Its stated scope is landing pages, portfolios and redesigns, excluding dense product UI and native mobile. Compared the baseline of `design-taste-frontend-v1` and the separate `gpt-taste`; these are distinct local skills, not one required bundle. This is a reference review, not invocation of their generation workflows or a claim of a complete upstream audit.

Adopt these ideas through the current Design Brief and rubric:

- Write a short design read: surface purpose, audience, existing brand, intended character and constraints. Treat inferred preferences as proposals; they never replace the existing direction decision or select a new stack.
- Explain composition, motion and density in words tied to the task. A dense working view and a quiet showcase may share a brand without sharing spacing or animation. Do not add another numeric score or copy the default 8/6/4 settings.
- Define component roles consistently: radius by role, icon treatment, button prominence, spacing and layer order. Record layers such as content, sticky navigation, popover and modal in existing tokens/platform rules; inspect clipping and hit targets instead of escalating z-index until it appears fixed.
- Review CTA meaning as well as appearance. The same action should use consistent wording; repeated placement may be useful. Preserve approved copy and accessible names. Inspect label fit, contrast and line/descender clearance with actual fonts and required languages. Allow readable wrapping when appropriate instead of truncating, shrinking or rewriting approved labels to meet a one-line rule.
- For showcase pages, use section composition to serve different content responsibilities; remove empty filler cells and redundant labels. Do not force novelty into repeated task components, reorder reading/focus with dense grid packing, or add decorative assets merely to meet a quota.
- Audit the current product before a redesign and retain its valid brand, routes, content, accessibility and behavior. Use the existing enhancement scope and evidence, not a second redesign process.

Use `page-design-profiles.md` to adapt font avoid choices, expressive motion commitments and one- or two-line desktop headings by page purpose. Do not turn these into blanket product-wide rules. Mandatory dark mode or image generation, automatic dependency installs, page-wide overflow hiding and random layout selection remain outside these defaults. Never fabricate tool execution or preflight results. Standards and approved platform/product contracts take precedence over taste heuristics. Existing `frontend-design` remains the author, with the current review and approval boundaries; no Taste dependency or installation is introduced.
