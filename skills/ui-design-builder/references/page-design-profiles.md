# Design Profiles By Page Purpose

Use these authoring defaults for new or changed scope, not retroactive rules for approved pages. A profile describes a page's job, not its framework or a preset aesthetic. One product can mix profiles while sharing brand and component roles. Native platforms retain their own navigation, text scaling and input conventions.

## Select And Record

In the existing Design Brief, map each affected `UI-*` to its page purpose and profile. Record typography roles and avoid choices, headline target, density, motion intent, and justified exceptions. Reuse known decisions; resolve only missing choices through the current direction/motion intake. No new required heading, schema field, approval gate or global configuration is introduced. An included App and its showcase website need separate mappings.

| Profile | Typography and headline | Density and composition | Motion default to propose |
| --- | --- | --- | --- |
| Landing page | Deliberate display face with a readable body face; aim for a one- or two-line desktop hero heading. Avoid an unexamined generic font pairing when brand expression matters. | Low to medium density; visible primary message/action, purposeful section rhythm and content-specific media. | Expressive: one focal brand or product demonstration, plus control feedback; limit competing movement. |
| Portfolio page | Characterful display typography where it suits the work; one- or two-line desktop introduction, readable case-study titles and prose. | Let work lead; generous separation and varied project presentation where content warrants it. | Expressive: a purposeful project reveal or transition; keep browsing and case-study reading direct. |
| Dashboard / overview | Readable UI face, stable heading scale and aligned numeric roles. No hero-heading line quota. | Medium to high density; prioritize current status, exceptions and next action; consistent recurring components. | Functional only: state/progress/change feedback without ambient or cinematic loops. |
| Data list / table / detail | Legible labels and values, explicit number/date formatting; preserve long names with readable wrapping or approved access to full text. | High density when useful; stable columns, scanning alignment and reachable row/detail actions. | Functional only; avoid moving rows or controls while users compare, select or edit. |
| Form / settings / multi-step task | Readable labels, help and errors; concise headings without forced two-line wrapping. | Group by task, keep field/action placement predictable, reserve room for errors and longer translations. | Functional only: progress, validation and spatial continuity; never delay input, confirmation or recovery for an effect. |

For other purposes, derive a profile in the same brief from the nearest relevant task and state the differences; do not invent extra product pages to fit this table. On mixed-purpose pages choose by the primary task and name any bounded expressive region, rather than applying a marketing treatment to the whole workspace.

## Typography And Two-Line Headings

A selected direction may explicitly avoid named font families or set a two-line desktop headline requirement for its landing/portfolio pages. Keep these choices scoped by page and text role. Existing brand fonts, system fonts, language coverage and platform accessibility remain valid constraints. Do not turn an avoid list into a universal blacklist or install a font/library without the normal checks.

Measure the actual heading at each applicable desktop review target with loaded and fallback fonts. The default is one or two natural lines, not a forced line break or exactly two lines. First adjust container width and type scale within readable bounds. Mobile, localization and enlarged text may need more lines; record and inspect these exceptions. Never cut approved copy, clamp away text, shrink it below readable size or add nonbreaking spaces to pass. Copy changes return through their existing owner flow.

Only an accepted page-purpose/profile and motion decision is production design authority. Carry that accepted decision into direction rationale, connected HiFi, H1–H9 review, and, when required, the design-system pair and Harness implementation. Unselected direction studies and unselected profile recommendations do not authorize either.

## Motion Commitment And Review

The expressive defaults above are proposals, not automatic approval. Once selected in the existing motion intent, the named effect is required in HiFi: a static image or a promise to add it later cannot pass H6. Record its trigger, purpose, affected region, end state, compact behavior, performance constraints and equivalent reduced-motion path in the existing MM record. Respect an already accepted `not_required` or `functional_only` decision. Strong motion is appropriate only where it serves the selected page and direction; it never requires scroll hijacking, autoplay sound, a particular library or a generation provider.

Evaluate profile conformance through H1/H5/H7/H9 and required motion through H6, with actual normal/reduced-motion evidence. H2/H4/H8 layout, responsive and accessibility failures remain blockers in every profile. A two-line heading or impressive animation cannot compensate for overlapping buttons, clipped layers, lost focus or unreadable text. Use the existing consolidated repair budget and final matrix.
