## Required Skills And Inputs

1. **Resolve the agent-configured author and load `frontend-design` before directions, HiFi or design repairs.** Immediately before direction/HiFi authoring or repair, run `python "<delivery-harness-skill-root>/scripts/check_skill_bindings.py" --agents-md <target-AGENTS.md> --stage ui-design` using Installed Commands resolution. Agent configuration designates the authoring executor. The resolved writer must load the full owner-pinned `frontend-design` skill in its own context; a parent read, source snapshot, role title or earlier-stage check is no substitute. Never backfill usage evidence or silently replace the binding. Missing or conflicting dependencies block only the dependent authoring stage; preserve earlier approvals and closed historical records. This rule grants no spawn action. Assemblers and reviewers build the shell or validate; they do not make product-design decisions. Record the observed digest, retained `SKILL.md` snapshot path/hash, candidate path/hash and applied choices in `### Frontend Design Usage`; every stage digest must match the snapshot. Directions use its hierarchy, layout and visual-interaction methods; HiFi uses its full visual methods. Taste may supplement an approved direction, never replace the author.
2. **Resolve UI research through agent policy.** UI reference, PRD-surface, market, and code research are read-only assignments and may use multiple sibling `market_researcher` or `code_explorer` instances. Use `../product-definition-builder/scripts/readonly_assignments.cjs` as specified in `references/review-workflow.md`; retain the inventory, frozen packets, separate parent launch records and joined findings in the existing Epic/task record. Do not substitute graders for research, and do not apply the grader count cap to researchers. One designated UI writer owns each candidate checkout.
3. Use `impeccable` as the required HiFi quality review: one `critique` and one `audit`. It does not author the selected direction or edit the candidate, and its side effects require their own explicit authorization. Both must record PASS evidence before Visual Approval and publication; if the owner declines that authorization, the HiFi review stage is `blocked`.
4. Require an approved Product Definition and Stack Decision Checkpoint. Before a new round, run `python "<product-definition-builder-skill-root>/scripts/check_product_package.py" --prd <approved PRD.md> --architecture <approved architecture.md> --stack-decisions <approved stack-decisions.md> --repo-root <repository-root> --require-filled --require-approved --ui-contract ui-design/3` from the repository root. New initial and explicit full-redesign packages use `ui-design/3`; an existing `ui-design/2` package keeps `--ui-contract ui-design/2` and its original rules.
5. Read the complete PRD UI Surface Contract and the approved frontend stack, including component foundation and styling approach. A design that needs a stack change returns upstream before direction studies or Style Integration continues.
6. Read `references/artifact-lifecycle.md` and inspect any existing `ui-design.md`, direction captures, retained HiFi references, wireframes and design-system pair before drafting. Preserve stable `UI-*`, `UX-*`, `VD-*`, `REF-*`, and `RP-*` identities. Treat an existing wireframe as historical unless the package explicitly remains legacy.

## Workflow

Before direction or HiFi author dispatch, apply [Frontend Visual Inputs](../../../delivery-harness/references/frontend-visual-inputs.md). Include its block in the actual author task, not only the parent record. Use `direction` before selection and `hifi` after selection; retain the stage's existing approval requirements.

For initial UI work and affected frontend/mobile enhancements, apply `references/enhancement-recommendations.md`. Reuse supplied decisions, proactively recommend task-fit reference/CSS or native treatments, and carry explicit hero/motion requests into the existing UI/MM records. Recommendations never replace the existing approvals or actual platform evidence.

Before choosing incremental work, inspect the owner instruction for **full design rebuild with retained PRD**. Follow `references/design-translation.md` for that explicit exception, reading UX and iPhone scope. After skill updates and before implementation, apply `references/design-freshness.md`. Rebuild changes design authority, not product scope or filesystem permissions.

Enhancement mode takes precedence over the initial-design sequence below unless the owner explicitly selected a full design rebuild. Apply `references/enhancement-recommendations.md`'s Incremental UI Scope: add or patch only accepted pages/regions and connecting controls, retain every unaffected product screen and the approved direction, and record the before/after scope. Do not restart the all-screen authoring sequence, intake or direction selection for unchanged decisions. Complete package coverage means existing screens plus the delta, not redrawing existing screens. Re-run required validation and renew only affected decisions without rewriting old approval receipts.

1. Confirm the approved Product Definition and stack with the product preflight above, selecting `--ui-contract` by the package selection rule in Required Skills And Inputs. Read the complete PRD UI Surface Contract directly: page count and scope, each page's purpose and elements, operations, data and charting responsibilities where declared, agent integration boundaries, routes, states, responsive rules, copy responsibilities, traces, frontend and backend joins, and approved component foundation. Record only the exact PRD identities; do not copy the PRD into a second per-page inventory. Read `references/ui-design-intake.md` and `references/motion-and-media-routing.md`. Combine unanswered design, imagery and motion questions into one intake. Explicitly ask about unresolved reference images, screenshots, websites, Figma views or products, what to learn and what to avoid. Extend the Visual Preference Brief with the Design Brief in the existing UI intake. Reuse existing decisions; wait only for answers that block the next step.

    If intake leaves an unresolved visual or motion choice within the approved stack, consult the optional rule in `../delivery-harness/references/reference-selection.md` and only the relevant domain under `../delivery-harness/references/option-library/` before direction work. An unresolved CSS framework, component library, icon package/dependency, or stack selection returns to `product-definition-builder` before dependent direction work. Keep the approved stack; `frontend-design` remains mandatory, Taste/GPT Taste stays optional, and motion follows the CSS/WAAPI, Motion, GSAP and Three.js routes. Only visual and motion decisions within the approved stack belong here. The catalog adds no authority or automatic skill invocation.
2. Load `frontend-design` and translate the PRD with `references/design-translation.md` for direction authoring. The prompt for each direction reads the PRD UI Surface Contract directly. It states the approved page count, surface scope, element and operation responsibilities, states, responsive targets, copy/data obligations and integration boundaries; the Design Brief's Page-purpose mapping states page-specific constraints and where the design author has freedom. It does not lock hero, feature, CTA or another section recipe. Each direction and HiFi prompt opens with the delegation contract's maximum-creativity brief: pursue the most distinctive, high-craft visual concept the frozen PRD allows — ambitious hierarchy, typography, composition and motion, not a generic template.
3. With `frontend-design`, produce direction studies over the same representative primary/stress cases and relevant platforms. A `ui-design/3` package renders three materially different HTML studies by default, with applicable playable motion in one existing `docs/design/directions/<round>/` folder; the same author self-checks each, and the owner selects, mixes or modifies. Assemble new studies with `scripts/assemble_ui_review.py --mode direction` as specified in `references/output-contract.md`. For `ui-design/3` and `ui-design/2`, the owner may explicitly choose one recommended direction, recorded in the intake with the human Decision owner and Decided on; ambiguity or silence is not that choice. The study count must match the recorded mode. Enhancements retain an existing accepted direction for unchanged scope. Ask the owner to approve/select/mix/reject a new direction. Do not invent this decision. Simple functional motion may be proposed in a study; scripted work follows the Motion, GSAP or Three.js routes. Provider generation still needs its exact authorization.
4. After owner selection, use `frontend-design` to author the complete connected `ui-hifi/2` package with the shared reviewer assembled by the official tools. Apply `references/output-contract.md`: App, Web front and administration groups, one product canvas, each platform's sizes/states with real switchable variants, working product menus and tabs, `ui-hifi-copy/1` copy provenance, and a dedicated source-derived Design Tokens view with token purposes. Keep the package closed with every non-HTML asset inline; there is no sidecar asset registry. Keep reviewer shell/panels isolated from product CSS. Preserve the restrictive CSP, page hashes and all product interaction destinations. HTML native projections remain design evidence, not native implementation evidence.
5. Before Impeccable or H1–H9 scoring, run a cheap machine completeness check on the candidate manifest against the PRD UI Surface Contract and approved UI decisions. Require every PRD `UI-*`, page, route, state, responsive target and operation join to be represented by a real manifest page, product control or interaction; require the closed package, `ui-hifi-copy/1` provenance and declared interaction destinations to be accounted for. The author and reviewer separately check data/charting responsibilities, integration meaning and conditional media intent. A gap is repaired on the candidate and the check is rerun. This gate proves coverage, not visual quality, and does not replace the PRD-side product checks, Impeccable review, browser matrix, H1–H9, Visual Approval or compiler preflight.

    Inspect the `ui-design/3` CLI's advisory compiler-source diagnostics before owner review. Registry-dependent checks remain deferred; source diagnostics add no approval gate.
6. Run Impeccable critique/audit under the existing authorization, the browser matrix and H1–H9 in one diagnostic wave before human review. Use the same frozen candidate and current shared evidence. The lead returns one consolidated assessment and defect ledger for the same `frontend-design` author. Do not add a separate aesthetic or scoring wave. Use `ui-output/3` and `ui-evidence/3` for new observations. Separate machine results, qualitative assessments and human decisions. Recheck original defects and affected consumers on the changed candidate. Readiness requires an overall score of at least 85, every H1-H9 dimension at least 80, and no block or dispute. Recorded scores must match the actual assessment. Keep the existing diagnostic-wave, repair-batch and re-review budget.

    Follow [Repair Re-review Scope](../ui-grading-rubric.md#repair-re-review-scope) for that re-review. Inspect original defects and affected consumers; retain mandatory Impeccable checks, required browser coverage and a complete current assessment.
7. Present the complete current HiFi entry, every manifest-listed sibling page and affected `ui-design.md` handoff using verified absolute Markdown links. Request one **Visual Approval** covering copy, structure, menus, tabs, all other interactions, visuals and tokens. Use final logical paths in the authorized publication checkout, then canonical files in the source checkout after publication. Do not collect approval on `.ui-staging` paths. State scope and review focus. A preview panel is convenience only. Missing or stale pages/evidence block readiness. Wait for the explicit human decision; record owner, date, exact candidate and scope. Preserve valid authorization for same-scope repairs.
8. Apply the **Design System Need Gate** after Visual Approval. Only `required` invokes `design-system-compiler`. A `ui-design/3` package is always `required` and records `Package action: compile|update|reuse`; it publishes the complete `design-system/4` Markdown/JSON/HTML package, and its full HiFi review adds evidence for intermediate web widths. Without adjacent approved web widths, use the exact `Intermediate width check: not_applicable — no adjacent approved web viewport widths`; ordinary HiFi evidence and native size-class checks remain required. A `ui-design/2` required pair is `design-system/3`; both consume approved `ui-hifi/2` identities and have no wireframe binding. Its exact temporary marker is `Compiled design system pair: pending — design-system-compiler`; normal publication rejects it. Legacy `design-system/2` pairs retain their historical meaning and validation. `not_required` uses the approved HiFi/UI/PRD contract and records existing-pair disposition.
9. Run the normal publication checker at final logical paths in the authorized publication checkout. Retain every sibling, evidence file and required pair/preview. Publication, installation, commits and archival retain their separate authorization boundaries. The approved HiFi is the design baseline for this round's initial implementation. Apply `../product-definition-builder/references/review-presentation.md` here and at step 7. At final handoff, combine all current Product Definition and UI documents in one chat response, with individual verified absolute Markdown links, purpose and status, for whole-package review before a later implementation phase.

## Author Self-Review Before Handoff

Apply `../delivery-harness/references/pre-delivery-self-review.md` at two existing stage exits. In step 3, the same producing agent that used `frontend-design` reviews UI structure, operations and rendered representative direction studies, then repairs defects before requesting direction selection. After step 5's cheap completeness preflight, the same producing agent reviews and repairs the connected HiFi/UI HTML's copy, layout, states, responsive behavior and actual interactions before step 6's independent quality review. Record the producing agent identity, equal self-check agent identity, final candidate hash, inspected evidence, findings, repairs and `pass` or `blocked` in the existing Epic/task record, linking the existing UI evidence. Recheck the affected scope after changes; a stale hash or a different agent does not satisfy self-review.

These author checks retain the existing review/repair limits and do not replace Impeccable, H1–H9 or the owner's decisions. Missing applicable self-review or required evidence blocks handoff to Harness execution. Enhancements review the accepted delta and shared consumers; maintenance retains its existing route and records the applicable check without rebuilding historical HiFi.
