Record the observed digest, retained `SKILL.md` snapshot path/hash, candidate path/hash and applied choices in `### Frontend Design Usage`; every stage digest must match the snapshot, and the record proves traceability, not quality.

Reading runs no Impeccable command and writes nothing, so it needs no execution authorization (the manifest's `author_quality_reference` use). `frontend-design` stays the single author; the selected direction, the Design Brief and the PRD win over the craft floor. Running any Impeccable command stays with the Impeccable operator.
4. **Require an approved Product Definition and Stack Decision Checkpoint.** Only an owner-requested R0 exploration round ([review-workflow.md](../review-workflow.md#optional-r0-exploration-round)) runs earlier, with `--require-filled` alone.
    - Before a new round, run `python "<product-definition-builder-skill-root>/scripts/check_product_package.py" --prd <approved PRD.md> --architecture <approved architecture.md> --stack-decisions <approved stack-decisions.md> --repo-root <repository-root> --require-filled --require-approved --ui-contract ui-design/3` from the repository root.

5. **Read the complete PRD UI Surface Contract and the approved frontend stack,** including component foundation and styling approach. A design that needs a stack change returns upstream before direction studies or Style Integration continues.
6. **Read `references/artifact-lifecycle.md` and inspect what exists before drafting:** any `ui-design.md`, direction captures, retained HiFi references, wireframes and design-system pair. Preserve stable `UI-*`, `UX-*`, `VD-*`, `REF-*`, and `RP-*` identities. Treat an existing wireframe as historical unless the package explicitly remains legacy.

## Workflow

**Author dispatch.** Before direction or HiFi author dispatch, apply [Frontend Visual Inputs](../../../delivery-harness/references/frontend-visual-inputs.md). Put its block in the actual author task, not only the parent record. Use `direction` before selection and `hifi` after selection; retain the stage's existing approval requirements.

**Recommendations.** For initial UI work and affected frontend/mobile enhancements, apply `references/enhancement-recommendations.md`: reuse supplied decisions, proactively recommend task-fit reference/CSS or native treatments, and carry explicit hero/motion requests into the existing UI/MM records. Recommendations never replace the existing approvals or actual platform evidence.

**Full rebuild.** Before choosing incremental work, inspect the owner instruction for **full design rebuild with retained PRD**. Follow `references/design-translation.md` for that explicit exception, reading UX and iPhone scope. A rebuild changes design authority, not product scope or filesystem permissions.

**Delivery profile `mvp`.** The PRD's `## At a Glance` records the owner-selected `Delivery profile: standard | mvp` from the Harness System Review. Under `mvp`, author one direction study; the owner may accept it, and a second study is authored only on an owner request. The intake records `Direction mode: one recommended direction (mvp)`, Style Integration records `Direction decision: deferred to Visual Approval (mvp)` with no direction decision owner or date, and the Visual Approval records `Covers direction: yes`. The owner approves that direction and the HiFi together in the one Visual Approval, which also reviews the journey map and font pairings; no separate direction approval turn happens, and the standard profile keeps its explicit direction approval turn before HiFi. Author HiFi for the PRD's required surfaces only. After Visual Approval, compile a design system only when the recorded Need Gate is `required`, and the delivery Final UI Acceptance folds into the combined delivery review. The flow then has at most four owner gates: Product Definition Approval with the Stack Decision Checkpoint, Visual Approval, execution authorization, and release. Thresholds, first-wave Impeccable critique and audit, real-browser evidence, data safety and authorization do not change under `mvp`.

**Product tracks.** The PRD `Shape` row names the product track and fixes the required surfaces.
- `web` requires the landing surface and the primary return surface.
- `app` requires a landing or store-listing page, the store screenshot set, and the onboarding first three screens.
- `agent` requires the public docs page plus, when the Shape row records `console: operations`, the console's configuration, run-inspection and approval screens. The console is an internal-tool archetype: one direction, required surfaces only, full journeys.

Review and the completeness preflight join coverage against those surfaces.

**Enhancements.** Enhancement mode takes precedence over the initial-design sequence below unless the owner explicitly selected a full design rebuild. Apply `references/enhancement-recommendations.md`'s Incremental UI Scope: add or patch only accepted pages/regions and connecting controls, retain every unaffected product screen and the approved direction, and record the before/after scope. Do not restart the all-screen authoring sequence, intake or direction selection for unchanged decisions. Complete coverage is existing screens plus the delta, not redrawing existing screens. Re-run required validation and renew only affected decisions without rewriting old approval receipts.

1. **Confirm the approved Product Definition and stack with the product preflight above,** selecting `--ui-contract` by the package selection rule in Required Skills And Inputs.
    - Read the complete PRD UI Surface Contract directly: page count and scope, each page's purpose and elements, operations, data and charting responsibilities where declared, agent integration boundaries, routes, states, responsive rules, copy responsibilities, traces, frontend and backend joins, and approved component foundation. Record only the exact PRD identities; do not copy the PRD into a second per-page inventory.
    - Read `references/ui-design-intake.md` and `references/motion-and-media-routing.md`. Combine unanswered design, imagery and motion questions into one intake, and explicitly ask the reference, learn/avoid and owner reference library questions that the intake guide lists.
    - Extend the Visual Preference Brief with the Design Brief in the existing UI intake. Reuse existing decisions; wait only for answers that block the next step. The board starts from the owner's library when one exists, and the guide's one-time offer to add the round's references follows Visual Approval ([Owner Reference Library](../design-reference-guide.md#owner-reference-library)). The board and its proposed principles exist before direction authoring and reach the owner with the direction studies, or with the one study under `Delivery profile: mvp` ([Records](../design-reference-guide.md#records)).
    - If intake leaves an unresolved visual or motion choice within the approved stack, consult the optional rule in `../delivery-harness/references/reference-selection.md` and only the relevant domain under `../delivery-harness/references/option-library/` before direction work.
    - An unresolved CSS framework, component library, icon package/dependency, or stack selection returns to `product-definition-builder` before dependent direction work. Keep the approved stack; `frontend-design` remains mandatory, Taste/GPT Taste stays optional, and motion follows the routes and the stack rule in [Implementation Routing](../motion-and-media-routing.md#implementation-routing-after-direction-selection).
    - The intake does not ask the owner to decide the motion ceiling again; it asks which page gets which treatment within it. Only visual and motion decisions within the approved stack belong here. The catalog adds no authority or automatic skill invocation.
2. **Load `frontend-design` and translate the PRD with `references/design-translation.md` for direction authoring.**
    - Each direction prompt reads the PRD UI Surface Contract directly. It states the approved page count, surface scope, element and operation responsibilities, states, responsive targets, copy/data obligations and integration boundaries.
    - The Design Brief's Page-purpose mapping states page-specific constraints and where the design author has freedom. The prompt does not lock hero, feature, CTA or another section recipe.
    - Each direction and HiFi prompt opens with the delegation contract's maximum-creativity brief and its board, direction-match, time and ban-list lines ([Parent-Owned Delegation](../../../delivery-harness/references/delegation-contract.md#resolve-roles-before-direct-or-managed-work)); the prompt points at the board captures and the Design Brief instead of describing the style.
3. **With `frontend-design`, produce direction studies over the same representative primary/stress cases and relevant platforms.**
    - A `ui-design/3` package renders three materially different HTML studies by default, with applicable playable motion in one existing `docs/design/directions/<round>/` folder. The owner selects, mixes, modifies or asks for variants of one study ([Direction Records](../design-reference-guide.md#direction-records)). The study count must match the recorded mode; under `Delivery profile: mvp`, the mvp paragraph above applies.
    - When the mode calls for more than one study and agent policy and observed capacity provide more than one frontend author, the parent launches one author per study at the same time. Each author follows the binding rule above, receives the same frozen inputs, reference board, Design Brief and representative cases, is told which direction it owns (`direction <k> of <n>`), reads no other study, and writes only its own study file in its own isolated checkout. With one available author, that author writes every study in sequence.
    - Assemble new studies with `scripts/assemble_ui_review.py --mode direction` as specified in `references/output-contract.md`; a round of three also gets `_compare.html`, which puts the studies side by side. When parallel authors return, the parent brings each study file into the round's one `docs/design/directions/<round>/` folder and records the comparison.
    - If two studies present the same idea under the [Style Intake](../ui-design-pass.md#style-intake-gate) comparison rule, the parent returns one to its author for one revision, with the other study named as what to avoid; this adds no owner turn.
    - For `ui-design/3` and `ui-design/2`, the owner may explicitly choose one recommended direction, recorded in the intake with the human Decision owner and Decided on; ambiguity or silence is not that choice. Ask the owner to approve/select/mix/reject a new direction. Do not invent this decision.
    - Simple functional motion may be proposed in a study; scripted work follows the code routes in [Implementation Routing](../motion-and-media-routing.md#implementation-routing-after-direction-selection). Provider generation still needs its exact authorization.
4. **After direction selection, the HiFi author maps the journeys before any HiFi screen.**
    - The HiFi author is the selected study's author when the host can continue that author; otherwise it is a fresh `frontend-design` author who reads the selected study and the Design Brief. A mix or modification is revised by the author of the direction it is based on. The journey map and font pairings belong to the HiFi author.
    - Take the 2–5 core journeys from the PRD's `## User Journeys`: first run / onboarding, the core loop, the return loop, and enough others that every surface the Shape row requires sits on one.
    - Draw each as a simple flow diagram in the selected direction, one case per journey, on one page `journeys.html` in the round's `docs/design/directions/<round>/` folder. Assemble it alone with a one-direction profile, as `references/output-contract.md` describes for a revised study.
    - Every step is a PRD page, state or control. The map adds no page, route, state, control or copy, and a step the PRD lacks returns to `product-definition-builder`.
    - Ask the owner to confirm the journey set in the same reply as direction selection, or right after it; this is no new approval gate. In the same reply, present 2–3 font pairings for the selected direction, with display and body roles and CJK coverage when the PRD language needs it, and name the default faces you avoided and why; reuse an owner-supplied brand font without asking. This is a small part of this step, not a new round.
    - Record the confirmed set and the `journeys.html` path and SHA-256 under the Design Brief's Detailed decisions, and the chosen pairing and avoided faces under its typography roles and avoid choices.
    - Under `Delivery profile: mvp`, the mvp paragraph above applies. An enhancement maps only the journeys its accepted delta adds or changes.
5. **After owner selection and the journey map, the HiFi author uses `frontend-design` to author the complete connected `ui-hifi/2` package with the shared reviewer assembled by the official tools: kit and pilot first, then the other journeys.**
    - The package has three layers: kit, composition and art ([Connected HiFi Reference](../ui-design-pass.md#connected-hifi-reference)).
    - **Kit and pilot.** The author builds the kit together with the pilot pages, from the selected study. The pilot is the core-loop journey plus the landing surface when that is not on it, and it includes the product's hardest layout, overlay and long-text cases. No kit component is drawn without a pilot page that uses it with real content.
    - **Checks on the pilot.** The author runs the completeness check (missing-page findings for pages not yet authored are expected), the matrix driver with `--only` and `--measure-a11y`, and `slop_scan.py` ([HiFi Self-Review](../../../delivery-harness/references/pre-delivery-self-review.md#hifi-self-review)).
    - **Pilot diagnosis.** The lead grader and the Impeccable operator review the pilot pages once and return findings only: no receipts and no score gate. A comparison sheet of the pilot beside the selected study checks that the kit did not flatten the direction. Show the owner the pilot; this is a look, not a gate, and no reply means continue.
    - **One batch, then the kit lock.** Fix the findings in the kit and the composition approach in one batch, then lock the kit. Afterwards only an added component or variant (with all its states) or a value fix forced by a script failure may change it. A rename, removal or geometry change of an existing component needs a recorded reason and a rerun of the scripts on every consumer.
    - **Remaining journeys** are assembled from the locked kit, in journey order, in two passes: a static pass for every journey, the author self-check, the motion pass, then a recheck of the pages motion touched ([Composition Before Motion](../motion-and-media-routing.md#composition-before-motion)). The author runs the checks after each journey, not once at the end.
    - Skip the pilot diagnosis when the product has one journey or about six pages or fewer: the wave is then the first review. An enhancement assembles from the existing kit or design system and has no pilot.
    - Apply `references/output-contract.md`: App, Web front and administration groups, one product canvas with its screens grouped by journey, each platform's sizes/states with real switchable variants, working product menus, tabs and disclosures, `ui-hifi-copy/1` copy provenance, and a dedicated source-derived Design Tokens view with token purposes.
    - Keep the package closed with every non-HTML asset inline; there is no sidecar asset registry. Keep reviewer shell/panels isolated from product CSS. Preserve the restrictive CSP, page hashes and all product interaction destinations. HTML native projections remain design evidence, not native implementation evidence.
6. **Before Impeccable or H1–H9 scoring, run a cheap machine completeness check on the candidate manifest against the PRD UI Surface Contract and approved UI decisions.**
    - Require every PRD `UI-*`, page, route, applicable state, responsive target and operation join to be represented by a real manifest page, product control or interaction; require the closed package, `ui-hifi-copy/1` provenance and declared interaction destinations to be accounted for.
    - The author and reviewer separately check data/charting responsibilities, integration meaning, conditional media intent and that every confirmed journey step maps to a manifest page or state; the command does not read `journeys.html`.
    - A gap is repaired on the candidate and the check is rerun. This gate proves coverage, not visual quality, and does not replace the PRD-side product checks, Impeccable review, browser matrix, H1–H9, Visual Approval or compiler preflight.
7. **Run Impeccable critique/audit under the intake's authorization, and judge the author's browser matrix capture and H1–H9, in one diagnostic wave before human review.**
    - Dispatch only after the parent's [readiness gate](../ui-grading-rubric.md#capability-and-authorization) prints READY for the author's capture. The author records each kept `a11y` failure in `a11y-dispositions.json` beside that capture ([Readiness Check](../review-evidence.md#readiness-check)).
    - Launch the wave's independent readers together, not one after another; a visual review split into scoped calls by page group launches those calls together as one attempt. Use the same frozen candidate and current shared evidence. The wave uses the author's capture; reviewers do not capture the matrix ([Author Self-Review Before Handoff](#author-self-review-before-handoff)).
    - The lead returns one consolidated assessment and defect ledger for the HiFi author. Do not add a separate aesthetic or scoring wave.
    - Use `ui-output/3` and `ui-evidence/3` for new observations. Separate machine results, qualitative assessments and human decisions.
    - Readiness follows [Scores](../ui-grading-rubric.md#scores); repair and re-review follow [Repair Re-review Scope](../ui-grading-rubric.md#repair-re-review-scope). The first wave covers the base matrix from the author's capture and samples the stress axes as [First-Wave Audit Axes](../ui-grading-rubric.md#first-wave-audit-axes) states.
8. **Present the complete current HiFi entry, every manifest-listed sibling page and affected `ui-design.md` handoff using verified absolute Markdown links.**
    - Request one **Visual Approval** covering copy, structure, menus, tabs, all other interactions, visuals and tokens.
    - Link them at final repository paths on the task branch, with the comparison sheet beside them so the owner sees the candidate next to the selected direction. Do not collect approval on `.ui-staging` paths.
    - State scope and review focus. A preview panel is convenience only. Missing or stale pages/evidence block readiness.
    - Wait for the explicit human decision; record owner, date, exact candidate and scope. Preserve valid authorization for same-scope repairs.
9. Apply the **Design System Need Gate** after Visual Approval. Only `required` invokes `design-system-compiler`.
    - Under `Delivery profile: mvp`, the recorded Need Gate decision governs; the gate may record `not_required` with its reason when the approved HiFi and the PRD UI surface contract are sufficient for implementation, and the approved UI target row then carries the conformance identity.
    - A `ui-design/3` package records `not_required` only under that mvp exception; otherwise it is `required` and records `Package action: compile|update|reuse`, publishes the complete `design-system/4` Markdown/JSON/HTML package, and its full HiFi review adds the `Intermediate width check`, with its exact `not_applicable` record when no adjacent approved web widths exist ([HiFi Review](../output-contract.md#hifi-review)).
    - A `ui-design/2` required pair is `design-system/3`; both consume approved `ui-hifi/2` identities and have no wireframe binding. Legacy `design-system/2` pairs retain their historical meaning and validation.
    - The exact temporary marker `Compiled design system pair: pending — design-system-compiler`, its rejection by normal publication and the `not_required` pair disposition follow [Retention And Design System Need Gate](../ui-design-pass.md#retention-and-design-system-need-gate).
10. **Run the checker at the final paths** as [Artifact Lifecycle](../artifact-lifecycle.md#locations) states.
    - Retain every sibling, evidence file and required pair/preview. Publication, installation, commits and archival retain their separate authorization boundaries. The approved HiFi is the design baseline for this round's initial implementation.
    - Apply `../product-definition-builder/references/review-presentation.md` here and at step 8. At final handoff, combine all current Product Definition and UI documents in one chat response, with individual verified absolute Markdown links, purpose and status, for whole-package review before a later implementation phase.
    - Rewrite the current Epic's `## Handoff` block with the Visual Approval state, the final paths, and the next skill's first command.

## Author Self-Review Before Handoff

Apply `../delivery-harness/references/pre-delivery-self-review.md` at two existing stage exits.

- In step 3, each study's producing agent reviews its UI structure, operations and rendered representative study, then repairs defects before the owner's direction selection.
- In step 5 the same producing agent runs the pilot checks and the checks after each journey. After step 6's cheap completeness preflight it runs the matrix driver (`hifi_matrix_capture.py`) with `--measure-a11y` on the whole package, repairs its geometry FAILs and console errors, and reads renders for the pages it changed before step 7's independent quality review.
- The driver's `--measure-a11y` measurements (contrast, target size, text clip, text split, focus visible, text growth) change no case result. The author fixes each measured failure or records a disposition with a reason, as for a `slop_scan.py` cluster; the lead grader reads the measurements and dispositions as H4/H8 evidence, and an undisposed measured failure is a finding.
- The author's last clean driver run, on the exact bytes that are then frozen, is the candidate's one matrix capture. Nobody captures the same bytes again; the wave checks and samples it ([Review Evidence](../review-evidence.md)).
- After the consolidated repair the author reruns the completeness check, the driver with `--carry-from` and `--measure-a11y`, and `slop_scan.py`, and adds an after-capture for every ledger row, before the re-review. Until the parent's [readiness gate](../ui-grading-rubric.md#capability-and-authorization) with the ledger prints READY, the candidate returns to the author and no review is spent ([Repair Re-review Scope](../ui-grading-rubric.md#repair-re-review-scope)).
- Both exits include the `slop_scan.py` run, the `capture_sheet.py` comparison sheet and the author's direction match estimate, as that reference lists them.
- Record the producing agent identity, equal self-check agent identity, final candidate hash, inspected evidence, findings, repairs and `pass` or `blocked` in the existing Epic/task record, linking the existing UI evidence. Recheck the affected scope after changes; a stale hash or a different agent does not satisfy self-review.
- These author checks retain the existing review/repair limits and do not replace Impeccable, H1–H9 or the owner's decisions. Missing applicable self-review or required evidence blocks handoff to Harness execution.
- Enhancements review the accepted delta and shared consumers; maintenance retains its existing route and records the applicable check without rebuilding historical HiFi.
