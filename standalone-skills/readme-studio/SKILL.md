# README Studio

Make the project understandable and memorable from its README. Lead with its brand and the experience it offers, then give the reader a working path to try it. A polished result may be intricate; use the simplest GitHub-supported presentation that achieves it.

## Ground The Work

Read the target repository's effective instructions, existing README variants, public product facts, manifests, license and available brand/demo assets. Preserve its language, audience, approved design and working commands. Inspect file names before content; never read credentials to write public copy. Reuse the target's document/change record when one exists; a Harness installation is not required.

Distinguish a product showcase, CLI, library/SDK and monorepo entry point. Identify the primary reader and the action they should take. Ask only for a consequential brand/audience choice that the project cannot answer. Keep unrelated documentation and approved product decisions intact.

Read [the case library](references/case-library.md) to select useful visual and writing techniques. Cases are source observations, not measured rankings or proof of rendered appearance. Inspect the live rendered reference when visual fidelity matters; refresh facts before adopting them.

## Compose Around The Project

- Make the opening distinctive: project identity, a concrete promise, a strong real visual and a clear route to try or install it. Match the existing brand rather than pasting a fixed hero recipe.
- Show what the product does with an actual screenshot, output example or short demo. Explain the reader's task and resulting benefit; support compatibility, performance and credibility claims with project evidence.
- Build a readable rhythm with headings, images, short copy and selective tables. Badges earn their place by answering a useful question. Put extended reference material behind documentation links or applicable collapsed sections.
- Keep the main quickstart visible and copyable. A CLI needs a useful command after install; an SDK needs a minimal runnable example; an app needs a supported download or try-it route. Use only channels the project actually supports.
- Preserve license, trademark, attribution, contribution and operational information that readers need. Do not copy another project's logo, screenshots, text or license terms as the project's own.

The section order and visual treatment remain design choices within the user's scope. Do not flatten a requested ambitious presentation into a generic checklist. A writing pass does not authorize a product redesign or invent features.

## Author And Verify

Read [rendering and evidence](references/rendering-and-evidence.md) before changing presentation, media or a README used by a registry. Route visual authoring through the target host's required frontend binding and design skills, resolved from the target's effective instructions and observed skill configuration rather than this repository's defaults, never a generic author when that route is mandatory; plain factual copy edits follow the target's documentation rules.

Without target context, return a direction proposal and name the missing context before dependent authoring; a read-only direction exercise is not a visual implementation or rendered acceptance.

Check local assets, relative links, heading anchors, commands and examples. Inspect the actual destination renderer when available and capture evidence as Media And Claims describes. A local Markdown preview is fallback evidence, not GitHub or registry verification; name any unavailable renderer.

For release-related edits, reconcile version, downloads, supported platforms and installation instructions against the actual artifacts and per-channel publication state. Use `release-packager` if it is available and packaging is in scope; otherwise follow the project's native release process.

## Deliver

Return the edited README/assets, chosen reference techniques, actual checks and remaining gaps. Separate an authored README, inspected render, tested quickstart and published package. Preserve local Git, installation and external-action authorization; selecting this skill does not grant them.
